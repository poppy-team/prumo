# 17 — Plugin, Extension Architecture e Public SDK

> Status: Especificação especializada do Harness / Code Agent (Capítulo 17).


# Objetivo

Permitir expansão sem repetir o modelo de extensões web pesadas ou dar a plugins confiança irrestrita.

# Tipos de extensão

```
Harness Extensions
├── ModelProvider
├── AgentProvider
├── Custom Connectivity Adapter
├── ToolProvider / MCP bridge
├── SandboxProvider
├── LanguageIntelligenceProvider
├── Test/Quality Provider
└── Agent/Workflow package

Client Extensions
├── commands
├── panels/views
├── themes
├── keybindings
└── renderers/formatters
```

# Não misturar trust domains

Plugin de tema não precisa de shell. Model provider não precisa editar filesystem. Um painel não recebe secrets por padrão.

# SDK Go

O Harness deve eventualmente expor API pública suficiente para embedding e providers, mas apenas depois dos contracts internos estabilizarem.

Providers customizados são parte explícita do objetivo: usuários devem poder registrar **Custom Model Providers** e **Custom Agent Providers** sem recompilar o Core. Configurações puramente declarativas cobrem endpoints compatíveis/custom HTTP; adapters com código executável seguem o trust model de plugins/process isolation/WASM quando necessário.

Nenhum custom provider recebe filesystem, network irrestrita ou secrets implicitamente. Instalação, conexão e autorização permanecem eventos separados.

Exemplo conceitual:

```go
runtime := prumo.NewRuntime(config)
runtime.RegisterModelProvider(provider)
runtime.RegisterTool(tool)
runtime.RegisterSandbox(sandbox)
run, err := runtime.Run(ctx, request)
```

# Client SDK

Para clients Rust/outros, preferir protocolo versionado em vez de FFI interna. Isso reduz coupling e permite daemon remoto.

# Plugin sandbox

Avaliar formatos diferentes por classe:

- declarative manifests para commands/themes;
- process-isolated plugins via RPC para código não confiável;
- WASM/WASI onde capabilities e performance fizerem sentido;
- Lua apenas se houver caso claro de scripting local e permission model adequado.

# Compatibility

Manifest deve declarar protocol version, capabilities, permissions, platform, runtime, dependencies, checksum/provenance e cleanup.

# Regra de segurança

Instalação de plugin e autorização de capabilities são eventos separados. Instalar não equivale a conceder acesso total.

# Marketplace

P2/P3. Primeiro resolver local directory/Git/package install com lockfile e provenance. Marketplace central não deve dirigir a arquitetura.
