# Problema

O Prumo já possui Model Registry e Router, mas um harness precisa efetivamente conversar com provedores e controlar streaming, usage, cancellation, tool calling e erros.

# Separação proposta

```
Model Registry       → o que o modelo é
Model Router         → qual modelo/conexão deve ser usado
Model Provider       → Prumo chama um modelo e controla o agent loop
Agent Provider       → Prumo consome um runtime de agente externo
Connectivity Runtime → auth + transport + capability normalization
```

`ModelProvider` e `AgentProvider` são conceitos distintos. Um Codex/Antigravity/Kiro/Copilot autenticado pelo runtime oficial não deve ser reduzido artificialmente a uma chamada de modelo.

# `ModelProvider` conceitual

```
Capabilities()
Models()
Stream(ctx, Request) → EventStream
Count/EstimateTokens()
Cancel()
Health()
```

# Eventos mínimos

- response started;
- text delta;
- reasoning summary delta quando suportado e permitido;
- tool call started / arguments delta / completed;
- usage update;
- provider warning;
- completion;
- retryable failure / non-retryable failure.

# Provider adapters iniciais

A ordem deve seguir uso real, não quantidade de logos. Um adapter OpenAI-compatible pode cobrir muitos gateways/local models; adapters especializados entram quando capacidades divergem.

O Prumo também suporta **Custom Model Providers**, incluindo endpoints OpenAI-compatible, Anthropic-compatible, gateways locais/corporativos e configurações custom HTTP atrás de contratos estáveis. Um provider customizado declara credential source, base URL, capabilities, models e overrides necessários sem vazar sua configuração para o domínio canônico.

Para runtimes de agentes externos, usar o [22 — Agent Connectivity Runtime: Providers, OAuth, ACP, SDK, RPC e CLI](ch22.md), que cobre ACP, OAuth vendor-managed, SDKs, JSON-RPC, JSONL/headless e CLIs estruturadas.

# Fantasy como acelerador Go

Estudar **Charmbracelet Fantasy** como adapter inicial para normalização de providers/tool calls. Não tornar seus tipos parte da API canônica do Prumo. O contrato Prumo deve sobreviver à troca da biblioteca.

# Router v2

Além de privacy/context/latency/canary, avaliar por tarefa:

- coding quality;
- patch quality;
- tool-call adherence;
- agentic reliability;
- structured-output adherence;
- effective long-context quality;
- cost;
- TTFT e throughput;
- cache behavior;
- provider health/stability;
- modality;
- reasoning controls;
- privacy/data residency.

# Model Gateway / Routing Runtime

O Router v2 evolui para um `ModelGateway` explícito quando routing/fallback/pools são habilitados. O Gateway trabalha somente com `ModelProvider`s/targets compatíveis e não força runtimes externos de agentes através de uma API genérica.

Capabilities incluem `ModelRoute`, `RouteTarget`, `RoutingPolicy`, `FallbackPolicy`, `ProviderHealth`, `QuotaState` e `AccountPool`, com circuit breaker, cooldown e fallback auditável. Fallback automático só é transparente antes de efeitos observáveis; depois disso a recuperação pertence ao Handoff Runtime.

Especificação consolidada: [24 — Workforce Runtime, Model Gateway, Routing, Fallback e Handoff](ch24.md).

# Budget integration

Cada resposta real deve alimentar o Budget Envelope com usage observado e pricing versionado. Reservas precisam evitar iniciar uma etapa que já não cabe no budget hard.

# Failure taxonomy

Separar pelo menos: rate limit, quota, timeout, provider 5xx, invalid structured output, context overflow, unsupported capability, cancellation, policy denied, model refusal, transport failure e unknown.

# Critério para não criar dependência excessiva

Bibliotecas de provider são aceitáveis se forem **implementation details**. O usuário continua podendo distribuir o Prumo como binário autocontido quando a dependência puder ser compilada dentro dele.
