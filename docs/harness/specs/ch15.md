# Por que daemon/client

Paseo demonstra bem o valor de separar agent process orchestration dos clientes. No Prumo Code Agent, essa separação também permite que Desktop, TUI, CLI e ACP acompanhem o mesmo Run sem duplicar estado.

# Modos de implantação

```
Mode 1 — embedded
client + harness no mesmo processo/binário quando apropriado

Mode 2 — local daemon
client ↔ prumo-agentd ↔ workspace/models/tools

Mode 3 — remote host
client ↔ secure transport ↔ prumo-agentd na workstation/server

Mode 4 — distributed - futuro
control plane ↔ workers/sandboxes
```

# Regra

Começar com uma API/protocolo que não dependa de sockets mesmo que a implementação inicial seja in-process. Isso permite migrar para local IPC sem reescrever domain messages.

# Agent Protocol

Eventos candidatos:

- run created/state changed;
- session attached/detached;
- turn started/completed;
- model stream delta;
- tool requested/started/completed;
- permission requested/resolved;
- workspace/process update;
- diff changed;
- context/budget update;
- evidence/gate update;
- checkpoint/resume;
- error/warning.

# Local IPC candidates

Avaliar Unix domain sockets + Windows named pipes como baseline. HTTP/WebSocket pode ser boundary opcional para remote/browser clients; não precisa ser protocolo interno único.

# Reconnect/replay

Cliente envia last event sequence e recebe replay/snapshot + delta. UI deve sobreviver a restart sem reconstruir estado lendo transcript humano.

# Cross-device

P2. Se entrar: authentication/pairing, E2E encryption, device capabilities, permission delegation e remote filesystem semantics devem ser explícitos. Não copiar relay cloud antes de provar necessidade.

# Escalabilidade

A primeira escalabilidade necessária é **múltiplos Runs locais concorrentes com worktrees/sandboxes**, não Kubernetes. Workers distribuídos entram apenas se uso real justificar.

# Ownership

Um Run deve possuir/lease workspace e process resources. Concorrência sem ownership claro gera patch conflicts e side effects ambíguos.
