# Decisão arquitetural

Não tratar “RAG” como “colocar uma LLM pequena para procurar documentos”. Separar funções especializadas:

```
Canonical Knowledge
      ↓
Deterministic Parser / Structural Index
      ↓
FTS5 + BM25 + filters + graph
      ↓
Embedding Retriever        optional local encoder
      ↓
Reranker                   optional / on demand
      ↓
Context Compiler
      ↓
Tiny Knowledge Worker      optional / on demand
      ↓
Structured Proposal
      ↓
Schema + authority + provenance + deterministic validation
```

A LLM local é um **assistente de conhecimento**, nunca a autoridade documental.

# Por que vale a pena

- funciona offline e preserva privacidade para documentos locais;
- reduz chamadas pagas para tarefas mecânicas de organização;
- permite indexação e busca sem depender do provider principal;
- ajuda o Memory Atlas a crescer sem enviar todo o corpus para serviços externos;
- permite compaction e catalogação em background/local, sem consumir o orçamento do modelo principal;
- reduz tokens porque o modelo principal recebe somente registros já filtrados e summaries compactos;
- cria uma experiência consistente mesmo quando API/OAuth/provider está indisponível;
- favorece hardware modesto se os modelos forem carregados sob demanda.

# Regra de ouro: deterministic first, model only when semantic ambiguity exists

O Prumo não deve gastar inferência local para trabalho que código normal resolve melhor.

## Determinístico

- parsear Markdown/JSON/AST;
- extrair headings, links, IDs, code fences e refs;
- validar schemas;
- detectar stable IDs conhecidos;
- FTS5/BM25;
- graph traversal;
- exact dedup por digest;
- dependency/invalidation;
- ordenar e agrupar dados estruturados;
- gerar tabelas, índices, backlinks e manifests;
- atualizar artefatos via Documentation Compiler.

## Embedding/reranker

- semantic retrieval;
- similar-section discovery;
- near-duplicate candidates;
- clustering;
- related-memory candidates;
- query expansion candidate retrieval;
- code/text cross-lingual retrieval quando suportado.

## Tiny Knowledge Worker

- classificar o papel semântico de uma section;
- sugerir tags/domains/technologies;
- produzir summaries compactos;
- extrair candidate `Decision`, `Requirement`, `Constraint`, `Risk`, `Finding` e `Claim` em output estruturado;
- sugerir vínculos Section → Contract/KnowledgeItem;
- sugerir duplicates, contradictions e supersession para revisão;
- normalizar research notes em `ResearchRecord` candidato;
- produzir `KnowledgeDelta` compacto;
- gerar títulos e descrições curtas;
- preparar query rewrites para retrieval;
- produzir draft prose quando necessário.

Não pode aceitar decisões, alterar authority, satisfazer gate crítico ou tornar uma inferência canônica sem as políticas normais de validação/review.

# Recomendação de perfis do instalador

## Core Only

Nenhum modelo baixado.

```
Prumo Core
+ SQLite / FTS5 / BM25
+ structured filters
+ graph retrieval
+ deterministic Documentation Compiler
```

É um modo first-class, não fallback degradado.

## Local Knowledge Lite — recomendação para maioria dos usuários

```
Granite Embedding 97M Multilingual R2
+ FTS5/BM25
+ graph
+ Qwen3-0.6B optional/lazy-loaded
```

O encoder pode operar de forma persistente ou em worker leve. O generator deve ser carregado somente quando há trabalho semântico que justifique inferência.

## Local Knowledge Standard

```
Granite Embedding 97M Multilingual R2
+ Qwen3-0.6B/1.7B Knowledge Worker
+ optional reranker
```

Escolher 0.6B vs 1.7B por benchmark/hardware. O installer pode recomendar automaticamente sem impedir escolha manual.

## Local Knowledge Enhanced

```
Qwen3-Embedding-0.6B
+ Qwen3-Reranker-0.6B
+ Qwen3-1.7B or quality-class local worker
```

Voltado a grandes bases, code-heavy retrieval e hardware com RAM confortável.

## Custom

O usuário pode registrar encoder/reranker/generator próprios desde que declarem capabilities e contratos compatíveis.

Nunca embutir pesos enormes dentro do binário principal. O Package/Runtime Manager baixa artifacts pós-instalação, valida SHA-256/signature quando disponível e mantém cache/versionamento.

# Runtime architecture

Manter interfaces separadas:

```
EmbeddingProvider
RerankProvider
KnowledgeGenerationProvider
```

Implementações possíveis:

```
Local
├── llama.cpp / GGUF adapter
├── ONNX Runtime / ONNX embedding adapter
├── OpenVINO where useful
└── future platform-native acceleration

Remote
├── custom OpenAI-compatible embedding/rerank
├── provider-native APIs
└── user-defined providers
```

Não acoplar o Knowledge Runtime a Ollama/LM Studio/llama.cpp como fonte de verdade. Eles são runtimes/adapters substituíveis.

# Load / unload policy

A arquitetura deve priorizar idle footprint baixo.

```
Indexer event
→ deterministic parse
→ batch embeddings
→ unload encoder if policy requests

Ambiguous semantic work
→ load Tiny Knowledge Worker
→ constrained structured generation
→ validate
→ persist proposal
→ unload after idle TTL
```

Reranker trabalha somente no candidate set pequeno produzido por FTS/vector retrieval.

# Retrieval recomendado

Não usar vector search sozinho.

```
Query
→ scope / authority / freshness filters
→ FTS5/BM25 lexical candidates
  + vector semantic candidates
  + typed graph neighbors
→ union + dedup
→ optional reranker
→ diversity / authority / freshness policy
→ progressive disclosure
→ Context Compiler v2
```

Hybrid retrieval deve ser benchmarkado contra lexical-only; embeddings continuam derivados e podem ser apagados/reconstruídos.

# Document intelligence pipeline

```
Changed canonical document
→ AST parser
→ SectionID matching
→ deterministic metadata
→ embedding generation
→ semantic classification only if needed
→ structured extraction proposals
→ schema validation
→ contradiction/duplicate candidates
→ Knowledge Manifest / indexes
→ affected artifacts via BuildGraph
```

O modelo pequeno **não reescreve o documento inteiro** como rotina. Ele produz pequenos objetos estruturados que o resto do sistema pode verificar.

# Structured output contract

Preferir constrained output:

```json
{
  "section_role": "architecture-invariant",
  "summary": "...",
  "candidate_claims": [],
  "candidate_tags": [],
  "related_contracts": [],
  "confidence": "medium",
  "source_refs": []
}
```

Falha de parse/schema → discard/retry/fallback; nunca persistir texto livre quebrado como knowledge canônico.

# Privacy, security e trust

- modelos locais não ganham autoridade adicional por serem locais;
- external/untrusted document text permanece **data**, não instruction;
- prompt injection defenses continuam necessárias mesmo offline;
- secrets devem ser redigidos antes de index/summarization quando policy exigir;
- embeddings são derivados mas podem vazar informação semântica: respeitar privacy class e deletion policy;
- projetos podem desabilitar vector index e/ou Local AI;
- Memory Atlas cross-project respeita project-private/personal/public scopes;
- model artifacts têm source, digest, license e provenance verificáveis;
- nenhum modelo baixado executa código/plugin arbitrário por default.

# Licenciamento

Para um pack oferecido diretamente pelo instalador, favorecer artifacts com termos simples para redistribuição/uso comercial, especialmente Apache-2.0.

Liquid LFM2.5 é tecnicamente muito atraente por footprint, mas usa `LFM Open License v1.0`. A documentação oficial confirma que **redistribuição é permitida**, desde que o distribuidor inclua a licença e retenha notices/atribuição; o ponto diferenciador é o commercial-use threshold: empresas com receita anual acima de **US$ 10 milhões** precisam de licença comercial para continuar usando o modelo comercialmente. Por isso, mesmo sendo distribuível, eu evitaria torná-lo o default silencioso do Prumo: o installer deve mostrar claramente a licença/threshold e permitir opt-in, para não impor uma condição comercial inesperada ao downstream user.

# Benchmarks antes de ACCEPTED

Criar corpus real do Prumo com Português + Inglês + código.

## Embedding evals

- Recall@K / nDCG@K;
- code retrieval;
- Portuguese ↔ English cross-lingual retrieval;
- long-document retrieval;
- latency / docs per second;
- peak RAM;
- index size.

## Reranker evals

- nDCG delta sobre hybrid retrieval;
- latency por top-10/top-20/top-50;
- RAM cold/warm;
- ganho por token/context.

## Knowledge Worker evals

- document/section role classification accuracy;
- extraction precision/recall para Decision/Requirement/Constraint/Claim;
- hallucinated claim rate;
- schema-valid output rate;
- duplicate/supersession suggestion precision;
- summary faithfulness;
- Portuguese quality;
- latency / RAM / energy where practical.

## End-to-end

Comparar:

```
A deterministic + FTS
B + Granite embedding
C + embedding + reranker
D + embedding + tiny worker
E + standard worker
```

Aceitar cada camada somente quando o ganho mensurável justificar download, RAM e complexidade.

EmbeddingGemma permanece challenger importante para qualidade on-device; Qwen3-Embedding-0.6B é challenger para retrieval/code mais pesado; LFM2.5-350M/1.2B são challengers extremamente interessantes de eficiência, com distribuição permitida mas commercial-use threshold próprio.

## Challengers atuais de 2026

- **Qwen3.5-0.8B** — Apache-2.0, geração mais nova, 201 línguas, 262,144 tokens de contexto nativo e multimodal. Quantizações GGUF comunitárias Q4_K_M estão na faixa de ~0.58 GB. Deve entrar no benchmark **Lite** contra Qwen3-0.6B: custa pouco mais em armazenamento, mas pode eliminar a necessidade futura de um segundo modelo visual para screenshots, diagramas e documentos escaneados.
- **Gemma 4 E2B** — Apache-2.0 e explicitamente voltado a mobile/edge, reasoning, coding e agentic workflows. A distribuição LiteRT oficial reporta model size de ~2.58 GB, portanto fica acima do footprint desejado para o pack-base; considerar apenas em perfil Quality/Enhanced.
- **Granite 4.1 3B** — Apache-2.0, long-context instruct, suporta Português e possui bom alinhamento para instruction/tool use. É candidato de qualidade, não de footprint mínimo.

# Invariantes

- Local AI é optional e removable;
- Core Only continua completo;
- deterministic first;
- embeddings/reranking são derived state;
- generator produz **proposals**, não truth;
- model role é separado de model identity;
- modelos são substituíveis e customizáveis;
- lazy load/unload para reduzir idle RAM;
- nenhuma rede é necessária para operar após artifacts instalados;
- licença e supply-chain metadata são first-class;
- quality/performance são decididas por evals do corpus Prumo, não por leaderboard isolado.

# Installation profiles and resource-aware routing

A direção de instalação foi fechada em [29 — Local Intelligence Profiles, Resource Manager e Knowledge Model Router](ch29.md).

Os perfis oficiais são `No-LLM`, `Ultra-Light`, `Light`, `Balanced`, `Ultra` e `Custom`. Eles representam **capability/resource policies**, não listas rígidas de modelos. O mesmo Knowledge Runtime funciona em todos os perfis; `ResourceManager` e `KnowledgeModelRouter` escolhem o menor recurso suficiente, fazem lazy load/unload e podem escalar ao Model Gateway remoto quando a policy permitir. `Balanced` é o perfil recomendado para máquinas com 16 GB; valores finais de RAM/download serão sempre derivados de benchmarks/manifests da versão concreta dos artifacts.
