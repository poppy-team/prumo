# Princípio central

> **Prumo must not require direct model API access when an official authenticated agent runtime or interoperable agent protocol is available.**
> 

Quando houver um runtime oficial autenticado, ACP, SDK, JSON-RPC, JSONL/headless ou outra interface programática suportada, preferir essa integração sobre exigir uma segunda API key do usuário, desde que a abordagem seja oficialmente suportada e compatível com os termos do fornecedor.

# Dois tipos de conexão

```
Prumo Connectivity
├── Model Connections
│   └── Prumo controla o agent loop
│       ├── API key / BYOK
│       ├── OAuth oficial quando permitido
│       ├── OpenAI-compatible
│       ├── Anthropic-compatible
│       └── Custom Model Provider
│
└── Agent Connections
    └── runtime externo controla seu próprio agent loop
        ├── ACP
        ├── official SDK
        ├── JSON-RPC
        ├── structured JSONL / stream-json CLI
        ├── headless HTTP/OpenAPI server
        ├── custom Agent Provider
        └── PTY bridge somente como último recurso
```

# Separar três dimensões

| Dimensão | Pergunta |
| --- | --- |
| Authentication | Quem autentica o usuário e possui as credenciais? |
| Transport | Como o Prumo conversa com o runtime? |
| Runtime ownership | Quem executa o agent loop, tool loop e session lifecycle? |

**ACP não é autenticação.** ACP conecta client/editor ↔ agent. O agente pode autenticar o usuário usando OAuth, device flow, keyring, environment ou outro mecanismo próprio.

# Ordem de preferência para integrações

1. API/SDK/server oficial programático com superfície rica;
2. ACP oficial/compatível;
3. protocolo oficial JSON-RPC/JSONL/headless;
4. CLI oficial com output estruturado e sessão persistente;
5. API direta com API key/BYOK;
6. PTY/screen scraping somente quando absolutamente necessário e sempre isolado atrás de adapter.

# Credential ownership

Credenciais devem declarar explicitamente seu owner.

| Owner | Exemplo | Regra |
| --- | --- | --- |
| `prumo` | OpenRouter/custom API key | Prumo armazena via keyring/secret store; nunca plaintext em config |
| `vendor_cli` | Antigravity/Gemini CLI OAuth | CLI oficial é dono da sessão/tokens |
| `vendor_server` | Codex app-server + ChatGPT OAuth | server oficial é dono de OAuth/refresh |
| `environment` | `ANTHROPIC_API_KEY` | Prumo referencia o nome da variável, não copia segredo |
| `os_keyring` | provider customizado autorizado | Prumo pode persistir segredo via store seguro |
| `external_identity` | AWS/Google ADC | credencial continua no mecanismo externo |

Nunca ler/copiar silenciosamente tokens privados de CLIs de terceiros. Quando possível, o Prumo deve **invocar o runtime oficial já autenticado**, não assumir suas credenciais.

# ACP como protocolo first-class

ACP deve existir em duas direções distintas:

- **ACP Client:** Prumo consome coding agents externos;
- **ACP Agent Server:** Prumo expõe o próprio Agent Runtime a editores/clientes externos.

O ACP Registry pode ser usado para descoberta de agentes compatíveis, instalação metadata e auth methods. Registry entries são descoberta; não concedem confiança automática.

# MCP e A2A

```
ACP = Client/Editor ↔ Agent
MCP = Agent ↔ Tool/Context
A2A = Agent ↔ Agent remoto/independente
```

A2A permanece posterior, mas a boundary deve continuar separada para futura federação.

# Providers customizados pelo usuário

O Prumo deverá permitir **Custom Model Providers** e **Custom Agent Providers** sem exigir recompilação do Core.

## Custom Model Provider

Configuração declarativa para APIs compatíveis ou quase compatíveis:

```
name
base_url
protocol = openai | anthropic | custom-http
credential_source
headers
default_models
capabilities
streaming
structured_output
tool_calling
context_window/pricing overrides opcionais
health endpoint opcional
```

O usuário pode cadastrar gateways locais, provedores regionais, proxies corporativos, endpoints self-hosted ou serviços futuros.

## Custom Agent Provider

Manifesto para runtimes programáticos externos:

```
name
command / endpoint
transport = acp | jsonrpc | jsonl | http | websocket
args/env allowlist
auth method
capability hints
session/resume support
permission mapping
event mapping
health/discovery
```

Adapters arbitrários com código executável devem usar o plugin/extension trust model e não ganhar filesystem/network/secrets implicitamente.

# Provider Profiles e múltiplas contas

Um mesmo provider pode ter múltiplos perfis:

```
Codex — Personal ChatGPT
Codex — Work account
OpenRouter — Personal
OpenRouter — Project budget
Custom Ollama — Local workstation
Antigravity — Google account A
```

Routing deve referenciar `provider_profile_id`, nunca assumir uma única credencial global por vendor.

# Capability negotiation

A UI e o Router devem conhecer capabilities reais por conexão:

- streaming;
- tool calling;
- file edits;
- permissions;
- resume;
- subagents;
- reasoning summaries;
- structured output;
- image input;
- context limits;
- usage/cost reporting;
- local/remote execution;
- sandbox ownership.

Features indisponíveis devem degradar por capability, não por vendor hard-coded.

# Segurança e termos

- preferir fluxos oficiais;
- não extrair tokens privados de aplicativos/CLIs;
- não simular OAuth privado quando o fornecedor não o oferece para terceiros;
- revisar termos/licença antes de distribuir adapters de assinatura;
- segredos nunca entram em logs, checkpoints, artifacts ou telemetry;
- auth terminal/device flow pode ser apresentado dentro do Desktop/TUI, mas o runtime oficial continua dono das credenciais quando essa for a arquitetura escolhida;
- custom providers são untrusted-by-default e sujeitos a egress/secret policies.
