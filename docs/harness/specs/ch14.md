# Objetivo

Escolher a fundação da TUI por capacidade de sustentar **editor + terminal + agentes + grandes listas + layouts complexos** com uma linguagem visual inspirada no Zed, não apenas por quantidade de widgets ou facilidade para dashboards.

# Direção visual comum

A TUI deve traduzir a linguagem do Zed para limitações reais de terminal: panes limpos, tabs compactas, divisores discretos, status bar fina, activity/sidebar lateral, command palette, hierarquia por contraste e espaçamento, foco muito claro sem molduras pesadas e densidade informacional alta. O objetivo é parecer um **editor moderno de verdade no terminal**, não uma coleção de caixas ASCII.

Em terminais com true color e Unicode, usar recursos modernos com degradação graciosa para 256 cores/ambientes SSH mais simples.

| Stack | Linguagem | Forças | Risco / custo | Fit inicial |
| --- | --- | --- | --- | --- |
| R3BL TUI | Rust | async-first, immediate/reactive, diff painting, flex-like layout, editor/Markdown e primitives de PTY/multiplexação; boa base para concorrência e SSH | avaliar maturidade da API, integração com editor-grade próprio e liberdade visual para um cockpit muito custom | **muito alto** |
| Revue | Rust | retained/reactive, CSS styling, signals/computed/effects, Flex+Grid, 100+ widgets, hot reload, profiler/devtools e single binary | extremamente novo e ecossistema pequeno; precisa provar performance, estabilidade e editor/PTY complexos | **alto potencial, risco alto** |
| Ratatui Kit | Rust | Ratatui por baixo com components, hooks, props, routing, theming, async/Tokio, input layers, virtual list e escape hatch para widgets Ratatui nativos | framework jovem; React-like reconciliation/hook model precisa ser medido sob cargas editor-grade; algumas integrações do ecossistema seguem migração Ratatui 0.30 | **muito alto para arquitetura modular** |
| Bubble Tea v2 | Go | Elm-style, ecossistema Charm, renderer v2, Bubbles/Lip Gloss v2 e integração direta com o Harness Go | editor, PTY e docking muito avançados ainda exigem componentes próprios; medir comportamento sob redraw intenso e Unicode complexo | **muito alto no caminho Go** |
| tview | Go | muito direto e pragmático; forms, TextView, textarea, tables, trees, lists, images, Grid/Flex/Pages; pequeno custo de adoção | arquitetura e rendering menos orientados a uma mini-IDE reativa moderna; provavelmente exigirá uma camada própria maior para chegar ao visual/ergonomia do Zed | **médio/alto como baseline de simplicidade** |

# Duas famílias de decisão

## Rust — editor/TUI especializado

`R3BL | Revue | Ratatui Kit` com editor core, LSP, Git, PTY, fuzzy search e Prumo Agent Protocol.

A rota Rust é atraente porque o cliente pode compartilhar bibliotecas e conceitos com Oride/Helix/Lapce e porque existe um ecossistema TUI/editor mais rico para componentes de baixo nível.

## Go — proximidade máxima com o Harness

`Bubble Tea v2 | tview` com componentes próprios para editor, diff, PTY, docking e agent surfaces.

A rota Go reduz fronteiras de linguagem/processo e pode facilitar um binário único no modo local, mas isso só vale se não sacrificarmos a qualidade de edição/renderização.

# Estratégia de avaliação — Zed-like TUI Spike

Todos os candidatos finalistas devem implementar a mesma composição:

```
┌ activity ┬ project/files ┬ editor tabs + splits ┬ agent/runs ┐
│          │               │                      │            │
│          │               │ editor / diff        │ thread     │
│          │               │                      │ evidence   │
├──────────┴───────────────┴──────────────────────┴────────────┤
│ terminal | problems | tests | output | gates                  │
└───────────────────────────────────────────────────────────────┘
```

E validar:

- 100k file picker;
- editor 100k+ linhas;
- 4+ splits;
- PTY com output intenso;
- agent event stream;
- diff view;
- command palette;
- mouse resize;
- keyboard-only workflow;
- Unicode/CJK/emoji width;
- true color + 256-color fallback;
- SSH high-latency scenario;
- terminal resize contínuo;
- CPU idle e redraw behavior.

# Critérios adicionais para visual Zed-like

- capacidade de desenhar separators de 1 célula sem excesso de borders;
- tabs compactas com estados active/dirty/attention;
- sidebars retráteis e overlays;
- command palette e quick pick virtualizados;
- suporte a spans com foreground/background/attributes finos;
- mouse hit-testing previsível;
- component focus graph explícito;
- tema tokenizado compartilhando semântica com o Desktop, mas não widgets.

# Hipótese inicial

**R3BL e Ratatui Kit** são os primeiros Rust spikes que eu colocaria lado a lado: R3BL pelo runtime/PTY/async e Ratatui Kit pela arquitetura componentizada sem perder o escape hatch para Ratatui. **Revue** é muito interessante para prototipagem visual rápida, mas ainda deve ser tratada como candidata de maior risco por juventude.

No Go, **Bubble Tea v2** é o primeiro spike. **tview** funciona como uma baseline de simplicidade e produtividade: se uma arquitetura custom sobre tview atingir nossos budgets e visual, ela pode surpreender; porém não deve ganhar apenas por ser fácil.
