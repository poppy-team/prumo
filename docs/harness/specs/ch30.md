<aside>
⚙️

**Status: ACCEPTED.** A inteligência local do Prumo será executada por **workers supervisionados fora do Core Go**, com contratos estáveis e isolamento de processo. O Core não incorpora `llama.cpp`, ONNX Runtime ou OpenVINO via business-logic/CGO direto. A implementação inicial usa `llama.cpp` para generation/rerank/GGUF e um worker ONNX Runtime dedicado para embeddings. OpenVINO entra como acceleration adapter opcional quando hardware/benchmark justificar.

</aside>

# Objetivo

Fechar a arquitetura de execução local dos perfis `No-LLM`, `Ultra-Light`, `Light`, `Balanced`, `Ultra` e `Custom` sem acoplar o Harness a uma família de modelo, formato ou runtime específico.

# Decisão principal: process isolation

```
Prumo Core / Harness (Go)
        │
        ├── KnowledgeModelRouter
        ├── ResourceManager
        ├── WorkerSupervisor
        │
        ├── LocalGenerationWorker
        │      └── llama.cpp / GGUF
        │
        ├── LocalEmbeddingWorker
        │      └── ONNX Runtime / ONNX
        │
        └── optional acceleration workers
               └── OpenVINO / future runtimes
```

O Core comunica com workers por protocol local versionado. Nenhum domínio conhece símbolos C/C++, execution providers ou nomes concretos de modelos.

# Por que não CGO/native binding dentro do Core

- crash do runtime/modelo não derruba o Harness;
- update de `llama.cpp`/ORT pode ser independente do binário principal;
- reduz superfície de build e ABI dentro do Go Core;
- diferentes backends podem coexistir por plataforma;
- facilita package rollback;
- resource limits/kill/restart ficam claros;
- workers podem ser sandboxed/restricted futuramente;
- testes do Core usam fake workers sem carregar modelos;
- torna `No-LLM` verdadeiramente independente de native inference dependencies.

Bindings diretos podem ser usados **dentro do executável worker** se isso for tecnicamente superior; a boundary obrigatória é processo/protocol, não HTTP necessariamente.

# Protocol dos workers

Preferência inicial:

```
Harness
  ↕ local IPC / loopback
Worker
```

Transport candidates:

- stdio framed JSON/CBOR para worker simples e single-owner;
- Unix domain socket / Windows named pipe para daemon persistente;
- loopback HTTP somente quando reutilizar uma API upstream reduz complexidade de forma material.

O contrato canônico é `LocalInferenceProtocol`; HTTP/OpenAI compatibility é implementation detail.

# Runtime primário para generators: llama.cpp

`llama.cpp` é o runtime principal para tiny/standard Knowledge Workers porque:

- GGUF é um formato compacto e amplamente disponível para modelos pequenos;
- CPU + múltiplos backends GPU;
- generation quantizada;
- constrained output via grammar/JSON Schema;
- embeddings e reranking também são suportados, úteis como fallback/experimentação;
- `llama-server` atual suporta router mode, load/unload dinâmico, model limit e eviction LRU;
- oferece health/metrics e API estruturada madura o suficiente para um adapter.

## Como será usado

Não depender da Web UI do llama-server. O Prumo controla lifecycle, models, resources e policy.

Duas estratégias de implementação são permitidas atrás do mesmo adapter:

1. **Supervised `llama-server` subprocess** — caminho inicial recomendado, menor integration risk.
2. **Dedicated worker linked to libllama** — somente se benchmarks/controle mostrarem ganho claro; continua fora do Core.

# Runtime primário para embeddings: ONNX Runtime

O default de embedding usa ONNX Runtime Core, não ONNX Runtime GenAI. Motivos:

- embeddings são inference graph tradicional, não necessitam generation loop;
- ORT C API de inference/session é estável e suportada em Windows/Linux/macOS;
- Execution Providers permitem CPU e aceleração por CUDA/OpenVINO/CoreML/DirectML/others conforme package/platform;
- Granite Embedding possui artifacts ONNX/quantizados adequados;
- mantém o encoder pequeno independente do generator GGUF.

`onnxruntime-genai` permanece fora do caminho principal enquanto sua Generate API continuar preview; não há necessidade arquitetural de adotá-la para nosso Knowledge Worker.

# Worker ONNX

O worker de embedding deve possuir interface mínima:

```
EmbeddingWorker
├── Load
├── Describe
├── EmbedBatch
├── Warmup
├── Metrics
├── Unload
└── Shutdown
```

Tokenização/preprocessing faz parte do model package/worker adapter para preservar reproducibilidade entre plataformas.

# OpenVINO

OpenVINO não é terceiro runtime obrigatório. Ele entra inicialmente de duas formas possíveis:

- como ONNX Runtime Execution Provider em hardware Intel quando suportado e benchmarkado;
- como worker OpenVINO/OVMS separado no perfil Enhanced/Ultra caso ofereça ganho material.

Nunca selecionar OpenVINO apenas por detectar CPU Intel; escolha depende de measured model/backend profile.

# Backend selection

`KnowledgeModelDescriptor` declara artifacts e backends válidos. `ResourceManager + KnowledgeModelRouter` selecionam:

```
model capability
+ installed artifact
+ platform
+ accelerator availability
+ measured performance profile
+ current resource pressure
→ backend
```

Não existe backend universal hard-coded.

# Quantization policy

## Generators / GGUF

Default candidate: `Q4_K_M` quando disponibilizado e validado.

Princípios:

- Q4_K_M é baseline de distribuição, não contrato do profile;
- Q5/Q6/Q8 podem ser oferecidos em `Custom`/advanced quando benchmark mostrar ganho de quality suficiente;
- nunca quantizar automaticamente no computador do usuário durante instalação normal;
- packages apontam para artifact pré-validado e digest conhecido;
- profile escolhe capability tier, Package Resolver escolhe quantização/artifact compatível com budget.

## Embeddings

Não assumir a mesma quantização dos generators. Preferir artifact ONNX quantizado oficial/validado quando retrieval quality se mantiver dentro do threshold do benchmark.

Embedding benchmark compara também impacto de quantização em Recall@K/nDCG, não apenas RAM/latency.

# Package Runtime

```
Catalog
→ Resolve profile/capabilities
→ Resolve artifact variant
→ show license/download/resources
→ Download to staging
→ SHA-256 verify
→ validate package manifest
→ atomic promote into cache
→ optional warmup/health probe
→ mark Installed
```

Updates never overwrite the currently working artifact in place. New version is installed side-by-side and promoted only after validation. Rollback keeps previous known-good version until cleanup policy permits deletion.

# Runtime packages separados de model packages


Uma atualização de runtime não força redownload de pesos.

# WorkerSupervisor

Responsabilidades:

- spawn;
- handshake/protocol version;
- health checks;
- cancellation;
- stdout/stderr capture com redaction;
- crash detection;
- bounded restart/backoff;
- kill on memory/resource violation;
- lifecycle telemetry;
- graceful shutdown;
- orphan cleanup após crash do Harness.

Não faz model routing; routing pertence ao `KnowledgeModelRouter`.

# ResourceManager — decisions

Separar **admission**, **residency** e **eviction**.

## Admission

Antes de load:

```
measured_peak_ram
+ expected_context_overhead
+ Prumo safety reserve
<= effective available budget
```

Se falhar: tentar artifact/model menor → remote if allowed → explicit unavailable.

## Residency

Default `Normal`:

- embedding pode permanecer warm se RAM estiver saudável;
- tiny generator: idle TTL inicial candidato 120 s;
- standard generator: idle TTL inicial candidato 60 s;
- reranker: unload rapidamente, TTL candidato 30 s;
- no máximo um standard/large generator residente por default;
- `Ultra` aumenta disponibilidade de models, não simultaneidade automática.

Valores são **provisional defaults** e podem ser ajustados por benchmark sem mudar a arquitetura.

## Eviction

Ordem preferencial:

```
expired idle model
→ reranker
→ standard generator
→ tiny generator
→ advanced embedding
→ default embedding last
```

A ordem pode ser ajustada por current tasks/pins.

# Safety reserve

ResourceManager não usa `available RAM == can allocate`. Manter reserva para OS, editor, compiler e browser.

Policy inicial:

```
reserve = max(1.5 GiB, 12.5% total RAM)
```

Em máquinas <= 8 GiB, policy Conservative pode aumentar proporcionalmente a proteção e preferir remote/tiny.

O valor final será validado em hardware benchmarks; é uma policy versionável, não invariant.

# Memory pressure states

```
healthy
pressure
critical
```

`compact` continua reservado ao Context Compiler, não é estado de memória do sistema.

Transições usam métricas do SO + thresholds com hysteresis para evitar load/unload oscillation.

## pressure

- cancelar preload;
- impedir novos loads grandes;
- reduzir TTL;
- evict idle workers;
- preferir smaller/local or remote conforme privacy policy.

## critical

- unload non-pinned models imediatamente;
- recusar new local generation;
- preservar Core responsiveness;
- fallback remoto somente quando permitido.

# GPU/VRAM policy

GPU é acelerador oportunista, não requisito.

- detectar accelerator/backend compatibility;
- reservar VRAM para aplicação do usuário;
- partial offload permitido quando runtime suportar;
- nunca ocupar toda VRAM conhecida;
- se VRAM pressure/graphics workload for alto, cair para CPU/smaller model;
- Knowledge Runtime não deve competir agressivamente com aplicações 3D/editor por default.

`Normal` prioriza estabilidade sobre máximo throughput.

# Battery / thermal policy

Em notebooks:

- power-saver pode desabilitar preload e advanced reranking;
- background indexing usa concurrency reduzida;
- long local generation pode preferir remote quando policy permitir;
- thermal signals só influenciam policy quando disponíveis de forma confiável por plataforma.

# Local → remote escalation

Arquitetura aceita:

```
Deterministic
→ Local minimal sufficient model
→ next local tier if justified
→ remote route if allowed
```

Remote escalation é permitida automaticamente apenas quando:

- task privacy permite;
- remote provider está habilitado;
- payload passou por Context Compiler/redaction;
- nenhum side effect externo é introduzido pelo Knowledge Task.

Para knowledge/document processing, payload remoto é sempre **minimal Context Pack**, nunca corpus completo.

# Privacy modes

```
local_only
local_preferred
balanced
remote_preferred
remote_allowed
```

`local_only` nunca escala para Model Gateway e deve retornar incapacidade explícita caso recursos locais sejam insuficientes.

Project/privacy class pode forçar `local_only` independentemente da preference global.

# Structured generation

Knowledge Workers devem receber schema explícito sempre que houver suporte.

No llama.cpp, adapter prefere JSON Schema/grammar-constrained output para `KnowledgeDelta`, classification/extraction e proposals.

Pipeline:

```
infer constrained output
→ parse
→ schema validate
→ semantic validate
→ provenance attach
→ candidate record
```

Falha nunca vira canonical knowledge silenciosamente.

# Concurrency

Default:

- deterministic/FTS/index operations podem ser concorrentes;
- embedding usa batch bounded;
- um generator job por worker/model por default;
- queue com cancellation/deadlines;
- background knowledge tasks têm prioridade menor que interactive Plan/Run tasks;
- ResourceManager é authority para admission, não cada worker isoladamente.

# Scheduling classes

```
interactive
foreground
background
maintenance
```

Ordem de prioridade: `interactive > foreground > background > maintenance`, com aging para impedir starvation.

Embedding indexing em massa é background; response necessária ao Plan Mode é interactive.

# Failure recovery

Worker crash:

```
mark unhealthy
→ release reservations
→ bounded restart
→ requeue idempotent task when safe
→ fallback backend/model if retry budget exhausted
```

Generation/extraction de knowledge é idempotent enquanto não houver canonical commit; commit ocorre só depois de validation.

# Runtime health / circuit breaker

Workers/backends recebem health state próprio:

```
healthy
suspect
cooldown
unavailable
```

Falhas repetidas abrem circuit breaker local, evitando spawn/retry loops. Este health não substitui ProviderHealth remoto.

# Observability

Registrar sem conteúdo sensível por default:

- selected model/package/backend;
- cold/warm load latency;
- inference latency;
- tokens/items processed;
- peak RAM/VRAM;
- eviction reason;
- crashes/restarts;
- schema-valid/invalid;
- escalation reason;
- accepted/rejected candidate when known.

Prompts/document text não entram em telemetry global por default.

# Security

- worker executa com menor privilégio prático;
- model packages são dados, não executáveis;
- runtime packages possuem provenance + digest/signature quando disponível;
- downloads passam por staging e verification;
- workers não recebem filesystem/network amplo por default;
- only explicitly mounted model/cache/temp paths;
- loopback server upstream deve bindar [localhost](http://localhost) e não ser exposto externamente;
- APIs internas do worker usam random capability token/pipe ownership quando aplicável;
- nenhum `llama-server` Web UI é exposto como superfície Prumo.

# Open questions removidas por esta decisão

Agora estão **decididos arquiteturalmente**:

- generator runtime primary: llama.cpp/GGUF;
- embedding runtime primary: ONNX Runtime Core/ONNX;
- OpenVINO: optional acceleration adapter;
- Core Go sem native inference binding obrigatório;
- inference process isolation;
- model/runtime packages separados;
- lazy residency/ResourceManager admission;
- local→remote escalation boundary;
- versioned package/cache architecture.

# Ainda benchmark-driven

Não congelar sem medição:

- tiny/standard model winner;
- Granite vs advanced embedding nas tarefas difíceis;
- reranker default/Ultra usefulness;
- Q4_K_M vs Q5/Q8 por worker;
- exact TTLs;
- exact safety reserve thresholds;
- CPU/GPU backend preference por hardware;
- measured profile RAM recommendations.
