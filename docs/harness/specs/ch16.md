# Dimensões

| Área | Métrica | Por quê |
| --- | --- | --- |
| Startup | cold/warm start | ferramenta deve abrir instantaneamente |
| Memory | idle, active, per-workspace, per-terminal | permite hardware com pouca RAM |
| CPU | idle %, background watchers | evita bateria/thermal waste |
| Input | key-to-render p50/p95/p99 | sensação de editor nativo |
| Render | frame time / dropped frames | scroll e stream fluido |
| Terminal | bytes/s + CPU | build logs e TUIs nested |
| Files | open/search/render 1MB/10MB/100MB+ | large-file resilience |
| Repo | 10k/100k/1M entries | monorepo behavior |
| Agent | stream events/s | UI não deve travar com tools/tokens |
| Binary | compressed/uncompressed footprint | distribution |

# Hardware test tiers

Definir pelo menos três classes:

- **Legacy:** dual/quad core antigo, 8 GB RAM, iGPU antiga ou software renderer;
- **Baseline:** notebook moderno de entrada/médio;
- **Developer:** workstation atual.

A release deve continuar funcional no Legacy, mesmo que alguns efeitos visuais sejam reduzidos.

# Degradation strategy

- software renderer fallback onde aplicável;
- animations optional/reduced;
- lazy syntax/LSP startup;
- virtualization everywhere large;
- bounded scrollback;
- tree scanning incremental;
- no background polling agressivo;
- model/network work fora da UI thread;
- backpressure em streams.

# Budgets iniciais

Não congelar números antes dos spikes. O Oride oferece uma referência agressiva de filosofia (`<=12MB` uncompressed, startup `<10ms`, input `<5ms`), mas Desktop e Agent Runtime possuem escopo maior. Definir budgets distintos por componente depois de medir protótipos.

# Regression gate

Guardar benchmarks e hardware fingerprint. PRs que mudam renderer/editor/runtime devem poder comparar baseline e candidato.
