<aside>
🧭

**Status: ACCEPTED.** O Prumo possui um `DocumentationPlanner` determinístico que decide **quais unidades/páginas deveriam existir**, para quais audiências, em quais superfícies e com quais dependências. LLMs podem melhorar títulos, summaries e prosa, mas não são responsáveis por inventar a arquitetura da documentação a partir de um prompt vazio.

</aside>

# Objetivo

Evitar tanto documentação insuficiente quanto a explosão de centenas de páginas artificiais. O Planner transforma capabilities, personas, comandos, schemas, APIs, workflows, erros, Requirements, Decisions e histórico do projeto em um `DocumentationPlan` reproduzível.

# Pipeline

```
Project/Knowledge Snapshot
        ↓
Project Classification
        ↓
Audience + Capability Inventory
        ↓
Documentation Profile Composition
        ↓
Candidate DocumentationUnits
        ↓
Merge/Split + Dependency Rules
        ↓
Coverage Analysis
        ↓
Navigation/Page Graph
        ↓
GenerationPlan
```

# Inputs determinísticos

Prioridade de sinais:

```
Project metadata/profile
Product capabilities
Command Registry
Config schemas
API/Plugin/Provider contracts
UI workspaces/features
Error Registry
File-format contracts
Requirements
Accepted Decisions
Workflows/Recipes
Tests/examples
Release/migration metadata
Troubleshooting knowledge
```

LLM extraction pode produzir candidates quando informação está apenas em prosa, mas candidates precisam ser normalizados no Knowledge Runtime antes de governarem o plan.

# Project Classification

Classificação é multi-label:

```
library
cli
desktop-app
service/api
framework/sdk
developer-tool
language/compiler
game/tooling
plugin-platform
```

Um projeto pode ser `developer-tool + framework/sdk + cli`. O profile final é composição, não escolha exclusiva.

# Audience capability matrix

Planner materializa matriz:

```
Audience × Capability × Need
```

Exemplo:

| Audience | Capability | Necessidade | Doc intent |
| --- | --- | --- | --- |
| new-user | install/run | primeiro sucesso | Quickstart |
| end-user | provider auth | realizar tarefa | How-to |
| developer | CLI commands | consultar fatos | Reference |
| plugin-author | Plugin API | consultar contrato | Reference + Tutorial |
| maintainer | Run/Session model | compreender design | Explanation/Architecture |

# Page Graph vs filesystem tree

O Planner cria primeiro um **Page Graph** sem paths físicos.

Edges candidatos:

```
parent_of
prerequisite_for
next_in_tutorial
related_to
explains
references
troubleshoots
migrates_from
supersedes
```

Depois um path allocator/nav renderer converte o graph para website/sidebar/files.

# Stable DocumentationUnit IDs

Exemplos conceituais:

```
DOC-getting-started
DOC-howto-provider-auth
DOC-ref-cli-provider-add
DOC-concept-model-vs-agent-provider
```

IDs não são derivados diretamente do slug para permitir rename e localização.

# Candidate generation rules

Exemplos:

```
Project has executable/install method
→ Quickstart candidate

CommandRegistry non-empty
→ CLI Reference root + grouped command units

Config schemas non-empty
→ Configuration Reference

Plugin contract exposed
→ Plugin Author docs

User-facing workspace exists
→ Manual section candidate

Accepted breaking change
→ Migration Guide candidate

Repeated validated failure pattern
→ Troubleshooting candidate

Accepted architectural Decisions
→ Architecture/Decision Book coverage
```

# Merge/Split heuristics

Evitar uma página por entidade pequena.

## Merge quando

- mesmo audience + intent;
- conteúdo é curto;
- entidades formam grupo natural;
- navegação ficaria fragmentada;
- atualização tende a ocorrer em conjunto.

## Split quando

- página ultrapassa budget de tamanho/leitura;
- diferentes intents Diátaxis estão misturados;
- diferentes audiences têm pré-requisitos incompatíveis;
- uma seção tem lifecycle/versioning próprio;
- reference possui muitas entidades consultadas independentemente.

Thresholds concretos são benchmark/UX tuning, não invariantes.

# Information architecture rules

Ordem default por necessidade humana:

```
Home
→ Getting Started
→ common Tutorials/How-tos
→ Concepts
→ Reference
→ Troubleshooting
→ Releases/Migration
→ Developer/Maintainer
```

Reference pode espelhar arquitetura do produto; Tutorials/How-tos seguem objetivos do usuário.

# No page explosion invariant

O Planner calcula `DocumentationDensity` e `NavigationComplexity` derivados. Antes de criar unidade nova tenta:

1. localizar unidade de mesmo intent/audience/subject family;
2. avaliar merge;
3. criar heading/section estável;
4. só então criar nova página.

# Coverage model para documentação humana

Coverage é semântico, não quantidade de páginas.

```
HumanDocCoverageRequirement
├── subject_ref/capability
├── audience
├── required intent
├── surface optional
├── freshness policy
├── ownership policy
└── severity
```

Exemplos:

- comando público precisa Reference;
- fluxo principal precisa Getting Started ou How-to;
- breaking change precisa Migration/Release coverage;
- plugin API pública precisa Reference;
- feature GUI pública precisa Manual/How-to coverage conforme profile.

# Coverage result

```
satisfied
partial
missing
stale
invalid
not_applicable
```

Integra com Readiness Engine: projeto pode estar `release-ready` em código e ainda falhar `documentation-release-ready` por migration guide ou reference faltante.

# Generation strategy selection

Para cada unit/section:

```
Can deterministic renderer produce authoritative content?
├── yes → GENERATED
└── no
    ↓
Is there sufficient canonical knowledge for grounded prose?
├── yes → ASSISTED LLM proposal
└── no → GAP / requires knowledge, not hallucinated documentation
```

Nunca pedir para LLM preencher uma página apenas porque o template possui um heading vazio.

# Content brief antes da prosa

LLM recebe `DocumentationBrief`, não o corpus inteiro:

```
DocumentationBrief
├── doc_unit_id
├── intent
├── audience
├── goal/question
├── prerequisites
├── authoritative refs[]
├── allowed claims[]
├── required examples[]
├── forbidden/private refs[]
├── style constraints
├── target length budget
└── related docs[]
```

Isso reduz tokens e alucinação.

# Diátaxis intent validator

Regras simples detectam mistura indevida:

- tutorial com grandes blocos de reference → warning;
- how-to sem objetivo/result → warning;
- reference com marketing/opinião → warning;
- explanation com passos imperativos extensos → warning.

LLM pode ajudar na classificação, mas validator reason codes continuam auditáveis.

# Example planning

Examples são assets first-class:

```
ExampleRecord
├── id
├── purpose
├── language/runtime
├── source files
├── expected output
├── executable/testable
├── required version
└── docs consumers[]
```

Preferir examples compartilhados/testados a snippets copiados manualmente em várias páginas.

# Screenshot planning

Planner pode criar `ScreenshotRequirement`, não imagem fictícia:

```
screen/view id
state/setup fixture
viewport/theme/locale
annotation need
consumer docs[]
```

Captura real pertence ao Publishing/Quality Runtime.

# Localization planning

Source locale é authoritative para prosa curated/assisted. Cada translation mantém:

```
source_doc_id
source_digest
locale
translation_digest
translation_status
translated_from_revision
review status
```

Quando source digest muda, translation vira `needs_update`, não é silenciosamente considerada current.

# Version planning

Cada unit declara versão:

```
current-only
stable
version-range
release-specific
historical
```

Reference e migration podem ser version-scoped; conceitos duráveis podem ser version-agnostic com validity conditions.

# Public/private planning

Visibility é eligibility gate antes do renderer.

Valores candidatos:

```
public
project-private
maintainer-only
internal-sensitive
```

Public documentation nunca recebe record proibido e depois tenta "redigir" no fim; filtering acontece antes da geração.

# Navigation determinism

Sidebar/breadcrumb/previous-next são materialized views do Page Graph. Ordem definida por:

1. explicit curated order;
2. tutorial sequence/prerequisite DAG;
3. profile section priority;
4. stable ID fallback.

Nunca usar ordem de filesystem como semântica implícita.

# Impact analysis

Mudança em KnowledgeRecord/contract:

```
KnowledgeChanged
→ Documentation dependency graph
→ affected DocumentationUnits
→ content/generation policy
→ regenerate deterministic sections
→ propose assisted diffs
→ mark translations/screenshots stale if needed
```

# Overrides

Usuário pode:

- pinar/remover unidade;
- mudar título/path/nav;
- promover ownership GENERATED→ASSISTED/CURATED;
- alterar audience/visibility;
- declarar aliases/redirects;
- criar docs custom não derivadas.

Override é versionado e nunca perdido na replanificação.

# Invariantes fechados

- planner é determinístico a partir de snapshot + overrides;
- profile compõe capabilities, não dita árvore rígida;
- Page Graph precede paths/sidebar;
- documentation gaps não são preenchidos por hallucination;
- navigation é materialized view;
- coverage é audience+intent+subject-aware;
- visibility filtra inputs antes da geração;
- translations/examples/screenshots têm lifecycle próprio;
- assisted prose recebe brief mínimo e authoritative refs.
