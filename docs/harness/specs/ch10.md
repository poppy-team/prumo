# Direção visual comum

O desktop deve seguir uma linguagem visual **Zed-like**: superfície escura e discreta, densidade alta sem poluição, bordas e divisores sutis, hierarquia construída mais por contraste de planos do que por caixas pesadas, tabs compactas, command palette central, sidebars/panels retráteis, status bar fina, typography técnica limpa, ícones lineares pequenos, estados de hover/focus pouco ruidosos e layout fortemente orientado a panes/splits.

A referência é de **composição e ergonomia**, não cópia literal da identidade do Zed. O Prumo Code deve possuir design tokens próprios e preservar personalidade própria.

# Critérios

- memória idle e active;
- startup frio/quente;
- input-to-render p50/p95;
- CPU idle;
- render de texto denso;
- virtualized lists e trees;
- editor viewport;
- terminal throughput;
- software-render fallback;
- accessibility;
- IME/Unicode/CJK;
- clipboard/drag-drop;
- multi-window;
- Linux Wayland/X11, Windows e macOS;
- packaging e binary footprint;
- maturidade/API churn;
- capacidade de custom rendering e custom widgets;
- facilidade para reproduzir uma UI Zed-like sem lutar contra estilos do toolkit;
- facilidade de AI-assisted development.

| --- | --- | --- | --- | --- |
| GPUI | Rust | é a própria fundação de UI GPU-accelerated do Zed; prova editor-scale, virtualização, texto e panes complexos | pre-1.0 e API churn; suporte Windows está evoluindo e a documentação ainda apresenta inconsistências sobre o estado cross-platform | **muito alto — referência primária** |
| Floem | Rust | native, fine-grained reactivity, origem no ecossistema Lapce; Windows/macOS/Linux; GPU + fallback CPU; virtual lists | maturidade e profundidade do ecossistema comparadas ao GPUI/Iced | **muito alto** |
| Iced | Rust | cross-platform forte; arquitetura modular; wgpu + tiny-skia software renderer; async e custom widgets | quanto trabalho custom será necessário para um editor/cockpit tão denso quanto Zed | **alto / baseline robusto** |
| libcosmic | Rust | camada de plataforma rica sobre Iced; widgets, desktop integrations, software rendering por padrão e WGPU opcional | foi desenhado em torno da linguagem visual e integrações COSMIC; medir quanto precisamos substituir para uma identidade Zed-like | **médio/alto** |
| Go-Gui | Go | native GPU, sem browser/JS/DOM; immediate-style com stable identity; 50+ widgets, virtualization, tree/table, IME/a11y e ecossistema com go-edit/go-term | projeto muito novo e ecossistema menor; validar estabilidade, performance e qualidade do editor/terminal | **alto e especialmente interessante para single-stack Go** |

# Leitura inicial após pesquisa

## Rust

**GPUI** é o candidato com menor distância conceitual e visual até o objetivo porque é literalmente o framework do Zed. **Floem** pode ser o melhor desafiante se quisermos uma biblioteca mais declarativa e explicitamente cross-platform. **Iced** é o baseline de estabilidade/ecossistema e também nos dá fallback por software. **libcosmic** entra como derivação prática do Iced com uma biblioteca de componentes desktop maior, mas precisará provar que sua identidade COSMIC não cria atrito para o design Prumo.

## Go

A pesquisa fortaleceu bastante as duas alternativas Go. **Go-Gui** já expõe virtualização, editor e terminal como projetos irmãos e assume explicitamente aplicações desktop sem browser. **GoGPU/UI** possui uma arquitetura ainda mais próxima de um toolkit completo para IDE, com SplitView, docking, TreeView, software backend e pipeline damage-aware. Nenhum dos dois deve ser tratado como maduro apenas por sua lista de features: ambos precisam de spikes agressivos.

# Arquitetura para evitar lock-in

Definir `DesktopClient` sobre o Agent Protocol; nunca criar interfaces de GUI no Prumo Core. O modelo de panes, commands, editor state, terminal sessions, runs e approvals deve ser serializável e independente da toolkit.

# Spike obrigatório — Zed-like Cockpit

Construir essencialmente a mesma tela em cada finalista:

```
custom titlebar + compact tabs
left activity/sidebar + 10k files
center editor com 100k linhas
right agent/run panel
bottom terminal/problems/output
arbitrary splits
command palette
virtualized run/thread list
diff viewer
stream de agent em alta frequência
mouse resize + keyboard-only navigation
```

# Benchmark obrigatório

Medir em pelo menos duas classes de hardware:

1. máquina moderna de desenvolvimento;
2. hardware modesto/antigo representativo do objetivo do produto.

Registrar startup, RSS, CPU idle, frame/input latency, scroll, resize, terminal flood, editor large-file, 10k/100k list behavior e comportamento sem GPU adequada.
