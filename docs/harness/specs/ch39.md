<aside>
📖

**Status: ACCEPTED.** O Prumo mantém uma trilha narrativa derivada da história real do projeto sem usar transcript bruto como fonte canônica. `Engineering Chronicle`, `CHANGELOG`, `Release Notes` e `Public Devlog` são projeções distintas de Planning/Run/Decision/Research/Evidence/Release records, com políticas explícitas de privacidade e curadoria.

</aside>

# Objetivo

Preservar não apenas o estado atual do projeto, mas **como e por que ele evoluiu**, de forma útil para criadores, mantenedores, comunidade e futura geração de conteúdo.

# Quatro produtos diferentes

```
Engineering Chronicle
→ diário técnico interno, rico em decisões/experimentos/lições

CHANGELOG
→ mudanças relevantes por versão, factual e compacto

Release Notes
→ narrativa da versão para usuários

Public Devlog
→ história selecionada do desenvolvimento para comunidade/blog
```

Eles não devem ser confundidos nem gerados pelo mesmo template textual.

# Fonte

```
Planning Journal
Decision Ledger
Research Ledger
Runs
Changes/Patches
Evidence
Benchmarks
Failures/Incidents
Milestones
Releases
Knowledge Harvest
```

Transcript completo não é necessário; compact events e semantic records bastam.

# ChronicleEvent

Entidade/projection candidata:

```
ChronicleEvent
├── id
├── semantic time/order
├── event_type
├── subject refs[]
├── compact factual summary
├── decisions/research/evidence refs[]
├── artifacts[]
├── significance
├── privacy/visibility
├── tags
└── source revision
```

Tipos:

```
milestone
decision
research
experiment
implementation
refactor
failure
incident
benchmark
release
lesson
rejection
migration
```

# Engineering Chronicle

Default privado/project-local.

Estrutura por período/milestone, não por mensagem:

```
Date / Milestone
What changed
Why
Decisions
Research/experiments
Problems encountered
Evidence/results
Lessons
Open threads
Related commits/runs/artifacts
```

A LLM pode sintetizar prosa a partir de ChronicleEvents selecionados; o factual skeleton é determinístico.

# Frequency

Não gerar necessariamente um artigo por dia. Compiler agrupa por:

- milestone;
- release;
- sessão de desenvolvimento significativa;
- week/sprint opcional;
- explicit user marker.

Sem eventos significativos, não cria entrada vazia.

# Private Chronicle vs Public Devlog

Public Devlog é projection allowlisted:

```
Private Chronicle
↓ visibility + secrets + sensitivity filter
Public-worthy candidate events
↓ narrative synthesis
Curated/approved Devlog Post
```

Nunca resumir primeiro e tentar descobrir depois se algo privado vazou.

# Public Devlog content

Bom candidato:

- milestone visual/funcional;
- decisão arquitetural interessante já publicável;
- benchmark público;
- lição geral;
- mudança de direção explicável;
- release retrospective;
- screenshot/diagram approved.

Evitar automaticamente:

- secrets;
- vulnerabilities não publicadas;
- dados pessoais;
- fornecedor/account details privados;
- incidentes internos sensíveis;
- research copyrighted copied verbatim.

# CHANGELOG

Changelog é human-oriented e release-scoped; não é `git log`.

Categorias default inspiradas em Keep a Changelog:

```
Added
Changed
Fixed
Deprecated
Removed
Security
```

Podemos acrescentar `Performance` e `Developer` quando profile justificar.

Source principal:

```
accepted Changes
merged/released Requirements
resolved Bugs
breaking-change records
security advisories/public flags
```

Commits são evidence/pointers, não unidade editorial obrigatória.

# Unreleased

Manter projection `Unreleased` derivada de changes elegíveis ainda sem release. No momento da release, compiler congela o conjunto no release manifest.

# Breaking changes

Breaking change exige:

```
CHANGELOG entry
+ Release Notes mention
+ Migration Guide or explicit not-required reason
```

Readiness blocker se policy requer migration e ela está ausente.

# Release Notes

Release Notes são ASSISTED por default.

Brief inclui:

```
release version/date
major user-visible changes
why they matter
breaking/migration
known issues
compatibility
credits optional
links to changelog/docs
```

LLM cria narrativa somente a partir do release snapshot; facts importantes são verificáveis por refs.

# Release Note structure

Default:

```
What's new
Highlights
Improvements
Fixes
Breaking changes / Migration
Known issues
Upgrade/install notes
Full changelog link
```

Se release é pequena, Planner comprime estrutura; não gera seções vazias.

# Decision/Research storytelling

Chronicle pode explicar:

```
Question
Alternatives considered
Research performed
Decision
Trade-offs
Outcome after implementation
```

Isso é particularmente valioso para projetos desenvolvidos com IA porque preserva trajetória sem publicar conversas inteiras.

# Lesson harvesting

Após milestone/release, Knowledge Harvest pode produzir candidate `MemoryRecord` e `ChronicleLesson` separados:

```
ChronicleLesson → narrativa contextual do projeto
MemoryRecord → generalização reutilizável cross-project
```

Não confundir os dois.

# Links Git/Run

Chronicle e releases podem referenciar:

- commits;
- PRs/issues;
- Runs;
- benchmarks;
- screenshots;
- decision IDs.

Mas Git não é obrigatório para a semântica de um evento: Project Knowledge continua canônico.

# Public post generation

O mesmo conjunto de eventos pode produzir variantes de superfície:

```
long devlog article
short project update
release announcement
social-post draft future
```

Essas projeções são CURATED/ASSISTED; publicação automática externa nunca é default.

# Media

Screenshots, diagrams e benchmark charts usados no Devlog são Artifact refs com provenance. Generated illustrative art deve ser marcado como ilustração, não screenshot factual.

# Chronicle index

Materialized views:

```
by date
by milestone
by feature/domain
by decision
by release
by lesson
```

Search index pode navegar história sem carregar tudo em contexto.

# Retention

Raw trajectory/logs podem expirar por policy; ChronicleEvents e accepted Knowledge persistem quando têm valor durável. Chronicle nunca depende da retenção integral de prompts/tool output.

# Generation policy

```
Chronicle factual skeleton → GENERATED
Chronicle narrative → ASSISTED
CHANGELOG → GENERATED + curated override
Release Notes → ASSISTED
Public Devlog → CURATED/ASSISTED
```

# Commands candidatos

```
chronicle.compile
chronicle.preview
chronicle.mark_significant
chronicle.public_candidate
release.changelog
release.notes
release.docs_check
devlog.draft
```

# Readiness integration

Antes de release/publicação:

```
changelog coverage
migration coverage
release docs freshness
public visibility validation
example/screenshot gates
```

Public Devlog nunca bloqueia release; changelog/migration podem bloquear conforme profile.

# Invariantes fechados

- transcript não é Chronicle;
- Chronicle usa semantic events/records;
- CHANGELOG não é commit dump;
- Release Notes são release-snapshot-grounded;
- Public Devlog nasce de allowlist/visibility antes de synthesis;
- private Chronicle é default;
- nenhum canal público é publicado automaticamente sem user/project policy explícita;
- Memory Atlas e Chronicle são relacionados, mas possuem finalidades diferentes.
