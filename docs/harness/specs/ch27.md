# Baseline observado no repositório

O `raillen/prumo` já possui uma fundação significativamente avançada para agentes:

- `ENTRYPOINT.md` como bootstrap curto;
- `AGENTS.md` com authority, Notion on-demand e routing quick reference;
- `FRAMEWORK.md` com invariantes de Git durable memory, least context, pointer-over-payload e persistence classes;
- `docs/PRUMO.md` como intent router;
- `docs/LEAN_PROGRESSIVE_CONTEXT.md` com WCC, budgets, progressive retrieval e context GC;
- Documentation System M5 com Contracts, Profiles, Bindings, Coverage, Readiness e Documentation Delta;
- Living Plan M6 com decisions/open questions/authority/confidence/resume;
- Traceability M8 com graph, journal, experiments, rejections e debt;
- Experience M9 com semantic events, summaries, handoff e experience proposals;
- `docs/SOURCE_MAP.json` ligando documentação local ao Livro Vivo;
- JSON Schemas para vários machine contracts.

A nova arquitetura discutida para Prumo Code não invalida essas fundações. O principal trabalho é **unificá-las e elevá-las de baseline documental para um Knowledge Runtime semanticamente tipado, incremental e barato em tokens**.

# G1 — Falta um profile/documentation contract específico para LLMs

Hoje `docs/contracts/builtin.json` possui contratos como `product.vision`, `project.scope`, `architecture.system`, `testing.strategy`, `security.trust`, `installation.lifecycle`, `cli.reference` e `ui.documentation`. `docs/profiles/builtin.json` combina esses contratos em profiles de produto como `core-software`, `cli`, `desktop-gui`, `web-application`, `api-service`, `compiler` e `library`.

Isso é ótimo para **o que precisa estar documentado no projeto**, mas não formaliza **o que uma LLM precisa saber para operar o projeto**.

Adicionar um profile first-class candidato:

```
llm-agent / agentic-development
├── agent.entrypoint
├── agent.authority
├── agent.context-routing
├── agent.execution-protocol
├── agent.knowledge-provenance
├── agent.handoff
├── agent.tool-permissions
├── agent.evidence-completion
├── agent.documentation-delta
└── agent.memory-policy
```

Esses contracts não duplicam arquitetura/produto. Eles apontam para os contracts canônicos existentes e definem **como encontrá-los, priorizá-los e utilizá-los**.

# G2 — Falta `KnowledgeManifest` machine-readable

`ENTRYPOINT.md`, `AGENTS.md` e `docs/PRUMO.md` são bons routers para LLMs capazes de navegar Markdown. Porém o Context Runtime deveria possuir um catálogo derivado e determinístico.

Modelo candidato:

```
KnowledgeManifest
├── version
├── source_revision
├── documents[]
│   ├── document_id
│   ├── path
│   ├── role
│   ├── authority
│   ├── ownership
│   ├── freshness
│   ├── content_digest
│   ├── token_estimate
│   ├── contracts[]
│   ├── sections[]
│   ├── dependencies[]
│   └── change_triggers[]
└── indexes
```

Esse manifest é **derived/rebuildable**. Não cria um novo source of truth; ele transforma a documentação canônica em uma superfície eficiente para retrieval.

# G3 — Source Map precisa de identidade/provenance mais forte

`docs/SOURCE_MAP.json` atualmente é útil, mas os vínculos com Notion usam principalmente `title` + `role`, além do `local_path` e `semantic_role` do documento.

Para uma arquitetura de provenance durável, incluir em cada source edge quando disponível:

```
source_id
source_type: notion | repository | web | generated
source_url / page_id
document_id / section_id
source_revision / last_reviewed_revision
content_digest
authority
freshness_class
imported_at / reviewed_at
extraction_version
supersedes / superseded_by
```

Especialmente para Notion, **título não deve ser identidade primária**; usar page ID/URL persistente.

# G4 — SectionID e ClaimID

O schema de Binding aceita `sections`, mas o binding real atual é essencialmente file-based. Isso limita context precision, provenance e invalidation.

Introduzir stable IDs independentes de heading text:

```
DOC:architecture
SEC:architecture.desktop-runtime
CLAIM:architecture.desktop-runtime.core-owned-state
```

Um heading pode ser renomeado sem destruir identidade histórica.

`Claim` candidato:

```
Claim
├── id
├── subject
├── predicate
├── value / statement
├── status
├── authority
├── confidence
├── freshness
├── provenance[]
├── valid_from / reviewed_at
├── supersedes[]
└── contradictions[]
```

Nem todo parágrafo precisa virar Claim. Claims são reservados para fatos/decisões/invariantes úteis a reasoning, contradiction e traceability.

# G5 — Impact analysis precisa deixar de ser path substring

No baseline atual, `triggerMatches` reduz algo como `architecture.changed` para `architecture` e verifica se esse token aparece no path alterado.

Evoluir para:

```
DomainEvent / KnowledgeDelta
      ↓
Typed ChangeEvent
├── entity_id
├── change_kind
├── changed_fields
├── semantic_projection_digest
└── source_revision
      ↓
Documentation Dependency Graph
      ↓
reverse closure
```

Paths continuam úteis como input para mudanças de código, mas não como único mecanismo causal.

# G6 — Coverage/readiness precisa de KnowledgeItem IDs

O evaluator atual concatena documentos, lowercases e considera um `required_knowledge` encontrado quando **qualquer palavra** daquela descrição aparece no texto. Isso é adequado como bootstrap heuristic, mas permissivo demais para contracts fortes.

Evolução:

```
Contract
required_knowledge:
  - KI:architecture.system.boundaries
  - KI:architecture.system.state-owner
  - KI:architecture.system.dependencies
```

Binding:

```
KI:architecture.system.state-owner
→ SEC:architecture.canonical-state
→ claims [...]
```

Coverage então é calculado por IDs/relationships, não por presença lexical.

Da mesma forma, `Verified` não deve depender apenas de `len(evidence) >= len(requirements)`. Cada `EvidenceRequirement` precisa ser satisfeita por evidence typed/compatible.

# G7 — Context Compiler v2 — arquitetura fechada, implementação pendente

O `Source` atual possui `Ref`, `Authority`, `Freshness`, `TokenCost`, `Included`, `Reason`, mas `Compile` ordena authority lexicalmente, depois menor custo e ref; freshness não participa efetivamente da seleção.

Novo `ContextItemDescriptor`:

```
id / ref
kind
authority_rank
freshness_class
freshness_revision
relevance_score
mandatory / pinned
scope_match
provenance
content_digest
retrieval_method
compression_level
token_estimate
full_content_pointer
related_entities[]
reason_codes[]
```

Selection pipeline:

```
hard mandatory/pinned
→ authority/trust filter
→ freshness validity
→ scope/task relevance
→ dependency completeness
→ diversity/coverage constraints
→ score per token
→ budget packing
→ pressure/compaction policy
```

A arquitetura foi posteriormente fechada: authority/trust/freshness/privacy como eligibility gates; exact/structured retrieval primeiro; FTS5/BM25 baseline; embeddings derivados; RRF para fusion; MMR para anti-redundancy; dependencies/coverage como constraints; greedy marginal-utility-per-token packing; progressive disclosure L0–L4 e Context Manifest replayable. Ver [31 — Context Compiler v2: Hybrid Retrieval, Authority/Freshness, Budget Packing e Progressive Disclosure](ch31.md). O gap desta auditoria passa a ser **implementar e provar conformance/evals**, não decidir a arquitetura.

# G8 — Concrete schema/runtime drift encontrado

`schemas/context-manifest.schema.json` aceita pressure:

```
healthy | pressure | compact | critical
```

mas `internal/contextcompiler/context.go` implementa apenas:

```
healthy | pressure | critical
```

Este é exatamente o tipo de drift que um machine-contract CI gate precisa capturar.

Recomendação:

- schema ↔ Go enum conformance tests;
- fixture round-trip;
- schema version compatibility tests;
- generated enum test data quando útil.

# G9 — Machine schema validation precisa ser centralizada

A documentação M5 declara machine schema validation. `LoadRegistry`/`LoadBindings` atuais fazem `json.Unmarshal` + validações manuais locais; durante esta auditoria não foi encontrado, nesses loaders, um passo explícito de validação contra `documentation-contract.schema.json` / `documentation-binding.schema.json`.

Não assumir que isso prova ausência global de validação; o gap arquitetural é que **a boundary que carrega o contract não torna a validação de schema inevitável**.

Direção:

```
Read bytes
→ Validate schema/version
→ Decode typed object
→ Semantic Validate()
→ Use
```

Ou validators tipados gerados/compilados, desde que JSON Schema continue sendo contrato interoperável.

# G10 — Contradiction Engine ainda é bootstrap-specific

`DetectContradictions` atual busca conflito de `port/default_port` por regexp em um conjunto fixo de documentos. É uma excelente prova de conceito determinística, mas não um contradiction system genérico.

Separar:

```
Syntactic Contradiction
→ typed values disagree

Semantic Contract Contradiction
→ incompatible Claims/Decisions

Authority Conflict
→ lower-authority source conflicts with higher-authority claim

Temporal Supersession
→ old claim was valid but superseded
```

O motor determinístico resolve somente relações declaradas. Contradições de prosa ambígua podem gerar candidate findings via LLM, sempre review-governed.

# G11 — Research Ledger precisa ser first-class

Living Plan tem Decision model forte, mas a pesquisa que alimenta decisões ainda não possui um record equivalente no core auditado.

```
ResearchRecord
├── id
├── question
├── scope
├── findings[]
├── sources[]
├── researched_at
├── freshness_class
├── review_after
├── confidence
├── supported_decisions[]
├── contradictions[]
└── search_seed
```

`SourceRecord` separa metadados da fonte de findings:

```
SourceRecord
├── id
├── locator
├── source_type
├── publisher/owner
├── trust_class
├── retrieved_at
├── published_at
├── content_digest
├── license/citation metadata
└── instruction_trust = data_only | trusted_instruction
```

Esse último campo é importante para impedir que conteúdo web/repositório externo seja tratado como instruction pelo agent.

# G12 — Memory Atlas ainda não existe como modelo completo

M9 Experience Layer possui `ExperienceProposal`, mas atualmente o objeto é principalmente pattern/observation/proposed action/source session/review status.

O Atlas precisa de um nível diferente:

```
MemoryRecord
├── id / kind / title
├── compact_summary
├── full_content_pointer
├── scope/privacy
├── domains/tags/technologies
├── claims[]
├── provenance[]
├── authority/confidence
├── freshness
├── valid_from/reviewed_at
├── project_refs[]
├── contradictions[]
├── supersedes[]
├── semantic_fingerprint
└── token_estimate
```

`ExperienceProposal` pode virar uma das **fontes de promotion candidates**, não ser o MemoryRecord em si.

# G13 — Handoff v2 precisa transportar pointers estruturados

O schema atual é sólido como M9 baseline, mas `claims`, `active_decisions`, `open_questions` e `evidence` ainda são arrays de strings.

Para cross-provider/cross-agent continuation robusta:

```
HandoffV2
├── from/to AgentSession refs
├── Run / Goal / Task
├── checkpoint_ref + digest
├── context_manifest_ref + digest
├── workspace_revision
├── active_decision_refs[]
├── open_question_refs[]
├── evidence_refs[]
├── current_change/diff refs[]
├── pending_permission refs[]
├── pending_side_effect refs[]
├── terminal/process refs when transferable
├── budget snapshot
├── provider/agent capability snapshot
└── acknowledgement requirements
```

Payload continua pequeno: pointers + summaries, não transcript.

# G14 — Traceability Graph deve absorver conhecimento documental novo

M8 já possui excelente base `req/dec/goal/code/test/doc/evidence/experiment/rejection/debt`. Para Planning/Knowledge Runtime considerar adicionar:

Node kinds:

```
constraint
risk
research
source
claim
open_question
memory
artifact
contract
section
```

Edge kinds:

```
supersedes
contradicts
informed_by
depends_on
answers

generated_from

```

Não é obrigatório colocar **dependency graph do build documental** exatamente no mesmo Graph. Uma solução limpa é dois graphs especializados com IDs interoperáveis:

```
TraceabilityGraph = significado/provenance
BuildGraph        = computação/invalidation
```

# G15 — Agent write protocol deve ser KnowledgeDelta-first

O agent não deveria ter como fluxo padrão “abra [architecture.md](http://architecture.md) e reescreva livremente”.

```
Agent result
→ KnowledgeDelta
→ validation
→ contradiction/authority check
→ Documentation Impact
→ Documentation Delta / GenerationPlan
→ preview/review policy
→ deterministic compiler
```

`KnowledgeDelta` candidato:

```
decisions[]
requirements[]
constraints[]
research_findings[]
risks[]
open_questions[]
evidence_refs[]
source_refs[]
supersessions[]
```

Para documentos human-owned, a alteração final pode continuar sendo patch/review; o importante é preservar a intenção semântica antes de mutar prosa.

# G16 — Generation ownership precisa ser explícito

Cada artifact/section deve declarar:

```
human-maintained
prumo-maintained
generated
mixed-managed-regions
external/reference
```

Para `mixed-managed-regions`, usar stable region ID + previous generation digest + conflict policy. Nunca overwrite silencioso de conteúdo humano.

# G17 — Agent Knowledge API

A documentação para LLM deve ter uma API/CLI determinística, evitando que cada integration invente seu próprio grep workflow.

Commands candidatos:

```
prumo knowledge locate --goal G...
prumo knowledge search <query> --scope ... --json
prumo knowledge explain <ref> --json
prumo knowledge provenance <ref> --json
prumo knowledge refresh <ref>

prumo docs context --goal G... --budget 8000 --json
prumo docs affected --record D-42 --json
prumo docs why --section SEC:... --json
prumo docs compile --plan --json
```

A UI/ACP/SDK consome application services, não shell parsing.

# G18 — Token-estimate index

Hoje token cost entra no Context Compiler como valor já fornecido. Criar derived index com:

```
bytes/chars
model-neutral token estimate
optional tokenizer-family estimates
compressed-summary token estimate
last estimated digest
```

Nunca invalidar knowledge porque tokenizer mudou; token estimates são derived metadata.

# G19 — Lint dos próprios agent docs

`ENTRYPOINT.md`, `AGENTS.md`, `FRAMEWORK.md` e `docs/PRUMO.md` possuem informação propositalmente sobreposta. Criar um `AgentDocsLint` para evitar drift:

- links/paths inexistentes;
- conflicting authority order;
- conflicting canonical-format rules;
- schema/runtime enum mismatch;
- router points to missing document;
- duplicate machine contract IDs;
- unknown profiles/contracts;
- stale SourceMap target;
- entrypoint exceeds configured token budget.

Durante esta auditoria, `docs/PRUMO.md` apresenta `SOURCE_MAP.json` como provenance contract, enquanto o arquivo concreto está em `docs/SOURCE_MAP.json`; um manifest/ID estável evita ambiguidade desse tipo.

# G20 — Schema evolution e migrations

Machine contracts possuem `version`, mas o Knowledge Runtime precisa de uma política única:

```
schema ID
schema version
minimum reader version
migration path
canonicalizer version
breaking/non-breaking classification
```

ContextManifest, Handoff, DocumentationContract, Binding, MemoryRecord e ArtifactManifest devem ter migration/conformance fixtures como outros protocolos do Prumo.

# G21 — Evaluation suite específica para documentação de agents

Criar corpus/gates com tarefas como:

- selecionar documento correto sem carregar árvore inteira;
- respeitar authority quando fontes conflitarem;
- rejeitar source stale para claim time-sensitive;
- recuperar decisão superseding em vez da antiga;
- atingir context recall com token budget baixo;
- detectar docs afetados por KnowledgeDelta;
- transferir Run entre agents sem transcript;
- compilar docs duas vezes com byte-identical output;
- não sobrescrever managed region editada manualmente;
- encontrar provenance de um claim;
- medir Memory Atlas reuse vs nova pesquisa.

Métricas:

```
context precision / recall
routing accuracy
authority violation rate
stale-knowledge use rate
handoff completeness
document-impact precision / recall
tokens per successful task
tokens per accepted decision
reproducibility rate
unnecessary rebuild ratio
```

# G22 — Privacy, scope e cross-project memory

Antes do Memory Atlas global:

```
scope:
  session | project | workspace | global

classification:
  public | project-private | personal | secret

promotion:
  forbidden | manual | suggested | automatic-allowed
```

Secret/token/raw credential nunca é promovido. Project deve poder impedir global reuse de categorias inteiras.

# G23 — Retention sem dangling provenance

M9 permite prune de raw events preservando summaries. Antes de apagar um source transitório que sustenta conhecimento promovido:

- garantir summary/evidence digest durável;
- promover provenance mínimo necessário;
- atualizar pointer para archived source quando aplicável;
- ou impedir promoção quando a evidence não poderá mais ser auditada.

A GC nunca pode transformar `MemoryRecord` em afirmação sem origem verificável.

# Inconsistências concretas encontradas nesta auditoria

## C1 — Context pressure schema/runtime

Schema possui `compact`; Go baseline não.

**Ação:** conformance test + definir semantics de compact ou remover até implementação.

## C2 — Impact trigger excessivamente lexical

`architecture.changed` → token `architecture` → substring em path.

**Ação:** typed ChangeEvent/dependency graph.

## C3 — Contradiction detector específico para port

Útil como fixture/proof, insuficiente como engine.

**Ação:** typed claims/rules.

## C4 — Coverage false-positive risk

Required knowledge é satisfeito por qualquer palavra encontrada no blob de docs.

**Ação:** KnowledgeItem IDs e explicit binding.

## C5 — Evidence verification por contagem

Quantidade de evidence pode marcar Verified sem mapear requirement → evidence.

**Ação:** typed EvidenceRequirement satisfaction.

## C6 — Context ranking usa authority como string

Lexicographic order não é semantic authority order e freshness não influencia inclusion.

**Ação:** enum/rank + explicit policy.

## C7 — Documentation Delta write não é transactional

`SaveDelta` usa write direto; timestamps fazem parte do persisted record lifecycle.

**Ação:** timestamps ficam lifecycle metadata, mas identidade/fingerprint semântica é separada; transactional writer para generated artifacts.

## C8 — SourceMap Notion links dependem de titles

**Ação:** IDs/URLs/revisions/digests.

## C9 — Handoff sem typed knowledge refs

**Ação:** Handoff v2.

## C10 — ExperienceProposal não equivale a MemoryRecord

**Ação:** promotion pipeline Experience → Project Knowledge → Atlas.

# Conclusão

O repositório já possui as peças corretas em estado baseline: routing, authority, Documentation Contracts, Living Plan, Context Compiler, traceability, Experience/Handoff e schema ecosystem. O gap não é “falta documentação para agentes”; é a ausência de uma **camada semântica unificada** capaz de transformar essas peças em:

```
Agent intent
→ deterministic knowledge discovery
→ minimal trusted context
→ structured decisions/research
→ traceable KnowledgeDelta
→ incremental documentation compile
→ typed handoff
→ validated project knowledge
→ cross-project Memory Atlas
```

A recomendação é evoluir incrementalmente as fundações existentes, não substituí-las.

# G24 — Local Knowledge Intelligence é um acelerador opcional, não source of truth

A auditoria levou a uma extensão útil: parte de retrieval, catalogação e compaction pode ser executada localmente sem consumir tokens do provider principal.

A direção é **não** usar uma única LLM para “fazer RAG”. Separar:

```
Deterministic index
+ FTS5/BM25
+ typed graph
      ↓
EmbeddingProvider
      ↓
optional RerankProvider
      ↓
Context Compiler v2
      ↓
optional KnowledgeGenerationProvider
```

A pesquisa e arquitetura completas estão em [28 — Local Knowledge Pack: Small Models, Offline RAG e Document Intelligence](ch28.md).

Integração com os workstreams:

- `LD2 Context Compiler v2` consome resultados de hybrid retrieval;
- `LD3 Knowledge & Provenance Model` define o que o modelo pode classificar/extrair;
- `LD4 Documentation Compiler` permanece determinístico;
- `LD7 Memory Atlas` usa embeddings como índice derivado;
- `LD8 Knowledge API` expõe providers locais/remotos de forma uniforme;
- `LD9 Evals` decide, por medição, se encoder/reranker/generator justificam custo de RAM/download.

Invariante adicional: **nenhum output de tiny local model se torna Decision, Claim, authority ou canonical documentation apenas por ter sido produzido localmente**. O output é proposal e passa por schema, provenance, authority, contradiction e review policies normais.
