# Princípio central

A arquitetura deve separar explicitamente:

```
Capability requested
        ↓
Routing policy
        ↓
Resource availability
        ↓
Concrete local/remote model
```

Código de domínio nunca deve depender do nome concreto de um modelo. O Knowledge Runtime solicita capabilities e quality tiers; o `KnowledgeModelRouter` resolve a implementação disponível respeitando o perfil instalado, hardware, memória livre, preferência do usuário, custo e qualidade.

# Invariantes

- `No-LLM` é um modo first-class e plenamente funcional, não uma versão degradada/quebrada.
- modelos instalados não precisam permanecer residentes em RAM;
- usar **minimum sufficient model**: escolher o menor recurso que satisfaz a capability/quality requerida;
- modelos maiores são lazy-loaded e descarregados por política de idle/pressão de memória;
- deterministic-first: código normal resolve tudo que puder antes de chamar qualquer modelo;
- local-first/remote-first é uma preferência, não uma dependência estrutural;
- todos os perfis usam os mesmos contracts, commands, schemas e artifacts;
- modelos podem ser substituídos no futuro sem alterar o nome/semântica dos perfis;
- estimativas de RAM exibidas ao usuário vêm de benchmarks reais do Prumo por artifact/runtime/backend, não de tamanho de arquivo tratado como RAM.

# Perfis de instalação

| Perfil | Capabilities locais | Stack candidata inicial | Headroom adicional de RAM alvo | RAM total recomendada do computador |
| --- | --- | --- | --- | --- |
| **No-LLM** | deterministic knowledge only | SQLite/FTS5/BM25 + graph + Documentation Compiler | ~0,2–0,5 GB de índices/runtime | **8 GB+** |
| **Ultra-Light** |   • semantic retrieval | Granite Embedding 97M R2 | ~0,3–0,6 GB | **8 GB+** |
| **Light** |   • tiny semantic worker | Granite 97M + Qwen3-0.6B ou vencedor do benchmark ultralight | ~1,5–2,5 GB pico | **8–12 GB+** |
| **Balanced** |   • standard local knowledge reasoning | Granite 97M + tiny worker + Qwen3-1.7B/standard winner | ~3–5 GB pico budget | **16 GB+** |
| **Ultra** | advanced retrieval/reranking + maximum local intelligence | Granite + Qwen3-Embedding-0.6B + reranker + tiny + standard workers | ~5–8 GB pico budget | **24–32 GB+** |
| **Custom** | user-defined | model registry + explicit capabilities/resources | declarado/medido | declarado/medido |

Os valores acima são **budgets de projeto conservadores**, não soma dos tamanhos dos artifacts. Eles serão substituídos por medições do Prumo para combinação específica de backend, quantização, context length, batch e hardware.

# Semântica de cada perfil

## No-LLM

Inclui:

- parsing Markdown/JSON/AST;
- JSON Schema e typed contracts;
- `KnowledgeManifest`, SectionID/ClaimID conhecidos;
- SQLite, FTS5/BM25 e structured filters;
- graph traversal e traceability;
- authority/freshness/provenance;
- Dependency/Build Graph;
- deterministic Documentation Compiler;
- Decision/Research Ledger e Memory Atlas estruturado;
- Context Compiler;
- optional remote providers quando policy permitir.

Não inclui semantic embeddings nem generation local. `No-LLM != no intelligence`; significa **deterministic intelligence only** localmente.

## Ultra-Light

Adiciona encoder semântico pequeno. Objetivo: related-doc search, semantic retrieval, clustering candidates e similar-memory discovery com footprint mínimo. Nenhum generator local é necessário.

## Light

Adiciona tiny Knowledge Worker para tarefas baratas e curtas: tagging, section classification, short summaries, candidate Decision/Requirement/Constraint extraction, title normalization e query rewriting.

## Balanced

É o perfil recomendado para 16 GB. Adiciona um worker standard para ambiguidades, contradiction candidate analysis, richer extraction, compaction e synthesis local moderada. Tiny worker continua sendo preferido quando suficiente.

## Ultra

Não significa “todos os modelos residentes”. Significa **maior catálogo local + budgets maiores + routing mais local**: advanced embedding, optional reranker, tiny worker e standard worker disponíveis on demand. O encoder default pode continuar sendo o único residente.

## Custom

Usuário pode substituir qualquer role desde que o `KnowledgeModelDescriptor` declare capabilities, licensing, resource profile, artifact digest e runtime compatibility.

# ResourceProfile vs ModelSelection

Perfis não devem hard-code nomes concretos de modelos.

```
Balanced
├── semantic_retrieval = local
├── cheap_generation = local
├── complex_generation = local_preferred
├── difficult_reasoning = remote_allowed
├── soft_memory_budget = measured profile target
└── hard_memory_budget = measured profile target
```

O Registry resolve, na versão atual:

```
semantic_retrieval → Granite 97M
cheap_generation → Qwen3-0.6B / benchmark winner
complex_generation → Qwen3-1.7B / benchmark winner
```

No futuro essas escolhas podem mudar sem redefinir `Balanced`.

# Knowledge Model Router

Pipeline:

```
Knowledge Task
→ deterministic possible?
  yes → deterministic engine
  no  → capability request
→ filter installed/available models
→ privacy/locality policy
→ hardware/resource feasibility
→ quality threshold
→ estimated latency/cost
→ minimum sufficient model
→ execute
→ validate structured result
→ accept proposal / escalate / remote fallback
```

Nunca usar `if model == "qwen..."` em business logic. Models são adapters atrás de contracts estáveis.

# Escada de inteligência

```
Tier 0 — Deterministic
  ↓ se semantic retrieval necessário
Tier 1 — Embedding
  ↓ se semantic generation necessário
Tier 2 — Tiny local worker
  ↓ se tarefa exceder qualidade calibrada
Tier 3 — Standard local worker
  ↓ se ainda insuficiente ou indisponível
Tier 4 — Remote cheap provider
  ↓ quando policy/quality exigir
Tier 5 — Remote premium agent/model
```

Cada perfil disponibiliza um prefixo diferente dessa escada; o domínio continua igual.

# Escada por perfil

```
No-LLM:
Deterministic → Remote optional

Ultra-Light:
Deterministic → Embedding → Remote optional

Light:
Deterministic → Embedding → Tiny → Remote optional

Balanced:
Deterministic → Embedding → Tiny → Standard → Remote optional

Ultra:
Deterministic → Default Embedding → Advanced Embedding/Rerank → Tiny → Standard → Custom/Larger Local → Remote optional
```

# Confidence / escalation

O worker menor pode emitir confidence/reason codes, mas **não tratar self-reported confidence como probabilidade calibrada**. O Prumo cria thresholds a partir de evals próprios.

```
small worker result
→ schema valid?
→ confidence/calibration policy
→ criticality policy
→ accept candidate or escalate
```

Em áreas críticas, escalation pode ser obrigatória independentemente do score.

# Resource Manager

`ResourceManager` observa o estado real da máquina e impede que o perfil instalado cause swapping/crash.

```
SystemResources
├── total_ram
├── available_ram
├── memory_pressure
├── swap availability/pressure
├── cpu_threads
├── cpu_load
├── gpu_vram / available_vram
├── backend availability
├── battery/power mode when available
└── thermal state when available
```

Antes de carregar um modelo:

```
required measured peak
+ safety reserve
<= available resource budget ?
```

Se não:

```
smaller local model
→ remote provider if allowed
→ capability unavailable with explicit reason
```

Nunca forçar load apenas porque o usuário instalou `Balanced`/`Ultra`.

# Residency and lifecycle

Instalado ≠ residente.

Política default candidata:

- embedding default: long TTL ou resident quando footprint/benchmarks justificarem;
- generator: lazy-load;
- somente um generator local grande por default;
- reranker: short-lived, somente candidate set pequeno;
- unload por idle TTL, memory pressure ou mudança de workspace/policy;
- preloading apenas em modo agressivo e quando benchmark mostrar benefício.

# MemoryPressurePolicy

Separada do installation profile:

## Conservative

- unload imediatamente após job/little TTL;
- nunca dois generators grandes simultâneos;
- preferir remote quando memória pressionada;
- contexto/batch conservadores.

## Normal — default

- short idle TTL;
- um generator ativo;
- embedding pode permanecer warm;
- balance local/remote segundo profile.

## Aggressive

- longer TTL;
- preload previsto quando seguro;
- maior uso de CPU/GPU/RAM;
- adequado a workstations.

# Execution Preference

Outra dimensão independente do profile instalado:

```
Lowest Memory
Lowest Latency
Balanced
Local First
Remote First
Lowest Cost
Maximum Quality
```

O usuário pode instalar `Ultra` e ainda escolher `Lowest Memory`; ou instalar `Balanced` e usar `Local First`.

# Hardware-aware installer

O instalador detecta recursos e **recomenda**, nunca bloqueia arbitrariamente.

Exemplo:

```
Detected:
RAM 16 GB
CPU 8 cores
GPU VRAM 6 GB

Recommended: Balanced
```

A tela deve exibir para cada profile:

```
models/artifacts candidatos
exact download bytes
post-install disk usage
measured typical RAM delta
measured peak RAM budget
recommended total system RAM
license summary
capabilities gained
can remove/change later
```

Valores de download/RAM são lidos dos manifests da versão atual, não hard-coded no frontend.

# Telemetry local e policy learning

Sem ML adicional, o Prumo pode registrar métricas locais agregadas por task class:

```
model
backend
hardware class
task kind
latency
peak RAM
schema-valid result
accepted/rejected/escalated
human/agent review outcome when available
```

Isso gera `TaskModelPolicy` derivada de benchmark/experiência:

```
short_summary → tiny worker
contradiction_candidate → standard worker
semantic_retrieval → Granite
```

Telemetry de conteúdo/documentos não deve ser enviada externamente por default; métricas respeitam privacy policy.

# Context discipline para modelos locais

Não usar context window máxima simplesmente porque existe. O pipeline deve fazer AST/semantic chunking e progressive disclosure antes da inferência.

Targets iniciais candidatos:

- classificação/tagging: centenas a poucos milhares de tokens;
- extraction/summaries: sections selecionadas;
- synthesis: somente records relevantes;
- large-context local inference: exceção explícita.

Menor contexto reduz RAM, latency e energia e facilita modelos pequenos.

# Fallback local/remoto

O Knowledge Router integra-se ao Model Gateway sem confundir os domínios:

```
Local Knowledge Router
→ local capability unavailable / resource constrained / quality insufficient
→ Model Gateway route appropriate to knowledge task
```

Remote provider recebe somente o **menor Context Pack necessário**, nunca corpus inteiro por default.

# Segurança e privacidade

- perfil local não altera authority;
- model output sempre proposta até validação/governance;
- conteúdo não confiável continua `data_only`, nunca instruction;
- secrets/redaction antes de embedding/generation conforme policy;
- vector index respeita deletion/privacy scope;
- cada artifact possui provenance/digest/licença;
- usuário pode desabilitar Local AI, embeddings, reranking ou generation separadamente;
- profiles podem ser alterados/reinstalados sem migrar canonical knowledge.

# Evals necessários antes de congelar modelos concretos

Perfis/capabilities estão ACCEPTED; **quais modelos concretos ocupam cada role permanece benchmark-driven**.

Avaliar no corpus Prumo PT/EN/código:

- retrieval Recall@K / nDCG;
- cross-lingual/code retrieval;
- classification accuracy;
- Decision/Requirement/Constraint extraction precision/recall;
- summary faithfulness;
- schema-valid rate;
- duplicate/supersession/contradiction candidate precision;
- latency cold/warm;
- measured RAM/VRAM;
- load/unload overhead;
- CPU utilization/energy where practical;
- escalation rate;
- quality/cost saved versus remote.

# Decisões fechadas nesta página

1. Perfis oficiais: `No-LLM`, `Ultra-Light`, `Light`, `Balanced`, `Ultra`, `Custom`.
2. `Balanced` é o nome preferido em vez de `Moderate`.
3. Profiles representam capability/resource policies, não listas rígidas de models.
4. `No-LLM` é first-class.
5. Installed ≠ resident; lazy load/unload é arquitetura padrão.
6. Minimum sufficient model é política central.
7. `ResourceManager` faz routing hardware-aware em runtime.
8. `MemoryPressurePolicy` e `ExecutionPreference` são dimensões separadas do installation profile.
9. Local fallback pode escalar para Model Gateway remoto quando permitido.
10. Concrete model mapping permanece benchmark-driven/versionável.

# Open Questions restantes

A arquitetura de profiles/routing está fechada; estes pontos permanecem `OPEN` ou `BENCHMARKING`:

1. **Concrete model winners por role:** Granite 97M é favorito de embedding default, mas tiny/standard worker, advanced embedding e reranker só viram default depois do Prumo Knowledge Benchmark.
2. **Tiny worker:** Qwen3/Qwen3.5 0.6–0.8B vs LFM2.5-350M vs futuros modelos equivalentes; medir qualidade PT/EN/código, structured output, RAM, latency e licença/distribuição.
3. **Standard worker:** Qwen3-1.7B vs LFM2.5-1.2B e challengers; mesma metodologia.
4. **Primary local runtime/backend:** `llama.cpp/GGUF`, ONNX Runtime, OpenVINO e possíveis backends platform-native; podemos usar backends diferentes por role.
5. **Quantization defaults:** Q4_K_M, Q5/Q8 ou variantes específicas por hardware/model; decisão guiada por quality/RAM/latency.
6. **GPU policy:** quando usar CPU-only, GPU offload parcial ou GPU-first; como medir VRAM sem degradar editor/terminal/compilação.
7. **Installer recommendation thresholds:** valores exatos de RAM/CPU/VRAM para recomendar Ultra-Light/Light/Balanced/Ultra após benchmarks reais; números atuais são budgets conservadores.
8. **Default MemoryPressurePolicy:** `Normal` está proposto como default; definir TTLs, safety reserve, thresholds de pressão e número máximo de models simultâneos.
9. **ExecutionPreference default:** `Balanced` é candidato; definir interação entre `Local First`, `Lowest Cost`, `Maximum Quality` e policies do Model Gateway.
10. **Local→remote escalation:** quais task classes podem escalar automaticamente, quais exigem confirmação e quais devem permanecer local-only por privacy.
11. **Calibration/escalation thresholds:** criar corpus e método para calibrar quando tiny worker é suficiente e quando subir para standard/remote; não usar confidence self-reported crua.
12. **Reranker adoption:** provar nDCG/Recall gain suficiente sobre hybrid FTS+embedding+graph para justificar download/RAM/latency.
13. **Advanced embedding adoption:** provar quando Qwen3-Embedding-0.6B supera Granite o suficiente para entrar em `Ultra` como route normal em vez de challenger manual.
14. **Model package distribution:** download on-demand vs optional installer bundle; mirrors/CDN, checksum/signature, atualização, rollback e retention de versões antigas.
15. **License UX:** como exibir/registrar aceite de modelos com licença não-Apache (ex. Liquid) sem tornar o Core dependente deles.
16. **Local telemetry retention:** métricas mínimas para TaskModelPolicy, retenção, opt-in/out e garantia de que conteúdo documental não é exportado.
17. **Power/thermal policy:** quanto battery/thermal state deve influenciar routing em notebooks.
18. **Multimodal knowledge:** quando habilitar modelos como Qwen3.5 para screenshots/diagramas e se isso pertence a `Ultra` ou a um capability pack separado.
19. **Custom profile schema:** formato final de override, inheritance e validation para profiles/model mappings definidos pelo usuário.
20. **Benchmark hardware matrix:** definir máquinas de referência (Legacy/Baseline/Developer/Workstation) para publicar measured RAM/latency de cada profile.

# Próximo gate recomendado

Antes de implementar model-specific routing, criar primeiro:

```
KnowledgeTask contract
KnowledgeModelDescriptor
ResourceProfile
SystemResources snapshot
KnowledgeModelRouter interfaces
ResourceManager interfaces
benchmark/eval corpus
```

Só depois congelar `model → role` e os budgets finais. Isso mantém a implementação testável e evita que o primeiro conjunto de modelos se torne acoplamento permanente.
