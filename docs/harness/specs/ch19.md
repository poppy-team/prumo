# Decisões consolidadas

- **Desktop ACCEPTED:** Rust + Floem.
- **TUI ACCEPTED:** Go + Bubble Tea v2 e Charm Stack.
- **Strategic challengers:** GoGPU/UI e R3BL permanecem em estado WATCH, com triggers explícitos de reavaliação.
- **Produto ACCEPTED:** Agentic Development Workbench, agent-first, editor-grade e não IDE-complete.
- **Workspaces ACCEPTED:** Agentic, Code, Review e Terminal como perspectivas do mesmo Run.
- Desktop e TUI compartilham a mesma **linguagem visual Zed-like + tokens semânticos**, mas implementações nativas distintas. A TUI pode ser deliberadamente **mais colorida, divertida e viva**, usando cor como parte forte da identidade de agents, Runs, tools e estados, sem perder densidade/clareza.
- **Connectivity ACCEPTED:** distinguir ModelProvider de AgentProvider; preferir runtimes oficiais/ACP/SDK/RPC/structured CLI quando disponíveis; credential ownership explícito; custom Model Providers e custom Agent Providers suportados.
- Stack consolidada: [21 — HISTÓRICO/SUPERSEDED: Stack H Floem + Bubble Tea v2](superseded-floem-stack.md)
- Connectivity consolidada: [22 — Agent Connectivity Runtime: Providers, OAuth, ACP, SDK, RPC e CLI](ch22.md)
- **Shared Product Contract ACCEPTED:** Run como entidade central; domínios e state ownership separados; `Thread/Session/Turn/Message`, `Provider/Profile/Agent/Session`, `Goal/Plan/Task/Run` e `Change/Patch/Diff/Evidence/Gate` distintos; Command Registry canônico; fluxo Command → Action → Event; capability negotiation Product/Agent/Client; Selection/Inspector contextual.
- Shared Product Contract: [23 — Shared Product Contract: Entities, State Ownership, Capabilities e Commands](ch23.md)
- **Workforce/Model Gateway ACCEPTED:** multi-agent heterogêneo opcional; Model Gateway/Proxy independente; routing/fallback/circuit breaker/quota-aware policies; fallback transparente somente antes de efeitos observáveis; após side effects usar Handoff explícito e auditável. [24 — Workforce Runtime, Model Gateway, Routing, Fallback e Handoff](ch24.md)
- **Planning & Knowledge direction ACCEPTED:** Plan Mode conversacional/investigativo com PlanningSession, Decision/Research ledgers, Documentation Compiler e Memory Atlas cross-project serializável; transcript não é verdade canônica e promoção global exige provenance/freshness/privacy. [25 — Planning & Knowledge Runtime: Plan Mode, Decision Ledger e Memory Atlas](ch25.md)
- **Local Intelligence Profiles ACCEPTED:** perfis `No-LLM`, `Ultra-Light`, `Light`, `Balanced`, `Ultra` e `Custom`; `Balanced` substitui o nome `Moderate`; profiles são capability/resource policies e não listas rígidas de modelos; `No-LLM` é first-class; installed ≠ resident; lazy load/unload e minimum-sufficient-model são invariantes; `ResourceManager`, `MemoryPressurePolicy`, `ExecutionPreference` e `KnowledgeModelRouter` são separados; fallback local→Model Gateway remoto é permitido por policy. Modelos concretos permanecem benchmark-driven/versionáveis. [29 — Local Intelligence Profiles, Resource Manager e Knowledge Model Router](ch29.md)
- **Local Inference Runtime ACCEPTED:** inference nativa fica fora do Core Go em workers supervisionados; `llama.cpp/GGUF` é o runtime primário de generation/rerank e ONNX Runtime Core/ONNX é o runtime primário de embeddings; OpenVINO é acceleration adapter opcional; model packages e runtime packages têm lifecycle independente; load/admission/eviction pertencem ao ResourceManager; packages usam staging + digest + side-by-side promotion/rollback. [30 — Local Inference Runtime Architecture: Workers, GGUF/ONNX, Lifecycle e Packaging](ch30.md)
- **Context Compiler v2 ACCEPTED:** authority/trust/freshness/privacy são eligibility gates antes de relevance; exact/structured retrieval precede fuzzy; FTS5/BM25 é baseline obrigatório; embeddings são derivados/opcionais; RRF é baseline de hybrid fusion; MMR controla redundância; dependencies/coverage são constraints; packing usa greedy marginal-utility-per-token + progressive disclosure L0–L4; Context Manifest v2 é replayable. [31 — Context Compiler v2: Hybrid Retrieval, Authority/Freshness, Budget Packing e Progressive Disclosure](ch31.md)
- **Deterministic Documentation Compiler ACCEPTED:** Knowledge IR separado de Document IR; pure build nodes; dependency DAG com reverse invalidation; red/green semantic digests; content-addressed cache; canonical serialization; reproducible outputs; whole-file generation ou AST-aware managed regions; JSON Pointer/Patch; platform-aware AtomicReplace; provenance/manifests; no-op detection e property/golden/fuzz tests. [26 — Deterministic Documentation Compiler: IR, DAG, Incremental Build e Canonical Outputs](ch26.md)
- **Handoff v2 + Knowledge API ACCEPTED:** continuation é typed/pointer-first e não depende de transcript; pending effects/idempotency são first-class; safe-point handoff é preferido; Planning→Build preserva provenance sem transformar PlanningSession em Run; KnowledgeService unifica locate/get/search/related/explain/context/affected e mutação via `KnowledgeDelta`; Validate→Commit + optimistic concurrency são obrigatórios; derived rebuild ocorre por events após canonical commit. [32 — Handoff v2 e Knowledge API: Typed Continuation, Query/Write Contracts e Agent Portability](ch32.md)
- **Architecture Governance ACCEPTED:** decisões de arquitetura técnica, boundaries, state ownership, contratos internos, algoritmos, persistência, concorrência, incrementalidade, cache, lifecycle, runtime/resource management, interfaces entre subsistemas e estratégias de implementação podem ser decididas autonomamente pelo arquiteto/agent responsável, usando este caderno e o Prumo Framework como fontes canônicas. Essas decisões devem preservar invariantes aceitos, Clean Code, modularidade, segurança, performance e testabilidade, ser documentadas com rationale e evidence quando relevante e não precisam retornar ao usuário para aprovação individual. Escalar ao usuário quando houver impacto material em produto/funcionalidade, UX/UI/design/acessibilidade, escolha de ferramenta/linguagem/framework que ele queira controlar, custo/licença/privacidade relevante, remoção de capability aceita ou mudança de direção/invariant já aprovado.
- **Knowledge Runtime Semantic Model ACCEPTED:** stable semantic IDs; `SourceRecord`, `Section`, `Claim`, `Finding`, `Decision`, `Requirement`, `Constraint`, `Risk`, `Assumption`, `OpenQuestion`, `ResearchRecord`, `Evidence` e `MemoryRecord` tipados; authority/trust/freshness/status separados; lineage/supersession e relationships tipadas; canonical records simples com indexes/summaries/embeddings derivados. [33 — Knowledge Runtime Semantic Model: Records, Claims, Sources, Sections, Authority e Lineage](ch33.md)
- **Contradiction/Coverage/Readiness Engine ACCEPTED:** contradiction, coverage e readiness são engines separados; typed rules e graph relations substituem substring heuristics; Evidence é revision/freshness-aware; readiness usa policy + blockers/gates; LLMs geram candidates, nunca authority. [34 — Contradiction, Coverage & Readiness Engine: Semantic Validation, Traceability e Gates](ch34.md)
- **Harness Build Strategy ACCEPTED:** o Harness Core será Prumo-native em Go sobre as fundações atuais; não haverá fork de Goose/OpenCode/ADK/etc. como kernel. External coding agents entram por `AgentProvider`/ACP/SDK/RPC/server; reusable infrastructure entra apenas atrás de ports substituíveis. Native Agent usa state machine reentrante, FakeProvider/conformance-first e dois tracks paralelos: Native Runtime + External Connectivity. Referências oficiais de engenharia são mantidas em [02 — Referências de Harnesses, Agent Frameworks e Coding Agents](ch02.md) e a decisão completa em [35 — Harness Build Strategy: Prumo-Native Core, External Agent Providers e Selective Reuse](ch35.md).
- **Human Documentation Runtime ACCEPTED:** documentação humana é projection do Knowledge Runtime; `DocumentationSpec`, audiences, profiles, surfaces e policies `GENERATED/ASSISTED/CURATED` são first-class. README é curto; docs site é superfície principal para projetos médios/grandes; Reference é automation-first; Manual/How-to/Tutorial/Explanation permanecem intents distintos. [36 — Human Documentation Runtime: Audiences, Profiles, Surfaces e Generation Policy](ch36.md)
- **Documentation Planner ACCEPTED:** planner determinístico deriva `DocumentationUnit`, Page Graph, navigation, coverage e GenerationPlan de capabilities/contracts/audiences; gaps não são preenchidos por hallucination. Visibility filtra antes da geração. [37 — Documentation Planner: Discovery, Information Architecture, Coverage e Page Graph](ch37.md)
- **Human Docs Publishing ACCEPTED:** Markdown + manifests são renderer-neutral; **Astro Starlight** é SiteRendererAdapter default recomendado; Node/Astro rodam fora do Core Go; GitHub Pages é deploy opcional default; examples/screenshots/translations/version snapshots possuem lifecycle e quality gates próprios. [38 — Human Docs Quality, Publishing, Website Runtime, Versioning e i18n](ch38.md)
- **Chronicle/Release Documentation ACCEPTED:** Engineering Chronicle privado por default, `CHANGELOG` factual/release-scoped, Release Notes assistidas e Public Devlog allowlisted/curated são projeções distintas de semantic events/knowledge; transcript e git log não são fontes editoriais suficientes. [39 — Development Chronicle, Changelog, Release Notes e Public Devlog](ch39.md)
- **Prumo ↔ Prumo Code Repository Boundary ACCEPTED:** Harness, Native Agent, daemon, protocol e SDK permanecem em `raillen/prumo`; o futuro `raillen/prumo-code` nasce depois do headless split gate e consome apenas o Prumo Protocol/SDK público. Core, Protocol e Product possuem versionamento independente; installer pode bundle runtime compatível sem fundir ownership. [40 — Repository Boundary & Product Split: Prumo Platform vs Prumo Code](ch40.md)
- **Notebook-to-Repository Promotion ACCEPTED:** export do caderno entra como snapshot imutável de planning/provenance em `.prumo/imports/notion/...`; agent deve inventory→normalize→reconcile target architecture com implementation reality→plan→generate→validate→promote. Após promoção, repository canonical docs retomam autoridade operacional e o snapshot deixa de participar de retrieval padrão com mesma autoridade. # Open Questions atuais

- TUI e Desktop compartilham editor model por RPC ou possuem presentation-local buffers sincronizados?
- `prumo-agentd` deve nascer junto com H9 ou só quando houver segundo cliente?
- Qual subset do **ACP Client** e do **ACP Agent Server** implementar primeiro, e quais agentes do Registry entram no primeiro compatibility matrix?
- Fantasy será bootstrap adapter ou evitaremos dependency desde o início?
- Qual MCP Go SDK e quais transports entram no MVP?
- Docker ou Podman como primeiro sandbox provider? Rootless obrigatório quando disponível?
- SQLite derived runtime: modernc pure Go ou driver diferente?
- Qual terminal core vence: libghostty, wezterm-term ou implementação diferente?
- Como compartilhar LSP entre agent e editor sem lifecycle duplicado?
- Plugin code: process isolation, WASM ou múltiplos modelos por trust class?
- Quais performance budgets mínimos para o primeiro desktop e primeira TUI?
- **Local Intelligence BENCHMARKING:** quais modelos concretos vencem `embedding-default`, `tiny-worker`, `standard-worker`, `advanced-embedding` e `reranker` no corpus Prumo PT/EN/código?
- Quais thresholds medidos de RAM/VRAM/latência definem as recomendações finais de `Ultra-Light`, `Light`, `Balanced` e `Ultra`?
- Quais policies default de TTL/memory pressure/local→remote escalation e quais tasks exigem confirmação/privacy-local-only?
- Como versionar/distribuir model packages, quantizações e licenças sem acoplar os profiles a artifacts concretos?
