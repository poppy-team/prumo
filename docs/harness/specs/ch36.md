<aside>
📚

**Status: ACCEPTED.** A documentação humana do Prumo é uma projeção do mesmo Knowledge Runtime que alimenta agents/LLMs. Não existe uma segunda fonte de verdade para README, website, manual, guias, changelog ou handbooks. O que muda é audiência, intenção, densidade, linguagem e superfície de publicação.

# Objetivo

Definir quais documentos humanos o Harness pode planejar, gerar e manter para projetos de tipos diferentes, preservando provenance, revisão humana quando necessária, baixo custo de tokens e ausência de drift entre código, conhecimento canônico e documentação pública.

# Princípio central

```
Canonical Project Knowledge
        ↓
Knowledge IR
        ↓
Documentation Compiler
        ↓
Human Documentation Runtime
        ↓
Audience Projection
        ↓
Surface Renderer
        ↓
README / Docs Site / Manual / Changelog / Handbooks / Chronicle
```

A mesma `Decision`, `Requirement`, `Claim`, `Command`, `ConfigSchema`, `Evidence` ou `ReleaseRecord` pode produzir diferentes projeções sem ser duplicada como verdade.

# Audiências first-class

Vocabulário inicial:

```
end-user
new-user
developer
plugin-author
api-consumer
contributor
maintainer
operator
project-owner
community/public
```

Cada `DocumentationUnit` declara uma ou mais audiências. Audience projection controla vocabulário, pré-requisitos, profundidade, exemplos, visibilidade e links relacionados.

# Taxonomia de conteúdo

A taxonomia base segue Diátaxis porque separa necessidades cognitivas distintas:

- **Tutorial:** aprendizagem guiada e sequencial;
- **How-to:** alcançar um objetivo concreto;
- **Reference:** informação factual/autoritativa sobre a maquinaria;
- **Explanation / Concepts:** compreender por que e como conceitos se relacionam.

O Prumo adiciona tipos operacionais complementares:

- Quickstart;
- Manual/feature guide;
- Troubleshooting;
- FAQ;
- Migration Guide;
- Release Notes;
- Changelog;
- Architecture Handbook;
- Maintainer Handbook;
- Decision Book;
- Development Chronicle / Devlog.

Fontes de referência: [Diátaxis](https://www.diataxis.fr/) e [Diátaxis Start Here](https://www.diataxis.fr/start-here/).

# Surfaces

`ContentType` e `Surface` são conceitos distintos.

```
Surface
├── repository-root
│   ├── README.md
│   ├── CHANGELOG.md
│   ├── CONTRIBUTING.md
│   └── SECURITY.md optional
├── docs-tree
│   └── Markdown/MDX
├── docs-site
├── downloadable/manual bundle future
├── release page
├── public devlog/blog
└── private engineering chronicle
```

Uma página de How-to pode aparecer no docs-site e também ser exportada como Markdown puro sem mudar identidade.

# Documentation Profiles

Profiles são templates de capability e podem ser compostos.

| Profile | Artefatos principais | Uso típico |
| --- | --- | --- |
| Minimal | README, Quickstart, Changelog | pequenos projetos/utilitários |
| Library | README, Getting Started, Tutorials, How-to, API Reference, Concepts, Changelog | bibliotecas |
| CLI | README, Quickstart, CLI Reference, Config, How-to, Troubleshooting, Changelog | ferramentas de terminal |
| Desktop App | README, User Manual, Getting Started, How-to, Shortcuts, Troubleshooting, Release Notes | apps GUI |
| Framework/SDK | Tutorials, How-to, Reference, Concepts, Migration, Architecture Overview | frameworks e SDKs |
| Developer Tool | CLI, Config, Providers/Plugins, Troubleshooting, Architecture, Maintainer docs | Prumo-like |
| Full Project | todas as superfícies relevantes | produto maior/open source |
| Custom | composição explícita | controle avançado |

Profiles não congelam a árvore; o Documentation Planner deriva páginas concretas a partir de capabilities reais.

# Default para o Prumo

O próprio Prumo usa composição:

```
Developer Tool
+ Framework/SDK
+ Chronicle
```

Isso gera documentação forte para usuário de CLI/clients, integradores, autores de providers/plugins, contribuidores e mantenedores.

# README contract

README é porta de entrada, não manual completo.

Estrutura default:

```
Project name / tagline
short problem + value proposition
status / maturity
key capabilities
installation
2-minute quickstart
minimal example
links to full docs
contributing
support/security links
license
```

README usa conteúdo curto e links; detalhes longos vivem no docs site.

# Docs Website contract

O site é a superfície humana principal quando profile possui documentação substancial.

Estrutura conceitual default:

```
Home
Getting Started
Tutorials
How-to Guides
Concepts
Reference
Troubleshooting
Releases / Migration
Developer / Maintainer area when applicable
```

A navegação concreta é gerada pelo Documentation Planner, não por template fixo.

# Quickstart vs Tutorial vs How-to

- **Quickstart:** menor caminho reproduzível para ver o produto funcionar; idealmente 2–10 minutos.
- **Tutorial:** experiência de aprendizagem controlada, incremental, com resultado previsível; não deve carregar longas explicações conceituais.
- **How-to:** solução direta de uma tarefa real para usuário já minimamente competente.

Misturar essas três intenções na mesma página é considerado smell de documentação.

# Reference — automation-first

Reference é a superfície que mais deve aproveitar geração determinística.

Fontes candidatas:

```
Command Registry → CLI Reference
JSON Schema → Config Reference
API/IDL/OpenAPI → API Reference
Plugin contracts → Plugin Reference
Provider Registry → Provider Reference
Error Registry → Error Reference
Keybinding Registry → Shortcut Reference
File-format schemas → Format Reference
```

A LLM não deve reescrever fatos estruturados quando um renderer determinístico consegue descrevê-los.

# Explanation / Concepts

Explanation deriva de Decisions, rationale, Architecture, Research e Claims aceitos.

A LLM pode produzir prosa humana, mas deve receber refs canônicas e retornar provenance. Ela não cria a decisão que está explicando.

# User Manual

Manual é feature/workspace-oriented e especialmente útil para Desktop Apps.

Exemplo de estrutura derivada:

```
Interface
Projects
Workspaces
Core workflows
Tools/features
Settings
Shortcuts
Import/Export
Plugins/Extensions
Accessibility
Troubleshooting
```

Manual não substitui How-to: manual descreve superfícies e workflows; How-to responde objetivos específicos.

# Troubleshooting first-class

Entidade derivada/canônica candidata:

```
TroubleshootingCase
├── id
├── symptom
├── affected versions/platforms
├── likely causes[]
├── diagnostic steps[]
├── solutions[]
├── related error codes[]
├── evidence/provenance
└── status/freshness
```

Knowledge Harvest pode sugerir casos a partir de failures recorrentes, mas publicar solução exige evidence suficiente.

# FAQ

FAQ não deve virar depósito de documentação mal localizada. Criar item somente quando a pergunta é realmente recorrente ou útil como porta de navegação; preferir linkar a How-to/Reference/Explanation authoritative.

# Architecture Handbook

Conteúdo operacional do projeto:


# Decision Book

Projection do Decision Ledger:

```
Decision
Status
Context
Alternatives
Chosen
Rationale
Consequences
Revisit triggers
Supersession lineage
```

Pode gerar ADRs individuais e um índice/livro consolidado.

# Roadmap projection

Roadmap humano é opcional e visibility-aware.

```
Internal roadmap → detalhado
Public roadmap → Now / Next / Later ou milestones permitidos
```

Nada marcado private/internal é publicado por inferência.

# Generation ownership levels

Todo artifact/section declara policy:

```
GENERATED
→ Prumo pode regenerar automaticamente a partir de fontes estruturadas.

ASSISTED
→ Prumo gera/atualiza proposta e diff; publicação depende da policy/review.

CURATED
→ conteúdo humano é authoritative; Prumo pode sugerir, mas não sobrescreve.
```

Defaults:

- CLI/API/config/reference/indexes: GENERATED;
- tutorials/how-to/manual/explanations/release notes: ASSISTED;
- positioning/philosophy/public roadmap/security-sensitive prose: CURATED ou explicitamente approved.

# Source-of-truth invariant

```
Human docs are projections.
Knowledge records/contracts/code-derived schemas remain truth.
```

Manual edit em conteúdo GENERATED vira conflict/review ou override explícito; nunca altera silenciosamente uma Decision/Requirement.

# Content identity

Cada unidade humana tem stable ID independente de path/título:

```
DocumentationUnit
├── id
├── intent/content_type
├── audience[]
├── subject_refs[]
├── visibility
├── ownership_policy
├── locale
├── version scope
├── source digests[]
├── content digest
└── lifecycle status
```

Rename/move não cria uma nova unidade semanticamente.

# Invariantes fechados

- Human docs e LLM docs compartilham Knowledge Runtime;
- Diátaxis orienta intent, não impõe stack/site;
- README é curto e navega para docs completas;
- website é superfície principal para projetos médios/grandes;
- Reference é automation-first;
- prosa semântica é provenance-backed;
- Profiles são capability templates, não árvores rígidas;
- GENERATED/ASSISTED/CURATED são first-class;
- private/public são policies explícitas;
- mesma verdade pode ter projeções por audiência sem duplicar canonical state.
