# Separação arquitetural

```
Prumo
├── Workforce Runtime
│   └── multi-agent, roles, delegation, diversity, budgets, worktrees
├── Model Gateway / Routing Runtime
│   └── provider pools, routes, health, quota, retry, fallback, load balancing, proxy
└── Handoff Runtime
    └── checkpoint, agent replacement, session migration e failure recovery
```

**Multi-agent heterogêneo != model routing/fallback.** Um resolve composição/orquestração de agentes; o outro resolve seleção resiliente de targets de modelo/provider.

# Workforce Runtime

Um Run pode trabalhar com agentes, modelos, runtimes e providers diferentes ao mesmo tempo.

```
Run
├── Primary Agent
├── Planner
├── Researcher
├── Implementer
├── Tester
├── Reviewer
└── Docs
```

Cada role pode apontar para um runtime externo, Prumo Native Agent, provider profile, modelo concreto ou ModelRoute.

## AgentBinding

```
AgentBinding

```

## Modos

- `off` — um agente, nenhuma composição automática;
- `manual` — usuário escolhe agents/roles;
- `suggested` — Prumo sugere delegações e usuário aprova;
- `automatic` — Workforce pode delegar automaticamente dentro de budgets/policies explícitos.

Default inicial recomendado: **manual/suggested**. Automatic é opt-in.

## Workforce Profiles

Perfis candidatos: `Solo`, `Pair`, `Balanced`, `Full` e customizados pelo usuário. São templates de roles/bindings, não comportamento hard-coded.

## Provider/model diversity

Policies podem exigir ou preferir diversidade em revisão, por exemplo `different_model = true` e `different_provider = preferred`, reduzindo correlação entre implementador e reviewer.

# Model Gateway

`ModelGateway` é uma interface interna para routing e resiliência de chamadas de modelo. Agents que controlamos podem pedir um alias lógico em vez de um modelo físico.

```
Prumo Native Agent
      ↓
ModelRoute: prumo/coding
      ↓
Target A → Target B → Target C
```

Runtimes externos como Codex/Antigravity não são forçados através do Gateway quando seu runtime oficial possui o agent loop e auth próprios.

# ModelRoute

Uma Route descreve um conjunto ordenado ou policy-driven de `RouteTarget`s.

Exemplo:

```
premium-coding
1. provider-profile-A / model-X
2. provider-profile-B / model-Y
3. provider-profile-C / model-Z
```

A Route pode filtrar/ordenar por capabilities, availability, quota, cost, latency, throughput, context, privacy, health, quality score, task type e provider preference.

# RoutingPolicy

Estratégias candidatas:

- `priority`;
- `weighted`;
- `least_cost`;
- `least_latency`;
- `quality`;
- `quota_first`;
- `capability`;
- `sticky` por Session/Run;
- `manual`.

Policies são configuráveis e combináveis apenas quando a semântica permanecer previsível/auditável.

# FallbackPolicy

Fallback transparente é permitido somente antes de efeitos observáveis relevantes.

## Request fallback

Seguro para: timeout antes de output, provider unavailable, quota/rate-limit, transport failure e 5xx sem side effect.

## Turn fallback

Pode ocorrer após texto parcial se nenhum side effect aconteceu, mas deve registrar mudança de target na Timeline.

## Handoff

Depois de tool calls, file edits, processos ou outros efeitos observáveis, a mudança deixa de ser fallback e vira **Agent Handoff explícito**.

> Nunca esconder mudança de modelo/agente depois de efeitos observáveis.
> 

# Handoff Runtime

```
Agent A
→ side effects
→ failure/quota/outage
→ checkpoint
→ state/context summary
→ Agent B
→ continue same Run
```

Handoff deve preservar Goal, Plan, Tasks, current diff, Evidence, relevant Context, pending permissions e workspace state, sem depender de memória privada do modelo anterior.

Policies: stop-and-ask, retry-same-agent, automatic-handoff, handoff-only-on-outage/quota.

# Health e Circuit Breaker

Cada target/profile mantém `ProviderHealth` e circuit state: `closed`, `open`, `half_open`. Falhas repetidas podem colocar target em cooldown e impedir requests inúteis até probe/recovery.

# QuotaState

Quota pode ser `known`, `estimated`, `unknown` ou `exhausted/cooldown`. Nunca inventar saldo quando vendor não o expõe; 429/quota errors podem apenas atualizar health/cooldown inferido.

# AccountPool

Múltiplos ProviderProfiles do mesmo provider podem formar um pool com priority, round-robin, weighted ou quota-aware policy, sempre respeitando termos, budgets e ownership de credenciais.

# Proxy Server opcional

O mesmo ModelGateway pode ser exposto opcionalmente por um `Prumo Proxy Server`, inicialmente OpenAI-compatible e posteriormente outros dialects quando útil.

```
External client
→ Prumo Proxy
→ ModelGateway
→ Routes / Providers
```

O Prumo Code interno **não depende** do proxy HTTP; ambos consomem o mesmo ModelGateway application service.

# Segurança e subscription runtimes

API/model providers podem participar do Gateway. Credenciais de subscriptions/runtimes oficiais como Codex, Antigravity ou Claude Code permanecem sob seus AgentProviders oficiais, salvo suporte explícito do fornecedor para exposição genérica. Não transformar OAuth privado em API genérica por scraping/replay.

# Invariantes

- todos os recursos são opcionais;
- um usuário pode operar com um único Agent sem Gateway;
- Gateway nunca altera comportamento pós-side-effect silenciosamente;
- decisions de routing/handoff entram na Timeline;
- budgets são aplicados por Run, AgentRole, Route e provider quando configurado;
- nenhuma UI conhece regras específicas de vendor.
