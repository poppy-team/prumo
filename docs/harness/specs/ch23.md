# Project, Workspace e Worktree

```
Project
└── configuração lógica do projeto

Workspace
└── ambiente de trabalho atualmente aberto

Worktree
└── checkout Git físico/isolado
```

Workspace pode apontar para Worktree, mas não são equivalentes. Multi-agent deve poder criar Workspaces/Worktrees isolados sem duplicar Project.

# Goal, Plan, Task e Run

```
Goal
└── Plan
    ├── Task
    ├── Task
    └── Task
```

`Run` representa **uma execução observável do Prumo**, não apenas filho de Task. Pode existir para implementação, review, research, maintenance, tests ou outras execuções.

## Run como entidade central

```
Run
├── goal
├── task
├── workspace
├── agents[]
├── sessions[]
├── changes[]
├── evidence[]
├── gates[]
├── context
├── budget
├── timeline
└── status
```

Estados mínimos candidatos: `queued`, `starting`, `running`, `waiting_user`, `waiting_permission`, `waiting_dependency`, `paused`, `completed`, `failed`, `cancelled`.

# Thread, Session, Turn e Message

- **Thread:** conversa lógica apresentada ao usuário;
- **Session:** sessão concreta com um `AgentProvider`/runtime;
- **Turn:** uma rodada de interação;
- **Message:** unidade de conteúdo.

Um Thread pode sobreviver à troca de Agent/Provider e conter múltiplas Sessions.

# Provider, ProviderProfile, Agent e Session

```
Provider
→ organização/runtime family

ProviderProfile
→ conta/perfil concreto, ex. Personal/Work/Local

Agent
→ Codex, Antigravity, Gemini CLI, Prumo Native, custom agent

Session
→ instância concreta daquele Agent
```

Nunca hard-code comportamento por vendor quando capability negotiation puder resolver.

# Agent capabilities

Capabilities devem ser dinâmicas e negociadas por conexão/session, por exemplo: `streaming`, `resume`, `tools`, `file_edit`, `permissions`, `subagents`, `reasoning_summary`, `images`, `terminal`, `structured_output`, `usage`, `cost`.

# Context como entidade first-class

`Context` não é apenas contagem de tokens. Deve carregar `ContextItem`s com source, reason, priority, token estimate, pinned state e lifecycle.

Tipos de item candidatos: file, symbol, diff, diagnostic, doc, run, message, tool result, artifact, memory e attachment.

# Budget como entidade first-class

Budget deve poder limitar money, tokens, time, tool calls, retries e concurrency. Cada dimensão pode ter `soft_limit`, `hard_limit`, `used`, `reserved` e `remaining`.

# Execution domain

- `Tool` = capability disponível;
- `ToolCall` = execução concreta;
- `Process` = processo do sistema;
- `TerminalSession` = stream interativo associado a um ou mais processos;
- `PermissionRequest` = decisão pendente.

**TerminalSession != Process.**

# Review domain

- `Change` = intenção lógica de alteração;
- `Patch` = representação aplicável;
- `Diff` = representação da diferença;
- `Evidence` = prova produzida;
- `Gate` = condição de aceitação;
- `Diagnostic` = problema/sinal técnico estruturado.

# Product capability classes

| Classe | Regra |
| --- | --- |
| Core capability | deve existir em Desktop e TUI |
| Equivalent workflow | resultado equivalente; UX pode diferir |
| Surface-specific | pertence somente a uma superfície |

Exemplo: review diff é Core; Desktop pode usar side-by-side rich diff e TUI inline/unified. Drag-and-drop é Desktop-specific; SSH TUI é TUI-specific.

# Command model

```
Command
├── id
├── target
├── args
├── source
└── metadata
```

Command é intenção do usuário, não contém business logic.

# Command → Action → Event

```
User
↓
Command
↓
Application Service
↓
Action
↓
Domain mutation
↓
DomainEvent / AgentEvent
↓
Clients
```

Exemplo: `permission.approve` → `ApprovePermission` → `PermissionApproved` → agent resumes por regra de domínio, não por chamada direta da UI.

# Eventos canônicos

## DomainEvent

Exemplos: `RunStarted`, `RunPaused`, `TaskCompleted`, `PatchAccepted`, `EvidenceAdded`, `GatePassed`, `PermissionApproved`.

## AgentEvent

Exemplos: `AgentTextDelta`, `ToolStarted`, `ToolFinished`, `SubagentStarted`, `UsageUpdated`.

As categorias podem compartilhar o mesmo event stream sem perder semântica.

# Command context

Commands podem declarar regras de `available_when`, `enabled_when` e `visible_when`. Desktop e TUI compartilham a semântica, mesmo com apresentação diferente.

# Selection e Inspector

`Selection` é client-local e aponta para a entidade atualmente selecionada, como Project, Run, Thread, File, Diff, Agent, ToolCall ou Evidence. `Inspector` é um padrão contextual que deriva suas informações e ações da Selection; não é entidade canônica do Harness.

# State ownership em três níveis

| Estado | Exemplos | Owner |
| --- | --- | --- |
| Canonical Domain State | Run, Task, Agent, Evidence, Diff, Budget | Harness |
| Portable Workspace State | active Run, workspace mode, open documents, attached terminals | Harness/profile sincronizável |
| Ephemeral Presentation State | scroll, hover, animation, popup, split pixel/cell size | Client |

Nenhum estado específico de Floem/Bubble Tea pode contaminar contratos do Harness.

# Capability negotiation em três camadas

- **Product Capability:** o Prumo suporta o conceito;
- **Agent Capability:** a sessão/runtime suporta a operação;
- **Client Capability:** a superfície consegue representá-la daquela forma.

Exemplo: Product suporta Review; Agent pode não suportar file edits; TUI pode suportar somente inline diff enquanto Desktop suporta side-by-side.

# Notifications

Notification é entidade/evento derivado para activity assíncrona: Run finished, approval requested, test failed, agent needs input, budget warning, provider disconnected e conflict detected. Desktop e TUI podem renderizar de formas distintas.

# Invariantes aceitos

1. `Run` é a entidade central de execução.
2. `Thread`, `Session`, `Turn` e `Message` são distintos.
3. `Provider`, `ProviderProfile`, `Agent` e `Session` são distintos.
4. `Goal`, `Plan`, `Task` e `Run` são distintos.
5. `Change`, `Patch`, `Diff`, `Evidence` e `Gate` são distintos.
6. `TerminalSession` é diferente de `Process`.
7. State ownership possui Canonical, Portable e Ephemeral.
8. Commands são compartilhados por GUI/TUI/CLI/plugins.
9. O fluxo é Command → Action → Event.
10. Capability negotiation ocorre em Product, Agent e Client.
11. Selection/Inspector é o padrão contextual de apresentação.
12. Toda funcionalidade importante deve ser acessível via Command Registry.
