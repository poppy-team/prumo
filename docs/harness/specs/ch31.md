<aside>
🧠

**Status: ACCEPTED.** O Context Compiler v2 será um pipeline **determinístico-first, budget-aware e provenance-aware**. Ele combina retrieval lexical, semantic e graph-based, mas nenhuma LLM decide o contexto por padrão. Ranking, filtros, diversity e packing são reproduzíveis e auditáveis; modelos locais/remotos entram apenas como optional reranker/query-rewrite quando benchmarks justificarem.

</aside>

# Objetivo

Entregar a cada Agent/Knowledge Task o **menor contexto suficiente** para resolver a tarefa, respeitando authority, freshness, privacy, dependencies e token budget.

# Pipeline canônico

```

  ↓

  ↓
Mandatory / pinned resolution
  ↓
Authority / trust / privacy gate
  ↓
Freshness gate
  ↓

  ├── FTS5 / BM25
  ├── embeddings optional

  ↓

  ↓

  ↓

  ↓
```

# Authority é gate, não feature fraca de score

Não misturar uma fonte não confiável com uma fonte canônica simplesmente porque a primeira tem maior semantic similarity.

Ordem:

```
policy eligibility
→ authority/trust gate
→ freshness validity
→ relevance ranking
```

Classes candidatas:

```
canonical
accepted-decision
validated-project-knowledge
trusted-reference
research-evidence
derived-summary
external-data
untrusted-data
```

A ordenação é enum/rank tipado, nunca comparação lexical de strings.

# Freshness

Classes:

```
static
slow
medium
fast
realtime
```

Estados derivados:

```
fresh
review_due
stale
expired
unknown
```

`expired` não entra automaticamente como resposta factual quando freshness for requisito; pode entrar como `search_seed` ou historical context com reason explícito.

# Candidate retrieval

## Structured/exact first

IDs, SectionID, ClaimID, DecisionID, Task/Run/Artifact refs e explicit links vencem fuzzy retrieval quando presentes.

## Lexical

SQLite FTS5/BM25 é baseline sempre disponível e funciona em `No-LLM`.

## Semantic

Embeddings são camada derivada opcional. Granite default quando instalado; advanced encoder só quando policy/benchmark justificar.

## Graph

Expandir relações tipadas com depth pequeno e budget explícito:

```
Decision → requirement / evidence / architecture section
Claim → provenance / supersession
Task → files / diagnostics / evidence
Run → changes / tests / decisions
```

Graph expansion não significa caminhar indiscriminadamente pelo atlas.

# Rank fusion

Para combinar listas BM25, vector e outras listas com scores incomparáveis, usar **Reciprocal Rank Fusion (RRF)** como baseline.

```
RRF(d) = Σ 1 / (k + rank_i(d))
```

Default inicial candidato `k=60`, versionável e benchmarkado. RRF é escolhido porque usa posição e não exige normalizar BM25/cosine/graph scores para uma escala comum.

Weighted RRF pode ser adicionado quando evals mostrarem valor, mas os pesos são policy/eval-driven.

# Hard boosts / reason codes

Após fusion, aplicar somente ajustes explícitos e auditáveis:

- exact entity/section match;
- same Project/Run/Task scope;
- pinned/mandatory handled separately;
- direct graph dependency;
- accepted Decision backing a selected requirement;
- user-selected item.

Não criar uma fórmula opaca com dezenas de coeficientes no MVP.

# Optional reranker

Reranker trabalha **apenas no top-K pequeno** após hybrid retrieval, por exemplo 20–50 candidates.

Regras:

- desabilitado em `No-LLM`/`Ultra-Light` por default;
- precisa provar nDCG/context quality gain;
- nunca consegue furar authority/privacy/freshness gates;
- output apenas reordena eligible candidates;
- se indisponível, RRF continua sendo caminho completo.

# Diversity / redundancy

Usar **Maximal Marginal Relevance (MMR)** como baseline simples para evitar contexto duplicado:

```
MMR = λ * relevance - (1-λ) * max_similarity(selected, candidate)
```

Aplicar depois de relevance fusion, antes do packing, principalmente a summaries/research/docs semanticamente redundantes.

`λ` é benchmark-driven; default inicial candidato favorece relevance (ex. ~0.7–0.8), não hard-coded como invariant.

Para records com stable semantic digest ou lineage conhecido, deduplicação determinística ocorre antes de MMR.

# Coverage constraints

Diversity não pode remover evidência necessária.

Context request pode declarar coverage requirements:

```
requires:
- active requirement
- current accepted decision
- changed code
- failing diagnostic
```

Packing deve preservar ao menos um item elegível por mandatory coverage class quando disponível.

# Dependency completion

Se um item selecionado exige dependency explícita para interpretação correta, o compiler tenta incluir dependency compacta antes de aceitar o item.

Exemplo:

```
Diff
→ Requirement summary
→ accepted Decision affecting public API
```

Se a dependency não cabe, o item pode ser reduzido/comprimido ou removido; manifest explica o motivo.

# Budget packing

Não usar full knapsack/ILP no MVP. Baseline determinístico e rápido:

1. inserir mandatory/pinned;
2. reservar minimum coverage budget;
3. ordenar candidates por marginal utility/token;
4. greedy select respeitando dependencies/diversity;
5. tentar compact representation quando full record não cabe;
6. parar ao atingir budget/safety margin.

Utility considera ranking fusion + explicit boosts + coverage gain - redundancy penalty.

# Score-per-token

Itens grandes competem com summaries menores:

```
utility_per_token = marginal_utility / estimated_tokens
```

Mas estabelecer floor para high-authority/critical evidence evita penalizar documentos essenciais apenas por serem maiores.

# Progressive disclosure levels

```
L0 pointer
L1 atlas/catalog line
L2 compact summary
L3 focused section/record
L4 full source
```

O compiler escolhe o menor nível que satisfaz a necessidade. Fetch de L4 é exceção, não padrão.

# Chunking

Prioridade:

1. stable semantic sections/IDs;
2. AST blocks / symbols;
3. paragraph/window fallback.

Evitar fixed-token chunks como identidade canônica. Token windows são derived retrieval units e apontam para SectionID/source range.

Código usa symbol/function/type boundaries quando disponíveis via parser/LSP/Tree-sitter.

# Pressure states

Context pressure e system memory pressure são domínios diferentes.

```
healthy
pressure
compact
critical
```

`compact` passa a ter semântica formal no Context Compiler v2, resolvendo o drift encontrado entre schema e runtime antigo.

## healthy

budget folgado; summaries/sections normais.

## pressure

mais L1/L2, reduz graph expansion e top-K.

## compact

somente mandatory + high utility compact representations + recent task state.

## critical

mínimo seguro para continuar; pode solicitar compaction/handoff ou recusar task se dependencies essenciais não couberem.

# Query rewrite

Determinístico primeiro:

- entity normalization;
- aliases known from registry;
- symbol/path tokens;
- domain tags;
- stemming/tokenization do FTS.

Tiny local LLM pode sugerir semantic query rewrites no `Light+`, mas rewrites são adicionais; query original sempre participa do retrieval e proposals não alteram authority.

# Search seed / stale research

Quando research está stale:

```
old ResearchRecord
→ use compact findings/keywords/source refs as search seed
→ external refresh
→ new ResearchRecord
```

O record stale pode aparecer no context como historical rationale, claramente marcado.

# Privacy

Filtro de privacy ocorre antes de semantic/vector candidate exposure.

Indexes devem ser partitionable por scope:

```
public
personal
project-private
workspace-sensitive
```

Cross-project retrieval nunca mistura escopos incompatíveis.

# Multi-agent context

Agents não recebem automaticamente o mesmo pack.

```
Planner → decisions + requirements + research
Coder → relevant code + requirements + diagnostics
Reviewer → diff + requirements + evidence + selected decisions
Tester → changed APIs + requirements + tests/evidence
Docs worker → public changes + accepted decisions
```

Context Manifest registra role/policy.

# Caching

Cachear:

- query fingerprint → candidate IDs/ranks enquanto indexes/source revisions não mudarem;
- embeddings por semantic digest;
- compact summaries por record digest + summarizer version;
- graph neighborhoods por graph revision;
- token estimates por tokenizer/version.

Cache nunca substitui freshness validation.

# Incremental invalidation

Context indexes dependem de Knowledge/Document semantic digests. Mudança em uma section invalida apenas:

- lexical row/chunks daquela section;
- embedding daquela projection;
- affected graph edges;
- query cache entries que dependiam do digest/revision quando rastreável.

# Determinism / replay

Com mesmos:

```
query/task
source revision
indexes
policy version
model-free retrieval mode
budget
```

compiler produz o mesmo manifest/order.

Se reranker/model rewrite estiver ligado, registrar model/package/version/seed/config e marcar result como probabilistic-assist; baseline deterministic retrieval continua disponível para replay comparison.

# Evals

Medir pelo que **chega no contexto**, não só retrieval recall:

- context precision;
- required-evidence survival;
- answer/evidence-in-context;
- tokens per useful item;
- duplicate token ratio;
- authority violation rate;
- stale-use rate;
- privacy leakage = zero;
- dependency completeness;
- context stability under irrelevant corpus growth;
- downstream task quality;
- latency.

Comparar camadas:

```
A BM25 only
B BM25 + graph
C + Granite + RRF
D + MMR
E + reranker
F + advanced embedding
```

Cada camada só vira default se justificar custo/complexidade.

# Relação com Local Intelligence Profiles

- `No-LLM`: structured + BM25 + graph + RRF sobre listas disponíveis + deterministic diversity/dedup.
- `Ultra-Light`: adiciona Granite semantic list ao RRF.
- `Light`: query rewrite/classification assist optional.
- `Balanced`: standard local rerank/synthesis assist quando policy pede.
- `Ultra`: advanced embedding/reranker candidatos.

A semântica do Context Compiler permanece igual em todos.

# Decisões arquiteturais fechadas

- authority/trust/freshness/privacy são eligibility gates antes de relevance;
- structured/exact retrieval precede fuzzy;
- FTS5/BM25 baseline obrigatório;
- embeddings opcionais/derivados;
- RRF baseline para hybrid fusion;
- MMR baseline para anti-redundancy;
- greedy marginal-utility-per-token packing em vez de optimizer complexo no MVP;
- progressive disclosure L0–L4;
- dependencies/coverage são constraints, não simples score;
- Context Manifest v2 first-class/replayable;
- `compact` formalizado como pressure state;
- LLM rerank/query rewrite são optional assists, nunca authority.

# Ainda benchmark-driven

- RRF k/weights;
- MMR λ;
- candidate top-K;
- graph expansion depth;
- budget safety margin;
- reranker enablement;
- advanced embedding usefulness;
- thresholds por pressure state.
