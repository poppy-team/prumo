<aside>
🧱

**Status: ACCEPTED architectural direction.** O Prumo **não será um fork de Goose, OpenCode, Letta, Pydantic AI Harness ou outro harness completo**. O Harness Core será Prumo-native em Go, construído sobre as fundações já existentes do repositório. Harnesses externos serão integrados como `AgentProvider`/ACP/SDK/server adapters, e frameworks/bibliotecas externas serão reutilizados seletivamente onde não competirem com o domínio canônico do Prumo.

# Decisão resumida

```
DO NOT:
Fork a complete coding agent and bend Prumo around its state model.

DO:
Prumo-owned control plane + resumable native agent loop
+ official provider/protocol SDKs
+ external AgentProviders for mature harnesses
+ selective small-library reuse.
```

# Por que não partir de um fork completo

O diferencial do Prumo está justamente nas áreas que harnesses completos normalmente querem possuir:

- Run/Goal/Task semantics;
- state ownership;
- Context Compiler;
- permissions/egress;
- sandbox/workspaces;
- evidence/gates/readiness;
- Planning/Knowledge Runtime;
- Handoff;
- budgets;
- provider/agent separation;
- multi-agent/workforce;
- timeline/observability;
- deterministic documentation/memory.

Um fork importaria outro `Session`, outro `Agent`, outro persistence model, outro permission model e outro event model. A adaptação logo se tornaria uma reescrita distribuída dentro de um código que não controlamos semanticamente.

# Two execution paths

## Native path

Prumo owns:

- context compilation;
- model call;
- tool loop;
- permissions;
- retries;
- compaction;
- checkpointing;
- evidence lifecycle;
- model routing.

## External agent path

External runtime owns its own model/tool/session loop. Prumo owns:

- Run/Goal/Task;
- workspace allocation;
- global budgets/policies;
- normalized events;
- review/evidence/gates;
- Handoff;
- Knowledge Runtime;
- provider lifecycle/health.

Nunca executar um external agent “dentro” do Native Agent loop fingindo que ele é apenas um ModelProvider.

# Native agent loop: re-entrant state machine

O Native Agent Runtime não será uma coroutine monolítica `while model wants tools`. Usar uma **state machine reentrante/unrolled**.

```
AgentStep
├── Prepare
├── CompileContext
├── RequestModel
├── ConsumeModelEvent
├── PlanToolCalls
├── PermissionCheck
├── ExecuteTool
├── RecordObservation
├── EvaluateStop/Quality
├── Checkpoint
└── Yield / Continue / Complete
```

Cada boundary relevante pode persistir state/event e retornar controle ao scheduler.

Benefícios:

- crash/resume natural;
- Handoff entre processos/providers;
- deterministic tests por step;
- cancellation/steering em safe points;
- durable execution sem stack/coroutine suspensa;
- background scheduling;
- replay/evals;
- fácil integração futura com daemon/queue.

# Canonical NativeAgentState

```
NativeAgentState
├── run_id
├── session_id
├── turn_id
├── phase
├── conversation/message refs
├── context_manifest_id
├── model_route / active model connection
├── pending model request optional
├── pending tool calls[]
├── pending permission refs[]
├── observations[] refs
├── checkpoint_id
├── budget snapshot
├── stop conditions
└── revision
```

Provider-private reasoning/state nunca é required canonical state.

# Ports of the Native Agent Runtime


# ModelProvider boundary

`ModelProvider` é transporte/inference, não agent semantics.

Contrato deve cobrir:

```
Capabilities
Models
Create/prepare request
Stream
Cancel
Usage
Health
```

Normalized model events:

```
TextDelta
ReasoningSummaryDelta when provider exposes safe summary
ToolCallDelta / ToolCallReady
UsageUpdated
Warning
Error

```

Vendor message types não escapam do adapter.

# AgentProvider boundary

External Agent Runtime contract permanece conforme Agent Connectivity Runtime:

```
Discover / Status / Authenticate / Capabilities / Models
CreateSession / ResumeSession
Send / Cancel
Approve / Deny
Events
Close
```

Codex/OpenCode/Goose/etc. podem fornecer valor antes que Native Agent tenha paridade completa.

# Bootstrap strategy

O desenvolvimento pode entregar valor cedo em duas linhas paralelas:

```
Track A — External Agent Connectivity
ACP / Codex app-server / OpenCode server / structured CLIs

Track B — Prumo Native Agent
minimal ModelProvider + unrolled loop + ACI
```

Track A reduz pressão para reimplementar imediatamente cada capability avançada de coding agents maduros. Track B constrói nossa independência e diferenciação gradualmente.

# Selective reuse policy

## Reutilizar como dependência quando

- boundary é infraestrutura genérica;
- API é pequena/estável;
- licença compatível;
- não possui product/session ownership;
- substituição futura é possível atrás de interface Prumo.

Exemplos:

- official model SDKs;
- official MCP Go SDK;
- JSON Schema validator;
- diff/parser libraries;
- LSP/DAP protocol libraries;
- SQLite driver;
- transport/IPC libs.

## Usar como referência/spike, não como dependency central

- full agent frameworks;
- coding-agent products;
- workflow engines que trazem seu próprio canonical state;
- memory systems com ontology concorrente.

# Google ADK Go

É o candidato mais plausível se fôssemos obrigados a escolher um framework-base porque:

- Go idiomático;
- Apache-2.0;
- multi-agent;
- graph workflows;
- parallel/loop primitives;
- HITL tool confirmation;
- MCP examples;
- model-agnostic embora otimizado para Gemini.

Ainda assim, ele traz `Runner`, `Session`, event/session schemas e orchestration semantics que sobrepõem exatamente o domínio que o Prumo já definiu. Adotá-lo como kernel economizaria loop inicial e cobraria adaptação contínua no longo prazo.

Decision: **não usar como kernel**. Pode entrar em `labs/`/spike e eventualmente como adapter/provider especializado.

# Goose/OpenCode/Letta/Pydantic

Esses projetos provam que nosso desenho é viável e oferecem referências úteis, mas são produtos/frameworks em Rust/TypeScript/Python com state models próprios. Forkar um deles também faria a migração Python→Go do Prumo perder sentido arquitetural.

# What to borrow from existing harnesses

Borrow **ideas/contracts**, not ownership:

- Goose: unrolled loop, security inspectors, ACP separation, extensions;
- OpenCode: headless server + generated SDK, plan/build distinction, client/server model;
- Letta: context/memory visibility, memory eval methodology;
- Pydantic AI: capability composition and durable-boundary discipline;
- Google ADK: Go API ergonomics, tool confirmation, graph/multi-agent patterns;
- small Go harnesses: minimal runner/provider/tool event API patterns.

# Build-vs-buy invariant

Se uma external runtime capability puder ser consumida por ACP/SDK/RPC sem comprometer Prumo semantics, **integrate instead of reimplementing immediately**.

Se a capability define Prumo's canonical product behavior, **own it**.

# Complexity assessment

Escala 1–10 de dificuldade de engenharia, considerando estado atual do Prumo e não um projeto vazio.

| Entrega | Dificuldade | Principal risco |
| --- | --- | --- |
| Minimal native model→tool loop | 4/10 | stream normalization/tool protocol edge cases |
| Single-agent production baseline | 7/10 | durability, cancellation, permissions, side effects, provider quirks |
| Robust sandboxed coding ACI | 8/10 | cross-platform process/fs/security semantics |
| Multi-provider Model Gateway | 7/10 | capability mismatch, retry/fallback semantics, auth/quotas |
| External AgentProvider matrix | 7/10 | different session/permission/event semantics |
| Multi-agent/worktree orchestration | 8/10 | concurrency, ownership, conflicts, budgets |
| Crash-safe Handoff + replay | 8/10 | pending side effects/idempotency |
| Full Prumo vision | 9/10 | integration complexity rather than any single algorithm |

# Why this remains feasible

A maioria dos itens difíceis já possui contracts/foundations no Prumo. O trabalho é incremental e conformance-driven. Não precisamos alcançar paridade com Claude Code/Codex antes de usar o produto, porque external AgentProviders oferecem uma ponte.

# Implementation sequence

```
HA0 Agent Runtime contracts + normalized events
HA1 one ModelProvider + deterministic fake provider
HA2 unrolled NativeAgent state machine
HA3 ToolGateway/Permission integration
HA4 checkpoint/resume + budgets + observability
HA5 coding ACI + Environment/Sandbox
HA6 second ModelProvider + Model Gateway/fallback
HA7 first external AgentProvider (Codex/OpenCode/ACP)
HA8 Handoff cross-provider dogfood
HA9 Context Compiler v2 / Knowledge integration
HA10 multi-agent/worktrees
HA11 compatibility/eval matrix
```

External connectivity may start alongside HA1–HA4.

# Conformance-first testing

Antes de provider real, fake scripted provider deve cobrir:

- text completion;
- one/multiple tool calls;
- streaming partial tool args;
- provider error before side effect;
- cancellation mid-stream;
- retryable/non-retryable failure;
- malformed structured output;
- usage updates;
- context overflow;
- permission wait;
- crash/resume boundaries.

Cada real provider executa o mesmo contract suite.

# Dependency policy

`go.mod` deve continuar enxuto. Não adotar framework de agent como transitively central dependency. Provider/protocol packages entram em adapters; Core domain packages permanecem testáveis com stdlib/fakes.

# Revisit triggers

Reavaliar uso de um harness/library como kernel somente se surgir opção Go que:

- seja explicitamente embeddable;
- permita host-owned Run/Session/state;
- não imponha memory/context ontology;
- tenha mature provider/tool event contracts;
- suporte resumable/unrolled execution;
- tenha licença permissiva;
- reduza implementação materialmente sem exigir tradução constante.

Mesmo nesse caso, esconder atrás de Prumo ports e testar substituibilidade.

# Repository/product boundary

A estratégia de repositórios está fechada em [40 — Repository Boundary & Product Split: Prumo Platform vs Prumo Code](ch40.md).

O Harness, Native Agent, daemon, protocol e SDK permanecem em `raillen/prumo`. O futuro `raillen/prumo-code` nasce apenas após o split gate HA0–HA5/headless protocol e funciona exclusivamente como consumidor do protocolo público — nunca de `internal/`.

Esse novo repositório será também um **architecture conformance test**: se um cliente completo não puder ser construído sem atravessar a boundary pública, corrigir o Prumo Protocol antes de permitir acoplamento.
