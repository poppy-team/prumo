# 33 — Knowledge Runtime Semantic Model: Records, Claims, Sources, Sections, Authority e Lineage

> Authority: canonical specification.
> Logical ID: PART2-CH-33
> Source: Notion Living Book (3d89bb7d023f8121b1dbda9852cb01ba)
> Status: Especificação especializada do Harness / Code Agent (Capítulo 33).


<aside>
🧬

**Status: ACCEPTED.** O Knowledge Runtime usa um modelo semântico tipado, versionado e provenance-first. Documento, seção, claim, decisão, requisito, pesquisa, evidência e memória são entidades distintas. Texto é representação; identidade e autoridade pertencem aos registros canônicos.

</aside>

# Objetivo

Fechar a ontologia mínima que sustenta Plan Mode, Memory Atlas, Context Compiler v2, Documentation Compiler, Handoff v2, traceability e futuras evals sem depender de transcript ou Markdown como banco de verdade.

# Princípio central

```
Source material
    ↓
SourceRecord / Section
    ↓
Claims / Findings
    ↓
Decisions / Requirements / Constraints / Risks
    ↓
Evidence / Relationships / Lineage
    ↓
Project Knowledge
    ↓
Memory promotion
```

O sistema diferencia **o que foi dito**, **o que foi observado**, **o que foi decidido** e **o que está autorizado a governar o projeto**.

# Stable semantic IDs

IDs nunca dependem de título, path, ordem de array ou posição no documento.

Namespaces candidatos:

```
SRC-...   SourceRecord
SEC-...   Section
CLM-...   Claim
FND-...   Finding
DEC-...   Decision
REQ-...   Requirement
CON-...   Constraint
RSK-...   Risk
ASM-...   Assumption
Q-...     OpenQuestion
RES-...   ResearchRecord
EV-...    Evidence
MEM-...   MemoryRecord
REL-...   Relationship when independently addressable
```

IDs são persistentes; rename/move não altera identidade. Human-friendly aliases podem existir, mas não são primary keys.

# Status lifecycle

Status é tipado por record kind, mas usa vocabulário coerente:

```
candidate
proposed
discussing
accepted
rejected
superseded
deprecated
invalidated
archived
```

Nem todo kind usa todos os estados. `Evidence`, por exemplo, tende a `observed/validated/invalidated`; `ResearchRecord` pode ser `current/review_due/stale/expired` via freshness sem confundir isso com authority.

# Authority classes

Authority é separada de confiança/freshness.

```
canonical-policy
accepted-decision
accepted-requirement
validated-project-knowledge
validated-evidence
trusted-reference
research
candidate
external-data
untrusted-data
```

Regras:

- model output nasce no máximo como `candidate/proposed`;
- promotion de authority exige policy/actor autorizado;
- `superseded` preserva história, mas deixa de governar novo contexto por default;
- uma fonte confiável pode estar stale; freshness não altera sua origem/authority histórica.

# SourceRecord

Representa material de origem, não conclusão.

```
SourceRecord
├── id
├── source_type
│   ├── repository_file
│   ├── web_page
│   ├── paper
│   ├── issue/pr
│   ├── transcript/session
│   ├── user_input
│   ├── external_document
│   └── generated_artifact
├── locator
├── title
├── publisher/owner optional
├── captured_revision / digest
├── captured_at semantic timestamp
├── freshness_class
├── trust_class
├── privacy_scope
├── license/citation metadata optional
└── sections[]
```

Web source content is immutable snapshot by digest for provenance, while latest-location metadata can point to a newer version.

# Section

`Section` is the smallest stable human/document semantic region worth addressing.

```
Section
├── id
├── source_id
├── parent_section_id optional
├── heading/title
├── source_range / structural anchor
├── semantic_digest
├── summary projections
├── claims[]
└── children[]
```

SectionID survives line shifts when structural matching can recover identity; if semantics fundamentally change, lineage records replacement.

# Claim

Claim é uma proposição verificável ou governável, não necessariamente uma Decision.

```
Claim
├── id
├── proposition
├── claim_type
│   ├── factual
│   ├── architectural
│   ├── behavioral
│   ├── performance
│   ├── compatibility
│   ├── security
│   ├── cost
│   └── other
├── scope/qualifiers
├── validity_conditions[]
├── source_refs[]
├── evidence_refs[]
├── confidence_class derived/curated
├── status
└── lineage
```

Claims permitem contradiction/coverage sem procurar palavras soltas em Markdown.

# Finding vs Claim

`Finding` representa uma conclusão de pesquisa/análise ainda não necessariamente normativa.

```
ResearchRecord
└── Findings[]
    └── may support Claims/Decisions
```

Isso preserva diferença entre “pesquisa encontrou X” e “o projeto decidiu X”.

```
MemoryRecord

│   ├── reusable_decision_pattern
│   ├── technical_finding
│   ├── implementation_lesson
│   ├── failure_pattern
│   ├── benchmark_result
│   ├── workflow_pattern
│   └── reference_summary

├── evidence refs[]
├── freshness_class
├── promotion_status
├── authority_class
├── retrieval_summary
```

Memory promotion preserva lineage até projetos/fontes de origem. Generalização não apaga condições.

# Lineage / supersession

Nunca apagar conhecimento apenas porque ficou antigo.

```
DEC-A --superseded_by--> DEC-B
CLM-A --qualified_by--> CLM-B
RES-A --refreshed_by--> RES-B
SEC-A --replaced_by--> SEC-B
```

Current view resolve lineage; historical view preserva trajetória.

# Semantic digest

Digest é calculado sobre projection semântica canônica; presentation metadata não invalida downstream sem necessidade.

Exemplo: alterar icon/tag visual não muda Claim digest; alterar proposition muda.

# Canonical vs derived

Canônicos:

- typed records e relations;
- stable IDs;
- authority/status/lineage;
- source/provenance pointers.

Derivados:

- FTS rows;
- embeddings;
- summaries;
- graph materializations;
- coverage indexes;
- contradiction candidates;
- document projections;
- Memory Atlas browse manifests.

Derived state é rebuildable.

# Storage

Arquivos Markdown/JSON/JSONL continuam canônicos quando apropriado; SQLite é runtime/index derivado.

Recomendação:

```
.prumo/knowledge/
├── records/
├── sources/
├── relationships/
├── snapshots/
└── manifests/
```

A implementação pode shardear por kind/project, mas API esconde layout.

# Privacy and deletion

Privacy scope acompanha cada record/source/edge. Deletion/redaction deve invalidar derived indexes/embeddings/caches e preservar somente audit metadata quando policy/legalidade exigir.

Cross-project promotion exige revisão de privacy e secrets.

# Knowledge Manifest

Manifest machine-readable cataloga:

```
record id/kind/status/authority/freshness
compact retrieval summary
token estimate
source/section pointers
relationships summary
semantic digest
revision
```

É navegação, não duplicação do conteúdo completo.

# Integration contracts

- Context Compiler consome descriptors/projections via Knowledge API;
- Documentation Compiler consome Knowledge IR tipado;
- Handoff usa refs/pointers;
- Contradiction/Coverage Engine opera sobre Claims/Requirements/Relations/Evidence;
- Memory promotion transforma records por policy, mantendo provenance;
- Agents mutam somente via `KnowledgeDelta`.

# Decisões fechadas

- stable semantic IDs first-class;
- Claim é entidade independente;
- SourceRecord/Section separados de conclusions;
- Finding != Decision;
- authority != trust != freshness != status;
- lineage/supersession preserva histórico;
- MemoryRecord é generalizado e provenance-backed;
- relationships tipadas substituem inferência por substring;
- canonical records simples; indexes/summaries/embeddings derivados;
- model output nunca recebe authority elevada implicitamente.
