# 41 — Notebook-to-Repository Promotion: Export, Reconciliation e Canonical Docs Bootstrap

> Authority: canonical specification.
> Logical ID: PART2-CH-41
> Source: Notion Living Book (3d89bb7d023f81559c14e3a7eac6b018)
> Status: Especificação especializada do Harness / Code Agent (Capítulo 41).


<aside>
📥

**Status: ACCEPTED workflow.** O caderno do Notion pode ser exportado e colocado no repositório como **snapshot de arquitetura/planejamento para promoção**, mas não se torna automaticamente documentação canônica. O agente deve reconciliar esse snapshot com código, schemas e documentos locais, produzir uma nova documentação coerente, validar diferenças e então promover os outputs aprovados como canonical repository docs.

</aside>

# Objetivo

Permitir o workflow:

```
Prumo Code Agent notebook
→ export snapshot
→ repository import area
→ inventory + reconciliation
→ Documentation Plan
→ generated/assisted docs
→ validation/review
→ canonical repository documentation
```

sem criar duas fontes de verdade permanentes.

# Onde colocar o export

Diretório recomendado:

```
.prumo/imports/notion/prumo-code-agent/<snapshot-id>/
```

Exemplo de `snapshot-id`: data + digest curto, sem depender apenas do timestamp.

Preservar a estrutura exportada e assets. Não mover esses arquivos diretamente para `docs/` como se já fossem documentação final.

# Snapshot manifest

Criar ao importar um `manifest.json` com, quando disponível:

```
schema_version
source = notion
notebook = Prumo Code Agent
root_page_id / root_url
exported_at
snapshot_id
source_revision information when available
files[]
assets[]
content digests
imported_by / tool version
notes / export limitations
```

JSON/Markdown permanecem formatos preferidos; não introduzir YAML canônico novo.

# Authority durante a promoção

O export é uma **fonte de decisão planejada**, não descrição automática do que já está implementado.

Resolver cada informação em duas dimensões separadas:

```
Design authority/status
→ OPEN / PROPOSED / ACCEPTED / REJECTED / SUPERSEDED

Implementation status
→ not_started / partial / implemented / verified / deprecated
```

Uma arquitetura `ACCEPTED` no caderno pode continuar `not_started` no código. A documentação nova deve representar essa diferença explicitamente em vez de afirmar que uma feature já existe.

# Reconciliation authority

Durante este bootstrap específico:

1. instrução atual explícita do usuário;
2. Decisions `ACCEPTED` mais recentes do notebook exportado para **target architecture/product direction**;
3. contratos/schemas/repository docs atuais para comportamento já canônico;
4. código/testes para **observed implementation reality**;
5. histórico/legacy docs;
6. inferência do agent.

Conflito entre target architecture e implementação não é resolvido apagando um lado: registrar **planned-vs-implemented drift**.

# Bootstrap pipeline

## B0 — Freeze/import

- exportar notebook completo e assets;
- criar snapshot directory;
- gerar digests/manifest;
- não editar o snapshot importado depois da ingestão.

## B1 — Inventory

Inventariar:

- README/AGENTS/ENTRYPOINT/FRAMEWORK;
- docs existentes;
- schemas;
- commands/contracts/profiles;
- packages Go e principais interfaces;
- tests/conformance fixtures;
- imported notebook pages.

## B2 — Normalize knowledge

Converter as decisões relevantes do export em records candidatos:

- Decision;
- Requirement;
- Constraint;
- Finding/ResearchRecord;
- OpenQuestion;
- Architecture Claim;
- Documentation requirement.

Preservar source pointers para página/arquivo exportado.

## B3 — Conflict/drift analysis

Classificar:

```
notebook accepted + repo aligned
notebook accepted + implementation missing
notebook accepted + repo docs stale
repo behavior newer than notebook
true contradiction
historical/superseded material
unknown / evidence insufficient
```

Não "resolver" divergência por resumo arbitrário.

## B4 — Documentation Plan

Executar Human Documentation Planner sobre:

```
normalized accepted target architecture
+ current implementation inventory
+ public/internal audiences
+ project capabilities
+ existing docs ownership
```

Produzir Page Graph, coverage, gaps, generation ownership e impact plan antes de reescrever arquivos.

## B5 — Generate canonical candidates

Gerar por prioridade:

- ENTRYPOINT/AGENTS/FRAMEWORK routing quando impactados;
- Project Overview/README;
- architecture/system docs;
- harness/runtime contracts;
- Knowledge/Documentation architecture;
- roadmap/status docs;
- reference material derivável;
- maintainers/development docs;
- human docs skeleton quando apropriado.

`GENERATED` pode ser rebuild completo. `ASSISTED/CURATED` produz diff/proposal.

## B6 — Validate

Executar:

- schema/runtime conformance;
- links/anchors;
- duplicated/conflicting claims;
- implementation-status claims contra code/tests;
- Decision supersession;
- coverage/readiness;
- examples quando houver;
- no-op/determinism where applicable.

## B7 — Promote

Somente após validação/review:

```
candidate docs
→ canonical docs paths
→ SOURCE_MAP/provenance update
→ KnowledgeManifest rebuild
→ derived indexes rebuild
```

Após promoção, os novos documentos do repositório superam o snapshot Notion para operação do projeto.

# Snapshot lifecycle

O snapshot importado é immutable evidence/input.

Após promoção pode permanecer versionado por auditabilidade ou ser movido para storage/retention definido pelo projeto, mas não deve participar de retrieval padrão com mesma autoridade dos docs canônicos.

Context Compiler classifica-o como `imported-planning-snapshot`/historical source depois da promoção.

# Source maps

Cada canonical document/section promovido deve apontar para os source records usados, inclusive páginas do snapshot quando relevantes.

Evitar provenance baseada somente em título. Preferir page ID/URL + snapshot ID + path + digest.

# No giant prompt invariant

Não pedir ao code agent:

> "Leia todos esses Markdown e reescreva tudo."
> 

O workflow correto é:

```
inventory
→ normalize
→ reconcile
→ plan
→ generate by dependency/impact
→ validate
→ promote
```

O agent pode ler o snapshot progressivamente conforme o Planner/Knowledge Runtime indicar.

# Preserve implementation truth

Exemplo:

```
Notebook Decision:
"Prumo Code will be a separate repository."
Status: ACCEPTED target architecture

Current repository:
no prumo-code repo yet

Correct documentation:
"Prumo Code is planned as a separate product after HA0–HA5 split gate."

Incorrect documentation:
"Prumo Code currently runs as a separate repository."
```

# Migration from older Prumo docs

Não apagar automaticamente documentação antiga útil. Classificar cada arquivo:

```
keep
update
split
merge
supersede
archive
remove candidate
```

Remoção deve ocorrer apenas quando conteúdo está coberto por nova fonte canônica ou comprovadamente obsoleto.

# Canonical output expectations

Ao terminar, o repositório deve possuir uma documentação navegável e menor que o corpus de planejamento:

```
short entrypoints
+ authoritative architecture/contracts
+ implementation/status truth
+ user/maintainer docs
+ provenance/source map
+ machine-readable manifests
```

O notebook exportado pode ser enorme; o runtime não deve exigir que agents o releiam normalmente depois da promoção.

# Handoff artifact

O bootstrap gera um `DocumentationMigrationReport` contendo:

```
snapshot id
sources inspected
accepted decisions promoted
implementation drifts found
files created/updated/superseded
open documentation gaps
conflicts requiring human/product decision
coverage/readiness result
validation/evidence
```

# Suggested execution boundary

Esse processo é uma **documentation migration/bootstrap Run**, não uma implementação livre do Harness. O agente deve evitar alterar código apenas para fazer a implementação combinar com a documentação; code changes são Tasks separadas derivadas dos drifts encontrados.

# Git workflow

Recomendação:

```
branch docs/notion-bootstrap
→ import snapshot commit
→ normalized/planning artifacts commit when persisted
→ documentation generation commits grouped semantically
→ validation fixes
→ review
→ merge
```

Separar import do snapshot das mudanças nos docs facilita auditoria e revert.

# Security/privacy

Antes de commit/publication:

- secret scan no export;
- classificar páginas/assets privados;
- evitar publicar conteúdo interno através do docs site;
- preservar licenças/source attribution relevantes;
- excluir transcript/raw data sem necessidade do repository snapshot.

# Exit criteria

O bootstrap termina quando:

- target architecture aceita está representada corretamente;
- current implementation status está distinguido de roadmap;
- não há contradições P0 conhecidas entre canonical docs;
- main entrypoints apontam para a nova estrutura;
- source/provenance mappings existem;
- docs readiness configurada passa ou blockers são registrados;
- agents futuros não precisam ler o export completo para operar o projeto.

# Regra pós-promoção

```
Notion/export snapshot = planning provenance/reference
Repository canonical docs = operational authority
```

Novas mudanças de arquitetura podem voltar a ser discutidas no caderno, mas precisam passar novamente por promotion/reconciliation para alterar o estado canônico do repository.
