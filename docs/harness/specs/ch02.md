# Objetivo

Usar projetos existentes como biblioteca de padrões, não como blueprint único.

| Projeto | O que estudar | O que evitar copiar cegamente |
| --- | --- | --- |
| Pi | separação provider API → agent core → coding agent → TUI; loop pequeno e componível | modelo de permissões/sandbox menos central que o desejado no Prumo |
| OpenCode | UX de coding agent; subagents; tools; permissions `allow/ask/deny`; configuração | acoplar regras canônicas do Prumo à implementação do cliente |
| OpenHands | workspace/sandbox; agent server; SDK; execução remota; separação client/server | adotar infraestrutura distribuída cedo demais |
| Cline | separação SDK/agents/core/apps; eventos; sessão; hooks | carregar toda complexidade de extensão/IDE no primeiro ciclo |
| SWE-agent | Agent Computer Interface; tools desenhadas para modelos, feedback conciso | tratar shell bruto como interface principal |
| Aider | repository map; context selection; architect/editor specialization | tornar estratégia de dois modelos um invariant |
| Codex | sandbox, approvals, workspace execution, app-server/CLI separation | assumir que UX de um produto web/desktop define nosso runtime |

# Padrão convergente encontrado

Os melhores projetos acabam separando aproximadamente:

```
Model Providers
    ↓
Agent Core / Loop
    ↓
Tool + Workspace Runtime
    ↓
Session / Persistence / Events
    ↓
CLI / TUI / Desktop / IDE / Server
```

O Prumo já possui boa parte das camadas de projeto, policy e control plane. A oportunidade é acrescentar **Agent Core + Execution Runtime**, preservando o diferencial de Goals, documentation contracts, workforce, Evidence e Gates.

# Direção arquitetural consolidada

<aside>
🧱

**Decisão ACCEPTED:** nenhum harness completo será adotado como kernel do Prumo. O Core/Harness será Prumo-native em Go. Projetos externos serão usados como **referências de engenharia**, fontes de padrões testáveis e, quando houver protocolo/SDK/server compatível, como `AgentProvider` externo.

</aside>

A especificação canônica dessa decisão está em [35 — Harness Build Strategy: Prumo-Native Core, External Agent Providers e Selective Reuse](ch35.md).

## Regra de reaproveitamento

```
Se define estado/produto canônico do Prumo
→ OWN

Se é infraestrutura genérica e substituível
→ REUSE behind Prumo port

Se já existe como agent runtime independente
→ INTEGRATE as AgentProvider

Se é útil apenas para aprender padrões
→ REFERENCE / SPIKE
```

# Programa de extração de padrões

Para cada reference harness, não basta registrar features. Criar spikes/evals com perguntas concretas:

- como representa Turn, Session e Event?
- quem possui canonical state?
- como pausa/cancela/resume?
- como representa tool call parcial/streaming?
- quais safe points existem?
- como lida com permission wait?
- como previne duplicate side effects?
- como faz compaction/context pruning?
- como expõe external agents?
- como testa provider conformance?
- como separa UI de runtime?
- quais failures aparecem somente em produção?

Resultados úteis viram `ResearchRecord`/`Finding`; somente padrões compatíveis com os invariantes Prumo podem virar Decision/implementation contract.

# O que explicitamente NÃO copiar

- canonical Session/Run de outro framework;
- ontology de memory externa;
- permission model que bypassa ToolGateway/Prumo policy;
- agent-specific persistence como fonte de verdade do Project;
- hidden coroutine state necessário para resume;
- vendor event types atravessando o Core;
- nested agent loop tratado como ModelProvider;
- shell-only ACI como interface principal;
- workflow DSL genérica antes de necessidade real.

# Padrões já promovidos ao desenho Prumo

- **unrolled/re-entrant agent state machine**;
- **ModelProvider ≠ AgentProvider**;
- host-owned Run/state/policy;
- external agent via ACP/SDK/RPC/server quando possível;
- structured ACI com observations compactas;
- UI como client do runtime/event stream;
- fake/scripted provider antes de provider real;
- conformance suite compartilhada por adapters;
- durable safe points/checkpoints em vez de stack suspensa;
- selective reuse behind Prumo ports.

# Hipóteses que vamos validar

- um loop simples e stateless entre turns, apoiado por estado persistido, é preferível a um megaclasse de agent;
- tools estruturadas tendem a ser melhores que shell-only;
- o agente deve poder continuar um Run em outro modelo sem fingir que a nova sessão é a anterior;
- architect/editor pode ser útil como recipe opcional;
- permissões e sandbox devem ser responsabilidade do runtime, não instruções textuais;
- UI deve reagir a eventos do runtime, não controlar o runtime diretamente.
