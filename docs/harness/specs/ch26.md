# Objetivo

Transformar `Decision`, `Requirement`, `Constraint`, `ResearchRecord`, `Evidence`, `Gate`, `Goal`, `Plan`, `Task` e outras entidades canônicas em documentação e dados reproduzíveis, incrementais, auditáveis e baratos em tokens.

O mesmo compiler atende duas famílias de projeção:

```
Knowledge Runtime
├── Agent/LLM Documentation
│   └── manifests, contracts, context, handoff, knowledge maps
└── Human Documentation
    └── README, docs site, manuals, guides, reference, handbooks, changelog e chronicle
```

Human Documentation não é um pipeline paralelo de verdade; reutiliza `Knowledge IR`, `Document IR`, dependency DAG, provenance, semantic digests e incremental build. Especificações: [36 — Human Documentation Runtime: Audiences, Profiles, Surfaces e Generation Policy](ch36.md) e [37 — Documentation Planner: Discovery, Information Architecture, Coverage e Page Graph](ch37.md).

```
Canonical Knowledge
      ↓
Knowledge IR
      ↓
Document IR
      ↓
Dependency DAG
      ↓
Incremental Evaluator
      ↓
Renderer
      ↓
Canonical Serializer
      ↓
Atomic Writer
      ↓
Artifact Manifest + Provenance
```

# 1. Knowledge IR separado de Document IR

Nunca renderizar Markdown diretamente a partir de registros crus.

## Knowledge IR

Representação normalizada do domínio: decisions, requirements, constraints, relationships, provenance, status, authority, freshness e stable IDs.

## Document IR

Representação semântica de documento, inspirada no padrão Reader → AST → Writer de sistemas como Pandoc:

```
Document
├── Metadata
├── Section
│   ├── Paragraph
│   ├── DecisionSummary
│   ├── RequirementList
│   ├── Table
│   ├── CodeBlock
│   ├── Admonition
│   ├── Diagram
│   └── References
└── ...
```

O renderer recebe `DocumentIR`, nunca business entities diretamente. Isso permite Markdown hoje e HTML/Notion/JSON/outros writers depois sem duplicar regras de domínio.

# 2. Pure build nodes

Cada documento ou seção gerada é modelada como uma função conceitualmente pura:

```
Artifact = Render(
  semantic inputs,
  template version,
  renderer version,
  schema version,
  options
)
```

Sem relógio atual, locale implícito, filesystem order, random IDs ou estado global oculto.

# 3. Dependency DAG

Criar um grafo explícito entre registros e artefatos:

```
Decision D-42 ─────┐
Requirement R-18 ──┼→ Architecture.Section.GUI → architecture.md
Constraint C-09 ───┘

Decision D-42 ───────────────→ ADR.D-42 → adr/0042-floem.md
```

Índices mínimos:

- forward dependencies: node → deps;
- reverse dependencies: input → dependents;
- artifact → source records;
- record → affected artifacts.

Usar stable IDs, não paths ou títulos, como identidade primária.

# 4. Incremental recomputation

Adotar um algoritmo inspirado em build systems e query engines incrementais:

1. detectar inputs alterados por fingerprint/revision;
2. propagar invalidation pelo reverse dependency graph;
3. avaliar somente o closure afetado;
4. antes de recomputar dependentes, comparar digest semântico do resultado intermediário;
5. se o valor derivado não mudou, interromper propagação adicional (`red/green` style);
6. reutilizar cache content-addressed quando fingerprint completo já existe.

Para scheduling:

- Kahn/topological ordering para DAG normal;
- Tarjan SCC para detectar ciclos e produzir erro explicável;
- ready queue + worker pool para nós independentes;
- commit dos outputs em ordem estável, independentemente da ordem de execução paralela.

# 5. Fingerprints e content-addressing

Cada node/artifact possui `InputFingerprint` derivado de:

```
semantic input digests
+ dependency digests
+ renderer version
+ template version
+ schema version
+ relevant options
```

Recomendação inicial: SHA-256 da stdlib Go pela simplicidade, portabilidade e ausência de dependência. BLAKE3 pode ser benchmarkado futuramente para CAS muito grande.

O fingerprint deve ser sobre representação canônica, não bytes arbitrários de YAML/Markdown.

# 6. Canonical serialization

## JSON

Para objetos que entram em hash, assinatura, cache key ou comparação cross-runtime, usar JSON canônico compatível com RFC 8785/JCS ou uma canonicalização equivalente bem especificada. Go `encoding/json` ordena map keys, mas JCS é preferível quando a identidade precisa ser interoperável entre implementações.

## YAML

YAML permanece formato humano quando útil, mas não deve ser base de hashing/identity por possuir maior superfície de representação equivalente.

## Markdown

Definir renderer próprio com regras fixas de whitespace, heading, listas, tabelas, code fences e line endings.

# 7. Reproducibility rules

Outputs determinísticos devem obedecer:

- UTF-8;
- `\n` como newline canônico;
- ordem explicitamente estável e locale-independent;
- IDs estáveis derivados do domínio, nunca índices incidentais;
- sem timestamps de build por padrão;
- quando data for necessária, usar data semântica do source/revision ou `SOURCE_DATE_EPOCH`-like input explícito;
- paths normalizados;
- maps/sets sempre materializados em ordem determinística antes de render;
- renderer/template/schema versions incluídas no fingerprint;
- nada depende de current working directory, timezone, hostname ou environment variável não declarada.

# 8. Schema validation antes da renderização

JSON Schema continua canônico no Prumo. Validar:

1. canonical records;
2. Knowledge IR;
3. Document IR serializado para debug/test quando aplicável;
4. Artifact Manifest.

CUE pode ser estudado como ferramenta opcional de authoring/validation de configurações, mas não substitui JSON Schema como contrato canônico sem decisão futura explícita.

# 9. Renderers como writers

Implementar writers pequenos:

```
DocumentWriter
├── MarkdownWriter
├── JSONWriter
├── NotionWriter        future/adapter
├── HTMLWriter          future
└── ...
```

`MarkdownWriter` deve ser deterministicamente testável. Em Go, `goldmark` é boa referência/parser AST para ler e modificar Markdown existente; o writer gerado pelo Prumo deve manter regras próprias estáveis.

# 10. Templates: usar com disciplina

`text/template` da stdlib Go é adequado para templates internos/trusted e leaf formatting, mas não deve carregar regras de domínio complexas.

Regra:

```
Domain rules → Go application/domain layer
Document composition → Document IR builders
Small presentation fragments → templates
```

Evitar template logic que consulta filesystem, relógio, rede ou estado global.

Jsonnet/CUE podem ser considerados futuramente para templates/configuração user-authored, mas aumentam superfície de segurança e complexidade; não são necessários no MVP do compiler.

# 11. Whole-file generation vs managed regions

## Arquivo totalmente gerado

Preferir **regenerar o arquivo inteiro**. É mais simples, idempotente e reproduzível.

## Arquivo misto humano + Prumo

Nunca fazer regex cega. Usar managed regions com stable IDs:

```
<!-- example:prumo:begin section=architecture.gui source=D-42,R-18 -->
...generated content...
<!-- example:prumo:end section=architecture.gui -->
```

Ao atualizar:

1. parsear Markdown para AST;
2. localizar região/anchor estrutural;
3. validar ownership/hash anterior;
4. substituir somente subtree/região gerenciada;
5. preservar conteúdo humano fora dela.

Se a região foi editada manualmente desde o último generation hash, gerar conflict/review em vez de sobrescrever silenciosamente.

# 12. Structured patching

Para dados estruturados, preferir operações explícitas:

- JSON Pointer (RFC 6901) para endereçamento;
- JSON Patch (RFC 6902) quando operações add/remove/replace/move/test importam;
- Merge Patch somente para objetos simples, onde sua semântica de `null` é adequada.

Para Markdown, AST-aware patching é primário; Myers/Patience/Histogram são úteis para preview e conflito, não como fonte canônica de mutação.

# 13. Provenance e source maps

Cada Artifact e, quando útil, cada Section deve saber de onde veio:

```
ArtifactManifest
├── artifact_id
├── output_path
├── output_digest
├── compiler_version
├── schema_version
├── template_version
├── input_records[]
│   ├── id
│   └── digest
├── generated_sections[]
├── generated_at_source_revision
└── warnings[]
```

`generated_at_source_revision` é revisão semântica/Git revision, não wall-clock obrigatório.

# 14. Content-addressed cache

Cache derivado candidato:

```
.prumo/cache/docs/
├── objects/<digest>
├── manifests/
└── graph.db
```

Se o fingerprint de um node já existe, seu resultado pode ser reutilizado sem renderização. O cache é descartável/rebuildable e nunca vira canonical source.

# 15. Impact analysis por delta

Quando entra um `KnowledgeDelta`:

```
changed record IDs
      ↓
reverse dependency lookup
      ↓
affected semantic sections
      ↓
affected artifacts
      ↓
rebuild only those nodes
```

Exemplo: trocar uma decisão de GUI não deve regenerar testing strategy se não houver dependência declarada entre ambos.

# 16. Atomic writes e crash safety

Pipeline recomendado:

1. render para memória/temp file;
2. validar output;
3. calcular output digest;
4. se digest == arquivo atual, **não escrever** e preservar mtime;
5. caso mude, escrever temp no mesmo filesystem/diretório do destino;
6. flush/close e, quando durability for requerida, sincronizar dados/metadados conforme a plataforma;
7. executar `AtomicReplace` por adapter de filesystem/OS; em Unix pode usar rename apropriado, mas **não assumir `os.Rename` como atômico cross-platform**;
8. atualizar generation manifest por último.

Para compilações multi-arquivo, manter um `GenerationPlan`/journal derivado para recovery e nunca deixar manifest afirmar que arquivos foram gerados antes de seus writes concluírem.

# 17. Deterministic materialized views

Índices, TOCs, decision tables, requirement matrices, backlinks, coverage maps e status dashboards devem ser materialized views de canonical records.

Exemplo:

```
Decision Ledger
      ↓ deterministic query
Accepted Decisions View
      ↓ renderer
DECISIONS.md table
```

Não chamar LLM para ordenar, agrupar, contar, criar backlinks ou preencher tabelas cuja informação já está estruturada.

# 18. Stable ordering policy

Cada collection define uma ordering key explícita. Exemplos:

- Decisions: semantic sequence/ID;
- Requirements: priority → stable ID;
- Tasks: plan order → stable ID;
- References: normalized source ID;
- tables sem ordem semântica: stable lexical key em locale neutro.

Nunca depender de iteration order incidental.

# 19. Idempotency

Invariant crítico:

```
Compile(S) = O
Compile(S) = O
```

E para patching:

```
Apply(P, Apply(P, D)) == Apply(P, D)
```

quando a operação for definida como idempotente.

O compiler deve detectar no-op por digest antes de tocar filesystem.

# 20. Tests obrigatórios

## Golden tests

Fixtures de Knowledge IR → bytes exatos esperados de Markdown/JSON/manifests.

## Reproducibility tests

Executar geração duas ou mais vezes com environment/order diferentes e exigir output byte-identical.

## Order-invariance properties

Em coleções semanticamente unordered, embaralhar inputs e exigir mesmo output.

## Incrementality tests

Mudar um record e confirmar que apenas seu reverse dependency closure é reconstruído.

## Idempotency tests

Rebuild sem alteração produz zero writes.

## Conflict tests

Editar manualmente managed region e garantir que Prumo não sobrescreva sem review/policy.

## Fuzzing

Fuzz Markdown parser/managed-region patcher, JSON patch input, manifests e recovery state. Go possui fuzzing nativo e recomenda targets determinísticos/sem estado compartilhado.

# 22. Algoritmos recomendados

| Problema | Técnica |
| --- | --- |
| dependency scheduling | DAG + Kahn topological sort |
| cycle detection | Tarjan strongly connected components |
| incremental invalidation | reverse dependency closure |
| avoid needless propagation | revision/digest red-green validation |
| cache identity | content-addressed fingerprints |
| structured data updates | JSON Pointer + JSON Patch |
| Markdown updates | AST-aware managed-region replacement |
| human diff preview | Patience/Histogram; Myers when minimal/general diff is desired |
| search/index views | SQLite + FTS5/BM25 + relational joins |
| deterministic output | canonical serialization + stable sort |

# 23. Research basis

Arquitetura inspirada principalmente em:

- Bazel Skyframe/remote cache: dependency graphs, incremental rebuild, action cache e content-addressed storage;
- *Build Systems à la Carte* / Shake: dependency discovery e incremental builds;
- Salsa: memoized query model + revision/red-green invalidation;
- Git internals: content-addressed object storage;
- RFC 8785: JSON canonicalization;
- RFC 6901/6902: structured addressing/patching;
- Reproducible Builds project: stable ordering, timestamps e environment determinism;
- Pandoc/CommonMark/goldmark: document AST and reader/writer separation;
- JSON Schema 2020-12: structural validation;
- SQLite FTS5/BM25: deterministic local retrieval/materialized indexes.

# Decisão recomendada

Começar simples, mas com as boundaries corretas:

```
Go structs + JSON Schema
→ typed Knowledge IR
→ typed Document IR
→ small dependency DAG engine
→ SHA-256 fingerprints
→ Markdown/JSON deterministic writers
→ whole-file regeneration first
→ managed-region AST patching second
→ local CAS/cache
```

Não implementar um framework genérico estilo Bazel/Salsa inteiro. Copiar os princípios e algoritmos necessários ao domínio de documentação do Prumo, mantendo uma API pequena e observável.

# 24. Consolidação aprofundada da pesquisa técnica

Esta seção consolida os achados externos e explicita como as ideias de build systems, incremental computation, content-addressing, canonicalização e ASTs devem ser adaptadas ao domínio documental do Prumo. O objetivo **não** é construir um Bazel genérico: é reutilizar os princípios que maximizam determinismo, auditabilidade, incrementalidade e economia de tokens.

## 24.1 Modelo mental: documentação como materialized build

O `DocumentationCompiler` trata documentação derivada como uma **materialized view reproduzível** do estado canônico:

```
Canonical Records
  Decision / Requirement / Constraint / Research / Evidence / Goal / Plan / Task
        ↓ normalize
Knowledge IR
        ↓ project
Semantic Projection Nodes
        ↓ compose
Document IR
        ↓ render
Artifact bytes
```

A informação normativa permanece nos records canônicos; Markdown/JSON gerados são projeções. O compilador deve conseguir apagar todos os caches/artefatos derivados e reconstruí-los a partir do estado canônico.

## 24.2 Pure-ish query/build model

Cada nó derivado é conceitualmente uma função `K → V` memoizável, semelhante ao modelo de query engines incrementais:

```
NodeKey
  = kind + semantic ID + compiler/schema/template versions + relevant options

NodeValue
  = canonical semantic result

NodeDigest
  = SHA-256(canonical(NodeValue))
```

A função não pode depender silenciosamente de relógio, timezone, ordem do filesystem, hostname, rede, current working directory ou estado global. Qualquer input externo relevante precisa virar dependência explícita e participar do fingerprint.

## 24.3 Dois digests: input fingerprint e semantic output digest

Usar duas identidades separadas:

```
InputFingerprint
= hash(inputs + dependency digests + renderer/template/schema/options versions)

SemanticOutputDigest
= hash(canonical semantic output)
```

Isso permite o comportamento red/green:

1. um input/revision muda;
2. o nó fica candidato a recomputação;
3. recomputa sua projeção semântica;
4. se `SemanticOutputDigest` permanece igual, o nó volta a **GREEN**;
5. dependentes podem continuar usando resultados anteriores sem cascata desnecessária;
6. se mudou, fica **RED** e a invalidação segue aos dependentes.

Assim, alterar metadata operacional de uma Decision que não modifica sua projeção documental não deve regenerar toda a árvore.

## 24.4 Grafo: identidade por stable IDs, não paths

Paths são atributos mutáveis, não identidade. Nós sugeridos:

```
Knowledge Nodes
- decision:D-...
- requirement:R-...
- constraint:C-...
- research:RS-...
- evidence:EV-...
- goal:G-...

Projection Nodes
- projection:architecture.desktop
- projection:requirements.security
- projection:decision-index

Document Nodes
- document:architecture
- document:requirements
- document:adr:D-...

Artifact Nodes
- artifact:docs/architecture.md
- artifact:docs/decisions/D-....md
```

Manter adjacency indexes diretos e reversos para evitar varreduras globais:

```
forward[node]  -> dependencies[]
reverse[node]  -> dependents[]
```

Persistência derivada pode usar SQLite; representação canônica do grafo pode ser reconstruída a partir de records/contracts/bindings.

## 24.5 Scheduling e ciclos

Para um subgrafo afetado:

- calcular reverse dependency closure;
- induzir o subgrafo mínimo afetado;
- usar **Kahn topological sort** para ready queue;
- executar nós independentes em worker pool;
- fazer commit/render final em ordem estável, não em completion order;
- usar **Tarjan SCC** para diagnosticar ciclos.

Erro de ciclo deve ser explicável:

```
DOC_DEPENDENCY_CYCLE
architecture.security
→ requirements.security
→ decision:D-104
→ architecture.security
```

Não apenas `cycle detected`.

## 24.6 Content-addressed cache em duas camadas

Inspirar-se no padrão Action Cache + CAS:

```
InputFingerprint
      ↓
Action Cache
      ↓
SemanticOutputDigest / ArtifactDigest
      ↓
CAS object
```

Estrutura derivada candidata:

```
.prumo/cache/documentation/
├── action-cache/
├── objects/
│   └── sha256/<prefix>/<digest>
├── manifests/
├── graph.db
└── recovery/
```

O cache é sempre descartável. Nenhuma Decision, Requirement, Evidence ou fonte normativa pode existir apenas no CAS.

## 24.7 Canonicalização para hashing

### JSON

Para objetos que participam de identidade interoperável, usar **RFC 8785 / JSON Canonicalization Scheme (JCS)** ou uma implementação equivalente formalmente especificada. O objetivo é garantir que representações logicamente idênticas produzam os mesmos bytes, inclusive com ordenação determinística de propriedades.

Fluxo:

```
Typed Go value
→ canonical semantic projection
→ JCS-compatible JSON
→ SHA-256
```

`encoding/json` continua adequado para muitos outputs internos, mas não deve ser assumido como contrato cross-runtime de identidade sem uma especificação de canonicalização explícita.

### YAML

YAML pode permanecer formato humano/legacy onde aplicável, mas nunca base direta de content identity. Parsear → estrutura tipada → projeção canônica → hash.

### Markdown

Markdown gerado deve possuir writer próprio e regras fixas:

- UTF-8;
- newline `\n`;
- heading spacing definido;
- blank lines definidos;
- lists/tables ordenadas por policy;
- code fence policy estável;
- whitespace final definido;
- nenhuma dependência de locale.

## 24.8 Reproducibilidade como quality gate

O compilador deve passar por uma suíte que altere deliberadamente condições irrelevantes:

```
shuffle input collections
change worker scheduling
change filesystem enumeration order
change locale/environment permitidos
run compiler repeatedly
```

Resultado exigido: bytes/digests idênticos para o mesmo estado semântico.

Quando uma data precisa aparecer no output, ela deve ser uma entrada semântica explícita — revision/date da fonte, release date ou equivalente — e não `time.Now()` escondido no renderer. Uma política inspirada em `SOURCE_DATE_EPOCH` é apropriada para outputs que realmente precisam de um timestamp reproduzível.

## 24.9 Whole-file generation é o default

Arquivos 100% owned pelo Prumo devem ser regenerados integralmente:

```
DocumentIR
→ render candidate
→ validate
→ digest
→ compare destination
→ same digest: NoChange
→ different: transactional replace
```

Regenerar integralmente reduz complexidade e torna idempotência/testes muito mais fortes. Patches estruturais são necessários somente quando conteúdo humano e gerado coexistem.

## 24.10 Managed regions AST-aware

Para arquivos mistos:

```markdown
<!-- example:prumo:begin id=architecture.gui source=D-42,R-18 generated=sha256:... -->
...
<!-- example:prumo:end id=architecture.gui -->
```

Pipeline:

1. parsear Markdown para AST;
2. identificar região por stable section ID;
3. calcular digest do conteúdo atualmente gerenciado;
4. comparar com `generated` anterior;
5. se intacto, substituir subtree;
6. se modificado manualmente, criar `GeneratedRegionConflict` e exigir review/policy;
7. preservar todos os nodes humanos fora da região.

Regex pode ser usada apenas para reconhecer markers simples durante parsing; nunca como mecanismo primário de mutação estrutural.

`goldmark` é candidato natural em Go para parsing/AST CommonMark; o writer do Prumo deve permanecer controlado por nós para evitar mudanças involuntárias de formatação entre versões de biblioteca.

## 24.11 Patching de JSON e optimistic concurrency

Usar padrões existentes:

- **RFC 6901 JSON Pointer** para endereço estável dentro do documento;
- **RFC 6902 JSON Patch** para `add/remove/replace/move/copy/test`;
- Merge Patch apenas em configurações simples onde sua semântica seja suficiente.

O operador `test` é especialmente útil antes de uma mutação por agente:

```json
[
  {"op":"test","path":"/decisions/D-42/status","value":"accepted"},
  {"op":"replace","path":"/decisions/D-42/status","value":"superseded"}
]
```

Se outro Run/Agent já modificou o record, a operação falha ao invés de sobrescrever silenciosamente.

## 24.12 `GenerationPlan` transacional

Antes de tocar o filesystem, produzir um plano derivado:

```
GenerationPlan
├── compile_id
├── source_revision
├── affected_nodes[]
├── artifact_operations[]
│   ├── create
│   ├── replace
│   ├── no_change
│   └── conflict
├── expected_old_digests[]
├── candidate_new_digests[]
└── manifest_digest
```

Fases:

```
PLAN
→ RENDER TEMP
→ VALIDATE
→ PRECONDITION CHECK
→ COMMIT ARTIFACTS
→ COMMIT MANIFEST LAST
```

Crash antes do manifest deixa o sistema capaz de detectar/reconciliar a compilação incompleta. O manifest nunca pode afirmar que um artifact foi gerado antes do replace correspondente ter concluído.

## 24.13 Atomic replace cross-platform

Não assumir que `os.Rename` possui a mesma atomicidade em todos os SOs. Criar boundary:

```
AtomicReplacer
├── Unix implementation
└── Windows implementation
```

Regras mínimas:

- tempfile no mesmo filesystem/directory family quando necessário;
- write + close/flush conforme política de durability;
- replace específico da plataforma;
- cleanup de temporários em erro;
- generation manifest atualizado por último;
- recovery journal para multi-artifact commit.

Atomicidade e durability não são sinônimos: `rename`/replace protege contra arquivo parcialmente substituído, enquanto fsync/durability possui semântica própria e deve ser tratada explicitamente quando o nível de garantia justificar.

## 24.14 Materialized views: zero LLM

Tudo que já está estruturado deve ser produzido por queries/algoritmos determinísticos:

```
Accepted Decisions table
Requirement trace matrix
ADR index
Backlinks
Goal/Task status
Coverage matrix
Evidence/Gate summary
Contradiction list
Source provenance table
Memory freshness dashboard
```

Pipeline típico:

```
Canonical records
→ SQLite/materialized query
→ typed rows
→ Document IR
→ writer
```

SQLite FTS5/BM25 pode apoiar lookup lexical/derived indexes. A LLM não deve ser chamada para ordenar, contar, agrupar, criar backlinks ou preencher tabelas cujo conteúdo já existe de forma estruturada.

## 24.15 Provenance em nível de seção/claim

`ArtifactManifest` deve evoluir para provenance granular:

```
ArtifactManifest
├── artifact_id
├── output_path
├── digest
├── compiler/schema/template versions
├── source_revision
└── sections[]
    ├── section_id
    ├── section_digest
    ├── source_records[]
    ├── source_claims[]
    ├── dependency_nodes[]
    └── ownership
```

Isto habilita perguntas determinísticas como:

- “por que esta seção existe?”;
- “qual Decision gerou este parágrafo?”;
- “quais documentos mudam se D-42 mudar?”;
- “este trecho foi gerado ou escrito manualmente?”

## 24.16 Stable ordering policies por domínio

Não usar uma única ordenação lexical universal. Cada coleção declara seu `OrderingPolicy`:

```
Decisions     → semantic sequence / stable ID
Requirements  → priority, then stable ID
Tasks         → plan order, then stable ID
Sources       → authority/freshness, then stable ref
References    → normalized source ID
unordered set → bytewise lexical stable key
```

A ordenação faz parte da versão do renderer/policy e, quando altera bytes, participa do fingerprint.

## 24.17 Evals e property tests do compiler

Além de unit tests comuns:

### Reproducibility property

Mesmo semantic state → mesmo digest/bytes.

### Permutation invariance

Em collections sem ordem semântica, qualquer permutação → mesmo output.

### Incrementality

Alterar um record reconstrói somente o reverse dependency closure esperado.

### Red/green pruning

Alterar input sem modificar semantic projection não reconstrói dependentes.

### No-op write

Segunda compilação sem mudança → zero writes e mtimes preservados.

### Managed-region safety

Edição humana dentro de região owned → conflito, nunca overwrite silencioso.

### Crash recovery

Interromper o commit entre artifacts e confirmar recuperação/reconciliação correta.

### Fuzzing

Fuzz targets para parser/managed regions, manifests, patch application, canonicalizer boundaries e recovery journal. Targets devem permanecer rápidos, determinísticos e livres de estado global compartilhado.

## 24.18 Métricas de implementação

Medir:

- nodes total / nodes affected / nodes recomputed;
- red-green prune ratio;
- action-cache hit rate;
- CAS hit rate;
- bytes rendered vs bytes written;
- no-op write ratio;
- graph lookup latency;
- compile latency P50/P95;
- artifact conflicts;
- provenance coverage por section;
- deterministic test failures;
- **LLM calls avoided by deterministic compilation**.

## 24.19 Ordem de implementação recomendada

### D0 — determinismo básico

Typed IR, stable sort, deterministic Markdown/JSON writer, SHA-256, no-op digest, golden/repro tests.

### D1 — dependency graph

Stable node IDs, forward/reverse indexes, Kahn, Tarjan, impact closure.

### D2 — generation manifests

Artifact/section provenance, source digests, explicit ownership.

### D3 — transactional writer

GenerationPlan, platform-specific AtomicReplace, recovery journal.

### D4 — structured patching

JSON Pointer/Patch, Markdown AST, managed regions, conflict detection.

### D5 — incremental optimization

Action cache/CAS + red-green pruning + parallel evaluator.

### D6 — materialized knowledge views

SQLite/FTS5 derived views, backlinks, indexes, trace matrices.

Essa ordem preserva simplicidade inicial: o MVP recebe as boundaries corretas antes das otimizações sofisticadas.

# 24. Imported planning corpus / promotion workflow

O Documentation Compiler também participa de migrations em que um corpus de planejamento externo (ex.: export do caderno Notion) precisa virar documentação canônica do repository.

Esse corpus entra como **immutable imported snapshot**, não como canonical docs.

```
Imported planning snapshot
→ normalize to candidate Knowledge records
→ reconcile authority/status with repo + code reality
→ DocumentationPlan
→ generate/patch candidates
→ validate
→ promote
```

A promoção preserva duas dimensões distintas: `target architecture status` e `implementation status`. Uma Decision `ACCEPTED` pode estar `not_started` na implementação e deve ser documentada assim.

Após promoção, repository docs/records passam a ser operational authority e o snapshot permanece provenance/historical input com retrieval reduzido.

Workflow completo: [41 — Notebook-to-Repository Promotion: Export, Reconciliation e Canonical Docs Bootstrap](ch41.md).
