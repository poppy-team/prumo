# Objetivo

Fechar o caminho entre `DocumentationPlan` e documentação confiável publicada: validação de conteúdo, exemplos executáveis, screenshots, links, accessibility, versioning, traduções, preview e deploy estático.

# Publishing pipeline

```
Knowledge Snapshot
↓
Documentation Plan
↓
Compile GENERATED content
↓
Generate ASSISTED proposals
↓
Apply approved CURATED/ASSISTED state
↓
Validate
↓
Build examples / capture required media
↓

↓
Build docs website adapter
↓
Preview
↓

↓
Publish
↓
Publication Manifest
```

# Renderer independence

O output canônico de Human Docs é:

```
Markdown/MDX-compatible content
+ docs.manifest.json
+ navigation manifest
+ redirects
+ media manifest
+ locale/version metadata
```

O Core Go não importa Astro/VitePress/etc. Um `SiteRendererAdapter` transforma esses artifacts em site.

# Website adapter default — Astro Starlight

**Decisão:** Starlight é o adapter padrão recomendado para novos projetos que pedem site de documentação.

Motivos:

- construído especificamente para documentation sites;
- Markdown/MDX;
- navegação, busca, SEO e code highlighting integrados;
- suporte i18n/fallback/RTL;
- boa acessibilidade como objetivo do projeto;
- extensível sem obrigar o conteúdo canônico a usar componentes proprietários;
- gera site estático adequado a GitHub Pages e outros hosts.

Referências oficiais: [Starlight](https://starlight.astro.build/) e [i18n](https://starlight.astro.build/guides/i18n/).

`VitePress` permanece adapter alternativo válido para projetos que prefiram ecossistema Vue/Vite; possui local search e i18n próprios. O Prumo não depende de ambos.

# Runtime boundary

```
Prumo Core (Go)
→ docs source tree + SiteBuildSpec
→ external supervised build process
→ npm/pnpm/bun adapter environment
→ static site output
```

Node toolchain é dependência do site package, não do Prumo Core/CLI básico. Profile `No-site` continua suportado com Markdown puro.

# SiteBuildSpec

```
SiteBuildSpec
├── renderer adapter/version
├── source directory
├── output directory
├── base URL
├── locale/version routes
├── theme tokens/branding refs
├── search policy
├── sitemap/SEO policy
├── redirects
└── deploy target
```

# GitHub Pages

Default de publicação para repositórios GitHub públicos quando usuário habilitar publishing:

```
static build
→ CI artifact
→ GitHub Pages
```

Também suportar generic static directory para Netlify/Cloudflare Pages/self-hosting sem alterar docs source.

# Documentation Quality Gates

## Structural

- todos os links internos resolvem;
- anchors/redirects não conflitam;
- sidebar aponta para unidades existentes;
- orphan pages explicitamente permitidas ou reportadas;
- stable IDs não duplicados;
- frontmatter/schema válido.

## Contract consistency

- comandos documentados existem no Command Registry;
- config keys existem no schema;
- environment variables documentadas existem no registry;
- API/plugin/provider symbols referenciados existem no contrato atual;
- error codes existem;
- version compatibility respeitada.

## Examples

- snippets executáveis são extraídos de `ExampleRecord` testado;
- compile/run/test em sandbox quando possível;
- expected output comparado;
- examples non-executable devem ser marcados explicitamente;
- snippets duplicados preferem source include/pointer em vez de cópia.

## Links externos

External link check é periódico/cacheado para evitar tornar todo build dependente da rede. Resultado inclui status e last_checked; não falhar build por indisponibilidade transitória sem policy.

## Content/provenance

- claim público precisa authoritative source permitido;
- stale source gera warning/error conforme profile;
- assisted content sem refs suficientes falha generation gate;
- superseded Decision não pode continuar governando seção current.

# Documentation Readiness profiles

Adicionar ao Readiness Engine:

```
documentation-dev-ready
documentation-release-ready
documentation-publication-ready
```

Exemplo `documentation-release-ready` exige:

- reference das capabilities novas;
- changelog/release metadata;
- migration guide se breaking;
- exemplos/testes current;
- traduções obrigatórias conforme policy;
- nenhum blocker de links/contracts/provenance.

# Accessibility

Website quality gate deve incluir:

- semantic headings/order;
- alt text obrigatório para imagens informativas;
- teclado/focus para componentes custom;
- contraste via theme tokens;
- idioma `lang` correto;
- links com texto útil;
- evitar informação apenas por cor;
- reduced-motion onde houver animações.

O adapter Starlight fornece boa base, mas componentes/customizações continuam sujeitos a gates.

# Screenshots como artifacts verificáveis

```
ScreenshotRecord
├── id
├── source app/version/revision
├── screen/view identity
├── fixture/state setup
├── viewport
├── theme
├── locale
├── capture digest
├── crop/annotation metadata
├── consumers[]
└── freshness status
```

Regra: LLM não gera screenshot falso de uma UI real para documentação factual.

# Screenshot capture strategy

Quando o projeto expõe automation/test hooks:

```
fixture
→ launch app/page
→ navigate deterministic state
→ capture
→ optional deterministic annotation overlay
→ visual artifact digest
```

Mudança na UI contract/revision marca consumidores como potentially stale. Captura manual pode existir, mas deve carregar provenance/version.

# Diagrams

Preferir diagramas gerados de dados estruturados quando possível:

- Mermaid a partir de graph/domain model;
- dependency graphs;
- state machines;
- sequence diagrams.

Diagramas ilustrativos manuais/curated são permitidos. Generated diagram mantém source refs.

# Versioning policy

Default:

```
main/current docs → desenvolvimento atual
stable docs → release estável
release snapshots → somente quando produto/API realmente exige histórico navegável
```

Evitar copiar árvore inteira por versão sem necessidade. Units declaram validity/version range; renderer monta views por versão.

Aliases/redirects preservam links após rename.

# Release snapshot

Em release:

```
Knowledge snapshot
+ DocumentationPlan digest
+ artifact digests
+ version
→ immutable DocumentationReleaseManifest
```

Permite reconstrução/auditoria do que estava documentado naquela versão.

# i18n

Modelo source-first:

```
Source DocumentationUnit
↓
TranslationRecord(locale)
```

`TranslationRecord` inclui source digest/revision. Mudança no source marca tradução `needs_update`.

Estados:

```
missing
machine_draft
needs_review
current
needs_update
stale
```

# Translation policy

- reference estruturada pode ser regenerada por locale com glossary;
- prosa assistida pode usar Local Knowledge Worker ou provider remoto conforme privacy;
- publicação pública pode exigir review humano para locales configurados;
- code/CLI identifiers nunca são traduzidos sem mapping explícito;
- glossary de termos do projeto é first-class.

# Search

Search index é derived artifact. Default site usa busca local do renderer sempre que suficiente; external search SaaS nunca é requisito do Prumo.

Search deve indexar locale/version separadamente e respeitar visibility.

# SEO / metadata

Gerar deterministicamente quando possível:

- title;
- canonical URL;
- description candidate/approved;
- sitemap;
- OpenGraph basics;
- robots policy;
- version/locale alternates.

Marketing copy permanece CURATED/ASSISTED.

# Security and privacy

Antes da Human Documentation Compiler pipeline:

```
visibility eligibility
→ secret scan
→ provenance/privacy policy
→ content generation
```

Não gerar conteúdo privado e tentar removê-lo na publicação. Public build recebe apenas refs elegíveis.

# Preview/review

ASSISTED/CURATED updates produzem:

```
semantic summary
+ rendered diff
+ provenance
+ affected pages
+ screenshots/examples changed
```

Review pode aceitar por section/unit ou batch policy.

# Atomic publishing

Build do site ocorre em staging directory. Somente após gates:

```
staging output
→ digest manifest
→ promote/deploy
```

Publication manifest é atualizado após deploy confirmado quando integration permitir.

# Incremental build

Documentation Compiler invalida units; site adapter pode usar seu próprio cache, mas Prumo não depende dele para correctness. Se apenas uma referência mudou, apenas seus docs nodes são recompilados antes do site build.

# Observability / metrics

Métricas úteis:

```
coverage by audience/intent
stale units
translation freshness
broken links
example pass rate
reference/schema drift
assisted acceptance/rejection rate
time/tokens per changed unit
public/private rejection count
```

Métricas servem melhoria; não criam meta de "mais páginas".

# Site customization

Theme/branding pertence ao projeto/usuário. Prumo fornece default sóbrio e acessível; pode aceitar design tokens/logo/nav extras. Custom components nunca tornam conteúdo canônico dependente de JSX/MDX proprietário sem opt-in.

# Invariantes fechados

- Markdown + manifests são renderer-neutral;
- Starlight é default adapter, não kernel;
- site toolchain roda fora do Core Go;
- GitHub Pages é deploy default opcional, não obrigatório;
- docs têm quality gates e readiness próprios;
- examples, screenshots e translations são versioned artifacts;
- public visibility é filtro de entrada;
- publication é staging→validate→promote;
- search/SEO/sidebar são derived artifacts.
