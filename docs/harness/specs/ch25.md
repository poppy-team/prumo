# Objetivo do Plan Mode

O Plan Mode não é apenas `generate plan`. Ele é uma sessão de descoberta semelhante a uma conversa técnica prolongada entre usuário e arquiteto/engenheiro.

```
Question
→ discussion
→ research
→ alternatives
→ analysis
→ decision
→ rationale
→ open questions
→ next topic
```

Cada etapa significativa produz registros estruturados que sobrevivem ao chat e podem popular a documentação do Prumo no encerramento.

# Princípio

> **Conversation is a workspace; decisions and evidence are the durable product.**
> 

A conversa pode ser longa, mudar de direção e conter hipóteses. O estado durável deve distinguir fatos, pesquisas, propostas, decisões aceitas, decisões superseded e perguntas abertas.

# PlanningSession

```
PlanningSession
├── Project / Idea
├── Threads
├── Questions

├── Alternatives
├── Decisions
├── Assumptions
├── Constraints
├── Requirements
├── Risks
├── OpenQuestions

```

Plan Mode pode ser iniciado para um Project existente ou antes de o Project formal existir.

# Interação

O agent pode:

- fazer perguntas ao usuário quando a resposta muda materialmente o design;
- pesquisar web/docs/repositórios/conectores quando autorizado;
- criar comparações sistemáticas;
- propor alternativas e trade-offs;
- registrar decisões assim que forem confirmadas;
- marcar decisões como tentative, accepted, rejected ou superseded;
- detectar contradições entre decisões novas e antigas;
- resumir o estado atual sem perder provenance;
- continuar dias depois a partir dos registros persistidos.

# Planning Journal append-only

Cada interação relevante produz um evento compacto append-only, não uma cópia integral da conversa.

```
PlanningEvent
├── timestamp
├── kind
├── subject
├── summary
├── status
├── source refs
├── related entities
├── supersedes
└── content pointer
```

Kinds candidatos: `question`, `answer`, `research`, `finding`, `proposal`, `decision`, `constraint`, `requirement`, `risk`, `assumption`, `rejection`, `supersede`, `open_question`.

# Decision Ledger

Decisões devem existir em um ledger first-class:

```
Decision
├── id
├── topic
├── status
├── chosen
├── rationale
├── alternatives[]
├── consequences[]
├── evidence[]
├── sources[]
├── created_at
├── supersedes / superseded_by
└── authority
```

O ledger permite reconstruir **por que** o projeto chegou ao estado atual e evita que exemplos históricos contradigam decisões mais recentes.

# Research Ledger

Research não é Decision. Cada pesquisa guarda pergunta, findings, fontes, data/freshness, confiança e quais decisões ela suporta. Conteúdo externo pode envelhecer sem invalidar automaticamente uma decisão; freshness deve ser explícita.

# Finalization / Knowledge Harvest

Quando um Project ou grande milestone é finalizado:

```
Project knowledge
→ normalize
→ deduplicate
→ validate status/freshness
→ redact secrets/private data
→ classify scope
→ generate summaries/indexes
→ Memory Atlas
```

O objetivo não é guardar `chat history forever`, e sim extrair conhecimento reutilizável e verificável.

# Três níveis de memória

## 1. Raw/Trace Memory

Trajetória, journal e artefatos de sessão. Pode ter retenção limitada e não entra automaticamente no contexto.

## 2. Project Knowledge

Decisions, requirements, architecture, lessons e research validados daquele projeto. Autoridade maior e versionada com o Project.

## 3. Cross-Project Memory Atlas

Conhecimento generalizável e explicitamente promovido: padrões, trade-offs, benchmarks, bibliotecas estudadas, decisões recorrentes, problemas encontrados e soluções comprovadas.

**Raw memory nunca deve ser promovida automaticamente como verdade cross-project.**

# Memory Atlas serializado

O Atlas precisa ser barato para LLMs explorarem sem carregar o banco inteiro.

```
Memory Atlas
├── catalog.json / manifest
├── domain maps
├── technology maps
├── decision maps
├── dependency/relationship graph
├── compact summaries
├── provenance pointers
└── indexes
```

Cada nó expõe summary muito curta + IDs relacionados + pointers para conteúdo completo. O Context Compiler faz progressive disclosure: mapa → resumo → registro → fonte completa somente quando necessário.

# Storage/index architecture

Fontes canônicas: Markdown/JSON/JSONL versionáveis. Camada derivada candidata:

```
SQLite
├── relational metadata
├── FTS5 / BM25 lexical search
├── relationship tables / graph edges
├── token counts
├── freshness/authority indexes
└── cached summaries
```

Embeddings/vector retrieval são **opcionais e derivados**, adicionados apenas se benchmarks mostrarem ganho sobre structured filters + FTS + graph traversal. O sistema deve funcionar bem offline e sem vector DB externo.

O Prumo pode oferecer um **Local Knowledge Pack opcional** no instalador, combinando encoder de embeddings, reranker sob demanda e um tiny Knowledge Worker para classificação, extração e compaction. A arquitetura, modelos candidatos, licenciamento, perfis de instalação e gates de benchmark estão detalhados em [28 — Local Knowledge Pack: Small Models, Offline RAG e Document Intelligence](ch28.md). O Core nunca depende desse pack.

# Retrieval pipeline

```
query/task
→ scope filter
→ authority/freshness filter
→ lexical/structured search
→ graph expansion
→ rerank
→ compact atlas entries
→ selective full record fetch
→ Context Compiler
```

Priorizar Least Context: entregar à LLM a menor quantidade de memória que resolve a pergunta.

# Reuse entre projetos

Ao iniciar projeto novo, o Prumo pode montar um `Prior Knowledge Pack` com conhecimento relacionado:

- stacks já avaliadas;
- benchmarks anteriores;
- decisões semelhantes;
- riscos conhecidos;
- libraries/frameworks estudados;
- implementação/maintenance lessons;
- padrões aprovados;
- decisões rejeitadas e por quê.

Isso reduz pesquisas repetidas, mas **não elimina verificação externa** quando informação é time-sensitive, normativa, segurança-critical ou pode ter mudado.

# Contradição e supersession

O Atlas representa conflito explicitamente. Uma decisão/research nova não apaga a antiga; usa lineage e relationships tipadas como `supersedes`, `contradicts`, `qualifies`, `invalidates` ou `deprecated`. Retrieval favorece autoridade + freshness + estado atual, mantendo história auditável.

Modelo semântico canônico: [33 — Knowledge Runtime Semantic Model: Records, Claims, Sources, Sections, Authority e Lineage](ch33.md).

Contradiction/Coverage/Readiness Engine: [34 — Contradiction, Coverage & Readiness Engine: Semantic Validation, Traceability e Gates](ch34.md).

# Knowledge promotion policy

Promoção Project → Cross-Project pode ser:

- manual;
- suggested (recomendado como default);
- automatic apenas para classes explicitamente permitidas.

O usuário pode rejeitar promoção. Informações sensíveis/secrets nunca são promovidas.

# Privacy e redaction

Antes de harvest/index:

- remover secrets/tokens;
- classificar personal/project-private/public;
- respeitar provider/tool retention policies;
- permitir Project excluir categorias da memória global;
- registrar provenance sem copiar conteúdo licenciado integral quando não necessário.

# Relação com Context Compiler

Memory Atlas é uma fonte do Context Compiler, não substituto dele. O Context Compiler opera sobre descriptors/records estáveis do Knowledge Runtime e nunca precisa inferir autoridade ou identidade a partir de headings/texto livre.

```
Repo Map
Project docs
Run state
Memory Atlas
External research
       ↓
Context Compiler
       ↓
Context Manifest
```

Context Manifest registra exatamente quais memórias foram incluídas e por quê.

# Token efficiency como contrato

O Planning & Knowledge Runtime deve ser desenhado para **reduzir**, e não aumentar, o custo de contexto ao longo do tempo. A meta é que projetos futuros reutilizem conhecimento com menos tokens do que uma nova pesquisa/releitura completa.

## Princípios de economia

- **Knowledge Delta no mesmo Turn:** sempre que possível, a resposta principal do agent também produz um pequeno delta estruturado de decisions/findings/questions; não fazer uma segunda chamada de LLM apenas para resumir cada mensagem.
- **Append-only compacto:** Journal registra eventos sem repetir transcript completo.
- **Progressive disclosure:** Atlas → compact summary → record → source completa somente quando necessária.
- **Retrieval local primeiro:** filtros estruturados, SQLite/FTS5/BM25 e graph traversal não exigem chamada de LLM.
- **Least Context:** Context Compiler recebe budget explícito para memória e pesquisa; resultados competem por relevância/authority/freshness.
- **Semantic deduplication:** conhecimento repetido aponta para o mesmo record/version lineage em vez de duplicar texto.
- **Cached research:** pesquisas podem ser reutilizadas por query/topic/source fingerprint enquanto freshness permitir.
- **Cheap compaction path:** compaction/harvest que realmente exija inferência pode usar modelo pequeno/barato/local ou processamento em lote; modelos premium ficam para decisões difíceis.
- **Documentation compile por delta:** gerar/atualizar somente documentos afetados por decisões novas, não regenerar o livro inteiro a cada turno.
- **Prompt/provider cache aware:** preservar prefixos estáveis e aproveitar caching do provider quando disponível.

## Active Planning Context

Uma PlanningSession longa não deve reenviar toda a conversa. O contexto ativo é montado de:

```
Current topic
+ active decisions/constraints
+ unresolved questions
+ tiny session summary
+ selected research/memory records
+ recent turns only when needed
```

O transcript completo continua disponível como trace, mas fica fora do prompt por padrão.

## Knowledge Delta conceitual

```
Agent response
├── user-facing answer
└── KnowledgeDelta
    ├── decisions[]
    ├── findings[]
    ├── requirements[]
    ├── constraints[]
    ├── risks[]
    ├── open_questions[]
    └── source_refs[]
```

Se o runtime/provider suporta structured output, o delta pode ser emitido junto da mesma inferência. Caso contrário, heurísticas/deterministic parsing ou compaction assíncrona futura podem complementar sem bloquear a conversa.

## Multi-agent budget discipline

Multi-agent é o maior potencial multiplicador de tokens. Portanto:

- Solo continua caminho mínimo;
- `suggested` é preferível a ativação automática indiscriminada;
- cada AgentRole recebe token/cost budget;
- delegação deve justificar expected information gain/evidence delta;
- evitar dois agents lendo o mesmo contexto completo; compartilhar pointers/summaries;
- reviewer recebe diff + requirements/evidence relevantes, não toda a trajetória do implementer.

## Research budget discipline

Pesquisa web não é repetida quando memória válida já responde ao fundamento. Quando freshness exige atualização, usar memória como **search seed** e verificar apenas claims envelhecidas. Resultados são normalizados uma vez e reutilizados por outros agents/Projects.

## Documentation budget discipline

O Documentation Compiler usa templates + dados estruturados para montagem determinística sempre que possível. LLM é reservado para síntese/prosa que realmente necessita geração; decisões, requisitos, tabelas, relações e provenance podem ser renderizados sem nova inferência.

## Métrica de produto

Além de qualidade, medir:

- tokens de entrada por Turn;
- tokens gastos em retrieval/compaction;
- percentual de contexto vindo de summaries vs full records;
- memória recuperada mas não utilizada;
- research cache hit rate;
- tokens por Decision aceita;
- tokens por Evidence delta;
- custo incremental de cada AgentRole;
- economia estimada por reuse cross-project.

# Ciclo de engenharia do Prumo Code

```
PLAN
  → BUILD
  → REVIEW
  → LEARN / KNOWLEDGE HARVEST
  → PLAN BETTER NEXT TIME
```

O Memory Atlas fecha o ciclo: conhecimento validado de Build/Review volta ao Planning futuro como prior knowledge, com provenance e freshness.

# Invariantes

- token efficiency é parte do contrato do produto, não otimização posterior;
- conversation transcript não é fonte canônica automática;
- decisions/facts mantêm provenance e status;
- knowledge retrieval é scope/authority/freshness-aware;
- memory Atlas é serializável, versionável e rebuildable;
- índices/embeddings são derivados e descartáveis;
- não usar memória antiga para substituir pesquisa atual quando freshness importa;
- documentação é compilada de conhecimento validado, não de contexto oculto do modelo.
