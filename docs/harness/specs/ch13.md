# Oride como ponto de partida conceitual

Oride já prova uma arquitetura Rust/Ratatui modular com rope buffers, filesystem, Git, PTY, Tree-sitter, LSP, Markdown, splits, mouse e performance budgets. Esta nova TUI deve estudar o que pode ser reutilizado como padrão e onde queremos ir além.

# Onde ir além do Oride

- Agent Runtime first-class;
- diff/patch review vinculado a tool calls;
- persistent multi-agent runs;
- integrated permissions;
- test/evidence/gates;
- worktree/sandbox awareness;
- terminal multiplexer mais completo;
- richer component/layout system;
- code actions/refactors/debugging;
- plugin SDK compatível com o Harness;
- remote attach a `prumo-agentd`.

# Fundamental

TUI não executa agent logic localmente por duplicação. Ela conecta ao mesmo Agent Protocol, mesmo se o daemon estiver embutido/in-process no modo simples.

# Direção visual: Zed traduzido para terminal

A referência principal de composição visual passa a ser o **Zed**. Isso não significa tentar imitar pixels impossíveis no terminal; significa preservar seus princípios de densidade, hierarquia e foco.

- poucas caixas explícitas: preferir contraste, gutters e separators sutis;
- tabs compactas e legíveis;
- sidebar/activity rail fina;
- command palette/quick pick como superfície central de navegação;
- panes/splits como primeira classe;
- status bar mínima;
- iconografia discreta por Unicode/Nerd Font opcional, sempre com fallback textual;
- seleção/focus fortes o suficiente para teclado, sem excesso de decoração;
- agent/run panel deve parecer parte do editor, não um chat anexado;
- terminal, problems, tests e evidence formam o bottom panel no mesmo modelo mental do editor;
- temas Desktop e TUI compartilham **tokens semânticos** — `surface`, `panel`, `border-subtle`, `text-muted`, `accent`, `success`, `warning`, `error`, `focus` — mas não código de widgets.

O objetivo é que uma pessoa alternando entre Desktop e TUI reconheça imediatamente a mesma família de produto, mesmo com capacidades gráficas diferentes.
