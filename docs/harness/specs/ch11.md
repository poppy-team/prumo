# Objetivo

O terminal será first-class tanto no desktop quanto na TUI, mas não devemos repetir xterm.js se a meta é uma stack nativa e leve.

# Separar responsabilidades

```
PTY Process Layer
    ↓ bytes
VT Parser / Terminal State
    ↓ cells/events
Renderer
    ↓
Desktop GPU/software OR host terminal/TUI
```

# libghostty

Estudar `libghostty`/`libghostty-vt` como core embutível de terminal. A direção do projeto Ghostty é expor parsing/state em biblioteca cross-platform sem exigir que o consumidor use a aplicação Ghostty inteira.

# WezTerm

`wezterm-term` é alternativa Rust madura para emulação VT, scrollback, OSC/hyperlinks e imagens de terminal. Benchmarkar API, footprint, Unicode e facilidade de embedding.

# PTY

Desktop e headless precisam de uma abstração PTY independente do renderer:

- spawn shell/process;
- resize;
- stdin/out stream;
- signals/cancel;
- process metadata;
- cwd/env;
- persistence/reconnect quando viável.

# Terminal multiplexer do Prumo

Possível modelagem:

```
TerminalSession
├── PTY
├── workspace/run binding
├── panes
├── scrollback/artifact pointer
├── process state
└── permission/network context
```

# Integração com Agent Runtime

Agente não deve obter acesso irrestrito ao PTY apenas porque a UI possui terminal. `process.exec` e `process.pty` passam pelas mesmas policies e environments.

# Performance tests

- sustained output MB/s;
- resize storm;
- Unicode/emoji/CJK width;
- huge scrollback;
- alternate screen;
- mouse protocols;
- bracketed paste;
- images/protocols opcionais;
- CPU idle;
- memory per terminal session.
