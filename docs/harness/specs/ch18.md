# Workstreams horizontais adicionados

Dois domínios atravessam várias fases e não devem ser tratados como feature tardia de UI:

- **Workforce + Model Gateway/Handoff:** contracts entram junto de H1/H2; health/routing/fallback podem amadurecer incrementalmente; multi-agent/worktrees conectam-se fortemente a H14. Proxy HTTP externo é opcional e posterior ao Gateway interno.
- **Planning & Knowledge Runtime:** PlanningSession/Decision/Research ledgers podem nascer cedo como persistência estruturada; Documentation Compiler e Project Knowledge amadurecem antes da UI grande; Memory Atlas integra-se ao Context Compiler/H4 e ao replay/evals/H8. Cross-project promotion deve depender de policies de provenance/freshness/privacy.
- **Knowledge Semantics + Validation:** stable semantic IDs, Claims/Sources/Sections/Research/Memory records, lineage e typed relationships formam a base compartilhada. Contradiction/Coverage/Readiness entram antes de H8 para que eval/replay trabalhem sobre evidence e blockers reais, não heurísticas lexicais.
- **Local Intelligence Runtime:** contracts de `KnowledgeTask`, `KnowledgeModelRouter`, `ResourceManager`, `WorkerSupervisor` e package manifests podem nascer junto de H4/Knowledge Runtime. `llama.cpp/GGUF` e ONNX Runtime são workers supervisionados fora do Core; nenhum cliente depende desses runtimes diretamente. `No-LLM` permanece parity target obrigatório. Runtime/package benchmarks integram H8 antes de recomendar perfis de RAM.
- **Handoff v2 + Knowledge API:** typed continuation, pending effects, KnowledgeService e `KnowledgeDelta Validate→Commit` entram entre H2/H4. H8 deve testar crash/restart/cross-provider resume, duplicate-side-effect=zero e provenance/concurrency. Esta boundary também prepara H11/H12 sem fazer ACP/SDK virarem o domain model.

Referências: [24 — Workforce Runtime, Model Gateway, Routing, Fallback e Handoff](ch24.md), [25 — Planning & Knowledge Runtime: Plan Mode, Decision Ledger e Memory Atlas](ch25.md) e [30 — Local Inference Runtime Architecture: Workers, GGUF/ONNX, Lifecycle e Packaging](ch30.md).

# Harness implementation track HA0–HA11

Este track detalha H1–H14 sem substituir o roadmap macro.

```
HA0  Agent Runtime contracts + normalized Model/Agent events
HA1  deterministic FakeProvider + first real ModelProvider
HA2  re-entrant NativeAgent state machine
HA3  ToolGateway + Permission lifecycle integration
HA4  checkpoint/resume + budgets + observability + failure taxonomy
HA5  Native Coding ACI + Sandbox/Environment hardening
HA6  second ModelProvider + Model Gateway/fallback/circuit behavior
HA7  first external AgentProvider via official protocol/server
HA8  cross-provider Handoff dogfood + duplicate-side-effect=zero
HA9  Context Compiler v2 + Knowledge Runtime integration
```

External connectivity pode avançar em paralelo a HA1–HA4. Isso permite usar Codex/OpenCode/Goose/Claude Code/etc. como execution backends maduros enquanto o Native Agent ganha capacidade.

# Connectivity gate

Antes dos clientes grandes, os contratos devem distinguir **ModelProvider** de **AgentProvider**, normalizar `AgentEvent`, suportar credential ownership e permitir adapters externos sem acoplar Run/UI a vendors. Custom Model Providers e Custom Agent Providers fazem parte do desenho desde o início, mesmo que adapters avançados entrem incrementalmente.

# Sequenciamento de clientes

A ordem Desktop vs TUI não precisa ser fixa. Depois de H9, podemos desenvolver spikes em paralelo porque ambos consomem o mesmo protocol. O primeiro produto visual escolhido será aquele que produzir maior valor com menor custo, sem bloquear o outro.

# Exit gate antes de UI grande

Antes de investir em uma grande UI, um Run headless deve conseguir:

```
prompt → context → model → tool → permission → sandbox → observation → model → tests/gates → checkpoint → completion
```

com crash/restart/resume e telemetry suficientes para depuração.

# Repository split gate

A criação de `raillen/prumo-code` não é uma fase inicial de UI; é consequência da maturidade do Harness headless.

Gate obrigatório:

```
HA0 contracts/events
HA1 FakeProvider + first ModelProvider
HA2 Native Agent loop
HA3 Tool/Permission integration
HA4 checkpoint/restart/resume
HA5 Coding ACI + Sandbox baseline
+ usable `prumo agent`
+ versioned protocol
+ reconnect/replay
```

Após esse gate, `Prumo Code` vira o primeiro consumidor externo sério do Prumo Protocol. Especificação: [40 — Repository Boundary & Product Split: Prumo Platform vs Prumo Code](ch40.md).

# Notebook-to-repository documentation bootstrap

Antes da próxima grande rodada de implementação, o caderno pode ser exportado para `.prumo/imports/notion/prumo-code-agent/<snapshot-id>/` e usado numa migration Run de documentação.

Fluxo obrigatório:

```
snapshot
→ inventory
→ normalize
→ reconcile accepted target architecture vs implementation reality
→ Documentation Plan
→ generate/update candidates
→ validate
→ promote canonical repo docs
```

O export nunca vira automaticamente canonical docs e não deve ser tratado como um giant prompt. Workflow completo: [41 — Notebook-to-Repository Promotion: Export, Reconciliation e Canonical Docs Bootstrap](ch41.md).
