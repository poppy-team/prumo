# Objetivo

Fechar a camada que responde de forma auditável:

- duas informações realmente se contradizem?
- um Requirement está coberto por implementação/evidence?
- uma Decision está refletida em docs/contracts/code?
- o projeto está pronto para avançar apesar de Runs concluídos?

# Separação de conceitos

```
Contradiction Engine
→ semantic consistency

Coverage Engine
→ required relation/evidence completeness

Readiness Engine
→ policy over coverage, gates, risks, questions and evidence
```

Um Run `completed` não implica readiness `ready`.

# Pipeline de contradiction detection

```
Changed records / snapshot
  ↓
Candidate pair generation
  ↓
Hard deterministic rules
  ↓
Scope + validity overlap
  ↓
Known lineage/supersession resolution
  ↓
Semantic candidate detector optional
  ↓
Typed validator / policy
  ↓
ContradictionCase candidate or confirmed
```

# Candidate pair generation

Nunca comparar tudo com tudo.

Gerar pares por:

- mesmo entity/topic key;
- same Requirement/Decision target;
- conflicting relationship types;
- same config/property/schema path;
- graph neighborhood;
- same claim subject/predicate;
- semantic similarity somente para ampliar candidatos;
- changed-record reverse neighborhood.

Isso mantém complexidade controlada.

# Hard deterministic rules

Exemplos:

```
same subject + same property + overlapping scope + unequal exclusive values
accepted DEC-A superseded by DEC-B but active docs still reference DEC-A
hard Constraint says no network while Task policy requires remote-only execution
Requirement status accepted but its canonical contract declares incompatible enum
```

Rules produzem reason codes reproduzíveis.

# Semantic contradiction assist

Tiny/standard LLM pode sugerir:

```
contradiction_candidate
qualification_candidate
specialization_candidate
```

Mas não marca `confirmed` por si só em records de alta autoridade.

Saída estruturada inclui refs, relation hypothesis e rationale curto; depois passa por scope/lineage/policy checks.

# Important distinction: contradiction vs qualification

```
"Use SQLite" 
vs
"Use SQLite for derived runtime state"
```

A segunda pode especializar a primeira, não contradizer.

Engine verifica qualifiers, scope e validity conditions antes de classificar conflito.

# Supersession drift

Caso especial importante:

```
Accepted Decision B supersedes A
but
Architecture Section / Contract / Skill still points to A
```

Isso gera drift mesmo se A e B não forem textual/logicamente contraditórios.

# Traceability-driven evaluation

Coverage usa relações tipadas:

```
REQ-10 --implemented_by--> code refs
REQ-10 --verified_by--> EV-55
DEC-07 --documented_by--> SEC-architecture-runtime
CON-02 --enforced_by--> PermissionPolicy-3
```

Ausência de edge explícita é um gap, não convite para substring search.

# Evidence validity

Evidence conta apenas se:

- subject/scope compatível;
- revision relevante;
- result satisfaz condition;
- freshness ainda válida;
- artifact/provenance acessível;
- gate policy permite aquele evidence type.

Um teste antigo contra revision diferente pode ficar `stale`, não `satisfied`.

# Requirement acceptance conditions

Requirements podem declarar conditions estruturadas:

```
REQ-42
acceptance:
- test suite auth.integration passes
- public API remains backward-compatible
- docs section auth.configuration updated
```

Coverage compiler transforma isso em required relations/gates quando possível.

# Policy profiles

Readiness é policy-driven por contexto:

```
planning-complete
implementation-ready
review-ready
merge-ready
release-ready
memory-promotion-ready
documentation-dev-ready
documentation-release-ready
documentation-publication-ready
```

Human Documentation profiles avaliam coverage por audiência/intent, reference/schema drift, examples, migrations, screenshots, translations, links, provenance e visibility. `documentation-release-ready` pode bloquear release quando uma breaking change carece de Migration Guide ou quando nova capability pública não possui Reference exigida pelo DocumentationSpec. Especificação: [38 — Human Docs Quality, Publishing, Website Runtime, Versioning e i18n](ch38.md).

Cada profile define required coverage/gates/severity thresholds.

# Gate semantics

Gates permanecem first-class:

```
Gate
├── id
├── condition
├── required Evidence/coverage
├── blocking
├── status
└── reason
```

Readiness agrega Gates; não os duplica.

# Contradiction severity

Candidatos:

```
info
warning
error
blocker
```

Exemplos:

- historical stale note: info;
- docs drift: warning/error conforme contract;
- two active canonical Decisions mutually exclusive: blocker;
- hard security Constraint violated: blocker.

# Resolution

Contradiction não é “apagada”.

```
resolve by:
- supersede
- qualify scope
- invalidate Claim
- update Requirement/Decision
- mark accepted exception with rationale
- refresh stale research
- repair docs/code/contract drift
```

Resolution cria relationships/provenance e fecha Case.

# Incremental evaluation

Mudança em record:

```
KnowledgeChanged
→ affected graph neighborhood
→ recompute contradiction candidates only there
→ recompute coverage requirements depending on changed refs
→ recompute impacted readiness profiles
```

Nada de varrer corpus inteiro após cada alteração.

# Rules engine

Não criar linguagem de regras genérica no MVP.

Usar typed Go rules:

```
Rule
├── ID
├── AppliesTo
├── Evaluate(snapshot/change)
└── reason codes
```

Rules são pequenas, puras quando possível e golden-tested.

Policy config seleciona rules/gates, mas business semantics ficam em Go/contracts.

# LLM assist boundaries

Permitido:

- candidate pair generation;
- classify candidate as contradiction/qualification/specialization;
- suggest missing traceability edge;
- summarize unresolved gaps.

Não permitido automaticamente:

- elevar authority;
- confirmar blocker canonical sem deterministic/policy validation quando rule exigir;
- inventar Evidence;
- marcar Requirement satisfied sem edge/evidence verificável.

# Coverage repair workflow

```
Gap detected
→ explain missing relation/evidence
→ optional agent proposal
→ KnowledgeDelta / implementation task
→ evidence produced
→ typed relation committed
→ incremental reevaluation
```

Isso conecta readiness diretamente ao Agentic Workspace.

# Explainability

Cada resultado responde:

```
Why conflicting?
Which scopes overlap?
Which rule fired?
What superseded what?
Why requirement is partial?
Which evidence is stale/missing?
What must change to become ready?
```

`KnowledgeService.Explain` usa reason codes, graph e manifests sem LLM por default.

# Evals

Contradiction:

- precision/recall em corpus rotulado;
- false positive qualification-vs-conflict;
- stale/supersession detection;
- incremental invalidation accuracy.

Coverage:

- requirement coverage precision;
- stale evidence rejection;
- missing edge detection;
- no lexical false satisfaction.

Readiness:

- blocker survival;
- deterministic replay;
- policy profile correctness;
- explanation completeness.

# Decisões fechadas

- semantic records/relations substituem substring heuristics;
- contradiction, coverage e readiness são engines separados;
- contradiction checks scope/validity/lineage;
- coverage é relationship/evidence-driven;
- evidence é revision/freshness-aware;
- readiness é policy + blockers, não um score mágico;
- typed Go rules primeiro, sem DSL genérica no MVP;
- LLMs geram candidates, não autoridade;
- avaliação incremental por affected graph;
- todos resultados possuem reason codes/provenance e são explicáveis.
