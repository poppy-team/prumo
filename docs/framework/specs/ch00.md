Esta página define as regras permanentes que devem orientar toda evolução do Project Atlas. Elas valem para humanos, agentes, plugins, conectores e automações.

## Clean Code como política obrigatória

Clean Code deve ser aplicado de forma pragmática. O objetivo não é maximizar abstrações, e sim tornar o sistema previsível, auditável e fácil de modificar.

### Regras

- Nomes devem expressar intenção e domínio, não implementação acidental.
- Funções devem ter responsabilidade coesa e contratos claros.
- Packages devem representar boundaries reais do domínio.
- Dependências devem apontar para abstrações estáveis quando houver benefício concreto.
- Evitar helpers genéricos sem semântica de domínio.
- Evitar singletons globais e estado implícito.
- Erros devem preservar contexto e causa.
- I/O deve ficar nas bordas; lógica de protocolo deve ser testável sem filesystem real quando possível.
- Comandos CLI devem ser adaptadores finos para serviços de aplicação.
- Schemas e invariantes devem ter um único dono lógico.
- Preferir composição a hierarquias complexas.
- Não criar interfaces antes de existir necessidade real de substituição/teste/integração.
- Não duplicar regras do Atlas em adapters.
- Não usar reflection ou metaprogramação quando uma estrutura explícita for suficientemente simples.

## Definition of Done do código

Uma mudança no Atlas Core só é concluída quando:

1. Compila e formata.
2. Passa testes unitários e relevantes de integração.
3. Passa conformance/golden tests quando altera protocolo.
4. Não cria dependência circular de package.
5. Possui tratamento explícito de erro.
6. Atualiza contratos/documentação afetados.
7. Produz evidência suficiente para o risco.
8. Não deixa TODO crítico sem registro.

## Governança das decisões

Classificar decisões em:

- **Canonical Decision:** aceita e incorporada ao protocolo/documentação.
- **Candidate Decision:** proposta ainda não aprovada.
- **Experiment:** hipótese a validar.
- **Rejected Approach:** opção deliberadamente recusada com justificativa.
- **Superseded Decision:** decisão anterior substituída por outra.

Decisões arquiteturais materialmente estáveis devem gerar ADR ou equivalente. Conversas não substituem ADRs.

## Authority hierarchy

1. Contratos e schemas bloqueados do Atlas.
2. Decisões canônicas/ADRs.
3. Goal/Plan/Task ativos e critérios de aceitação.
4. Documentação canônica especializada.
5. Recipes/skills/agents compilados.
6. Handoff e memória experiencial.
7. Contexto da sessão.

## Anti-overengineering guardrail

Antes de adicionar um novo serviço, package, banco, interface ou daemon, responder:

- Qual problema mensurável resolve?
- Por que o mecanismo atual não é suficiente?
- O recurso pode ser derivado ao invés de canônico?
- Existe custo de remoção?
- Precisa existir no core ou pode ser provider/plugin?

## Regra de portabilidade

Nenhum comportamento necessário para interpretar um projeto Atlas pode depender exclusivamente de um SaaS, LLM, IDE, plugin ou banco externo.
