# Baseline de standards

Usar OWASP Top 10 como awareness/risk map; OWASP ASVS como backbone de requisitos verificáveis; WSTG como catálogo de técnicas de teste; OWASP API Security Top 10 para APIs; NIST SSDF para práticas de desenvolvimento; OWASP SAMM para maturidade; OWASP SCVS/SBOM/provenance para supply chain.

## Threat families prioritárias

- broken access control / IDOR / BOLA;
- authentication/session/OAuth/OIDC failures;
- cross-tenant leakage e tenant context confusion;
- broken function/property-level authorization;
- injection (SQL/NoSQL/template/command/path/LDAP etc.);
- XSS/output encoding/CSP;
- SSRF e unsafe URL fetching;
- insecure file upload/content handling;
- business logic abuse, replay, race/concurrency e bypass de workflow;
- unrestricted resource consumption / rate abuse / noisy neighbor;
- secrets/credential exposure;
- insecure deserialization/data integrity;
- supply-chain, typosquatting, hallucinated dependencies;
- insecure defaults/misconfiguration;
- insufficient logging/audit/alerting;
- exception/failure-path mishandling;
- webhook verification/replay;
- cache/storage isolation failures;
- CI/CD confused-deputy and overprivileged agents;
- indirect prompt injection through issues/PRs/README/logs/web/MCP;
- tool/MCP poisoning, credential exfiltration and out-of-scope edits.

## SaaS tenant isolation

Todo projeto multi-tenant deve possuir modelo explícito de tenant context, recursos compartilhados, storage/cache/queue boundaries e matriz Actor × Tenant × Resource × Action. Testes negativos cross-tenant são obrigatórios para endpoints/flows relevantes.

## Authorization Contract

Representação machine-readable de atores, roles, resources, actions, ownership e tenant rules. Gerar automaticamente cenários: horizontal replay/IDOR, role demotion/vertical escalation, cross-tenant boundary, unauthenticated, stale session, revoked membership e ownership transfer.

## Business Logic Security

State machines e invariants de workflow devem ser documentados e testados. Valores sensíveis derivados no servidor; threat model inclui usuário desonesto; concurrency/race e anti-abuse são first-class test dimensions.

# Agentes especializados

### Security Architect / Threat Modeler

Read-only por padrão; identifica trust boundaries, assets, abuse cases, security requirements e risk tier.

### Authorization & Tenant Isolation Specialist

Focado em RBAC/ABAC/ownership/tenant boundaries e negative matrices.

### AppSec Static Analysis Specialist

Orquestra SAST, secrets, SCA, IaC/config e triagem de findings.

### Web/API Adversarial Tester

Cria e executa testes adversariais de API/business logic/authz.

### DAST Specialist

Configura ZAP e flows autenticados; correlaciona findings com routes/flows.

### Supply Chain & Secrets Specialist

SBOM, provenance, package verification, dependency risk e credential exposure.

### Security Verifier

Independente do implementador; confirma exploitability/fix/regression e evidence.

## Regra de independência

Mudanças high-risk em auth, tenant isolation, payments, secrets, admin, plugin execution, deserialization ou network boundary exigem verificador separado do implementador.

## Ferramentas/providers recomendados

CodeQL (SAST provider), Trivy (vulns/config/secrets/SBOM), OSV-Scanner ou Dependency-Check (SCA), ZAP Automation Framework (DAST), Semgrep opcional, Playwright para flows e auth context, scanners de secrets e policy-specific checks.

## Vibe Coding hardening

- validar pacote/nome/origem antes de adicionar dependency;
- tratar steering/rule files como security-critical;
- sandbox + least privilege + egress control para agentes quando possível;
- credenciais efêmeras/escopadas;
- MCP allowlist/review;
- proibir test deletion/fabrication para “passar CI”;
- validar alterações fora de scope;
- não confiar em texto de issue/PR/web como instrução privilegiada;
- security gates não podem ser desativados silenciosamente por prompt.
