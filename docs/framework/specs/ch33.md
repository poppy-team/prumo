# Profiles

Perfis principais:

- `game.core`
- `game.2d`
- `game.3d`
- `game.multiplayer`
- `game.simulation`
- `game.strategy`
- `game.action`
- `game.rpg`
- `game.procedural`
- `game.live-service`
- `game.engine-tooling`
- `game.editor-tool`
- `game.asset-pipeline`

Um projeto pode combinar vários perfis. Um editor 3D para assets, por exemplo, pode ativar `game.editor-tool + game.asset-pipeline + graphics`, sem ativar balanceamento de gameplay.

# Quality dimensions

O Game Quality Model deve avaliar separadamente:

1. **Correctness** — regras e invariantes estão corretas.
2. **Simulation stability** — o jogo mantém estado válido ao longo do tempo.
3. **Interaction quality** — inputs e feedback representam intenção do jogador.
4. **Game feel** — qualidade momento a momento, sem fingir que é totalmente automatizável.
5. **AI behavior** — decisões, navegação, robustez e custo.
6. **Physics/collision** — contatos, movimento, estabilidade e edge cases.
7. **Visual correctness** — render, shaders, câmera, animação, LOD e clipping.
8. **Audio feedback** — triggers, mix, spatialization e sincronismo quando aplicável.
9. **Balance & pacing** — distribuição de dificuldade, recursos, economia e tension curves.
10. **Level/map quality** — reachability, fairness, exploration, readability e flow.
11. **Performance** — CPU, GPU, memory, frame pacing, loading, streaming e stutter.
12. **Networking** — latency, jitter, packet loss, reconciliation, desync e authority.
13. **Content integrity** — assets, references, import, serialization e build.
14. **Player experience evidence** — playtests humanos continuam necessários para propriedades subjetivas.

# Test pyramid específica de jogos

```
Pure logic/property tests
        ↓
Simulation/headless tests
        ↓
Subsystem tests: AI / physics / animation / gameplay
        ↓
Scenario tests
        ↓
Automated playtesting / bots
        ↓
Visual + performance + network tests
        ↓
Human playtest / UX / gamefeel / balance validation
```

A regra é combinar automação com experimentação humana, não substituir uma pela outra.

# Engine e no-engine

O modelo é engine-agnostic. Engines são providers/adapters; os contratos de qualidade pertencem ao Atlas.

Primeiros adapters-alvo:

- Unreal Engine
- Unity
- Godot
- engine-agnostic native runtime
- frameworks/ECS customizados

Referências: Unreal Automation e Gauntlet oferecem testes unitários, funcionais, content stress, screenshot comparison e sessões multi-processo; Unity possui Edit/Play Mode Test Framework e Performance Testing; Godot expõe headless/profiling e pode usar providers comunitários como GdUnit4 para projetos.
