# Roadmap amendment — Agent Runtime Control Plane

A implementação do v0.4 deve agora considerar o Control Plane como infraestrutura horizontal necessária para tornar Skills, Experience, Quality e Connectors operacionais de forma confiável.

## Dependency ordering recomendado

1. **Control Plane contracts primeiro:** lifecycle de Run, `Run != ExecutorSession`, Portable Continuation/ContinuationRecord, failure taxonomy, Budget Envelope, Context Manifest, Tool Descriptor, Model Descriptor, Environment Contract e telemetry schema.
2. **Run + Context + Budget antes de automação avançada:** sem checkpoint/resume/cost/context control, automações amplificariam falhas.
3. **Tool Gateway + Model Router + Sandbox antes de connectors Level 4:** enforcement real exige mediação central.
4. **Observability desde o primeiro runtime:** toda feature de execução deve nascer explicável e medível.
5. **Harness Eval Suite antes de otimizar heurísticas:** context packing, workforce e routing só são promovidos por comparação com baseline.
6. **Package/Runtime Manager antes de multiplicar providers:** Playwright, fuzzers e adapters multi-runtime precisam instalação isolada e reprodutível.
7. **Migration Engine antes de proliferar schemas v0.4:** projetos reais precisarão evoluir sem reinstalação destrutiva.

## Novos deliverables obrigatórios do v0.4

- Budget/Cost Manager + rate-limit policy;
- Context Compiler + tool-output budgets + compaction/checkpoints;
- Run Engine + resume/cancel/retry/idempotency;
- Portable Continuation Protocol (`ExecutorSession`, `ContinuationRecord v1`, `atlas continue`) para continuidade entre sessions/models/harnesses sem connector obrigatório;
- Tool Gateway + MCP governance + lazy discovery;
- Model Registry/Router + drift/canary/fallback;
- Execution Environment/Sandbox contract;
- Observability Plane + incident bundle;
- event-driven Automation Engine + DLQ;
- Atlas Package/Runtime Manager + `atlas.lock`;
- Migration Engine + Unified Review Queue;
- incremental repo indexing + branch/monorepo/concurrency model;
- data classification + egress + SecretProvider;
- Atlas Harness Eval Suite.

## Priority guardrail

Não adicionar novas famílias grandes de Skills/Providers antes que os mecanismos horizontais necessários para ativá-las, orçamentá-las, observar e verificar seu comportamento existam. Exceções devem ser reference implementations usadas para validar os próprios contracts.

O roadmap histórico M0–M12 continua útil como mapa de evolução, mas a implementação deve seguir o dependency DAG e os Exit Gates do Programa 63. Antes de iniciar cada fase, revalidar o estado real do repositório e detalhar somente o current Goal/next dependency necessário; não reabrir invariants já fechados sem amendment explícito.
