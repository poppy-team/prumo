## Run como entidade formal

Uma Run executa um Plan/Task e possui lifecycle persistível.

State machine mínima:

```
created → planning → ready → running
running → waiting_approval | waiting_resource | retrying | verifying | blocked
verifying → completed | failed
qualquer estado ativo → cancelled
```

Transições inválidas são rejeitadas pelo Core.

## Checkpoint

Checkpoint é diferente de Handoff. Ele responde: **se o processo morrer agora, consigo reconstruir o estado?**

Deve registrar run/task, phase, workspace hash/ref, completed/pending steps, evidence pointers, pending side effects, budget snapshot e resume token lógico.

## Retry taxonomy

Classificar: rate-limit, timeout, provider 5xx, tool failure, invalid structured output, policy denied, product/test failure, environment failure e unknown. Cada classe possui retryability distinta.

Retries têm budget próprio e nunca convertem falha em sucesso silencioso.

## Action idempotency

Ações side-effecting devem receber idempotency key quando o provider/tool suportar. Atlas registra intenção e resultado antes/depois da ação para evitar duplicação após timeout.

## Resume

Resume reconstrói a partir de estado canônico + checkpoint + working state válido; não depende da memória privada do modelo anterior.

## Run != Session

`Run` é a identidade operacional durável do trabalho. `ExecutorSession` representa uma associação temporária com um agent/model/harness. Troca de quota, modelo, Code Agent, compaction ou host pode encerrar uma `ExecutorSession` e iniciar outra sem criar nova Run.

**Invariant:** nenhuma Run ativa pode exigir histórico privado de sessão/chat para continuar.

## Portable Continuation baseline

Toda Run ativa deve poder projetar um `ContinuationRecord v1` suficiente para um executor fresco reidratar o estado: Goal/Task/Run, branch/revision/dirty state, completed/current/pending steps, accepted decisions/constraints, evidence, blockers, pending/unknown side effects, relevant files e next steps.

O novo executor não recebe simplesmente o prompt anterior: Context Compiler recompila um Context Manifest para suas capabilities, model window, policy e budget atuais.

A continuidade básica deve funcionar sem connector nativo via `atlas continue`/JSON/generic prompt path. Handoff avançado em Experience adiciona síntese, claim/lease e conhecimento episódico, mas não é pré-requisito para resumability básica.

Referência: [77 — Portable Continuation Protocol: Continuidade Agnóstica de Session, Model e Harness](../../development/phases/phase-77.md).

## Cancellation

Cancellation deve propagar para subagents/providers quando possível, preservar evidence parcial e executar cleanup seguro.

## Livelock detection

Detectar repetição de tool/erro, ausência de repository/evidence delta, cyclic delegation e token burn sem progresso. Resultado: checkpoint + diagnóstico + stop ou escalation conforme policy.
