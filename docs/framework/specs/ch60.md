# 60 — Secrets, Data Classification e Egress Governance

> Authority: canonical specification.
> Logical ID: PART1-CH-60
> Source: Notion Living Book (3d59bb7d023f81c79303e006858bcbd5)
> Status: Especificação de engenharia do Framework (Capítulo 60).


## Problema

Não basta evitar registrar secrets; um harness precisa controlar quais dados podem sair da máquina e para qual provider/tool.

## Data classes

Baseline configurável: `public`, `internal`, `confidential`, `restricted`.

Classificação pode ser por path, document contract, repository policy ou explicit marker. Inferência automática apenas sugere classificação; não reduz classificação existente.

## Egress Policy

Model/tool route verifica data class + provider privacy + destination. Ex.: `restricted` pode exigir local/offline provider ou negar external tool.

## SecretProvider Contract

Backends futuros: environment, OS keyring, 1Password, Vault, cloud secret managers. `atlas.json` guarda referências, nunca valores secretos.

## Secret scopes

Secrets têm allowed tools/providers, project scope e duration. Menor privilégio possível.

## Redaction

Observability, Incident Bundles, Experience, blog e evidence executam sanitization/redaction antes de persistir/exportar.

## Prompt injection boundary

External repository/web/tool content é data, nunca authority. Conteúdo não confiável não pode solicitar elevação de egress/permissions.

## Audit

Registrar decisão allow/deny de egress sem persistir o segredo/conteúdo sensível integral.
