# 26 — Native Desktop GUI Test Bridge

> Authority: canonical specification.
> Logical ID: PART1-CH-26
> Source: Notion Living Book (3d59bb7d023f812b9ea4f4d7c8a134e8)
> Status: Especificação de engenharia do Framework (Capítulo 26).


Criar uma abstração Atlas de automação GUI desktop com locators semânticos e drivers por plataforma. O core não deve depender de um framework comercial específico.

## Provider family

`gui.native` com drivers:

- `gui.windows-uia` — Microsoft UI Automation;
- `gui.macos-ax` — macOS Accessibility/AXUIElement;
- `gui.linux-atspi` — AT-SPI2;
- `gui.macos-xcui` — provider opcional para apps/test bundles adequados;
- `gui.qt-squish` — provider opcional comercial para equipes que usam Squish.

## Locator model comum

`role`, `name`, `automation_id`, `label`, `value`, `description`, `state`, `parent`, `relation`. Providers fazem capability negotiation; não fingir que toda plataforma expõe o mesmo nível de informação.

## Por que accessibility tree

Testes ficam mais robustos que coordenadas, validam uma superfície real de acessibilidade e reduzem dependência de resolução/tema. Como efeito positivo, componentes custom precisam oferecer semântica acessível para serem facilmente testáveis.

## Test layers

### Semantic UI

Abrir app, encontrar elementos por role/name/id, executar ações, validar state/value/focus/visibility.

### Interaction

Keyboard shortcuts, focus navigation, menus, drag/drop quando provider suporta, modal lifecycle, clipboard, file dialogs via harness apropriado.

### Visual

Screenshot regression secundária com environment fingerprint, masking/tolerances e golden review.

### Accessibility

Tree completeness, names/roles/states, focus order e keyboard access; checks específicas por plataforma.

## Atlas GUI Scenario format

Provider-neutral scenario pode representar steps/expectations e compilar para driver. Não criar DSL excessiva no v0.4; começar por schema simples e adapter API.

## CI

Windows runner para UIA, macOS runner para AX/XCTest quando requerido, Linux desktop session/Xvfb/Wayland-compatible runner para AT-SPI. `atlas doctor gui` verifica sessão gráfica, accessibility bus e permissions.

## Crash/evidence

Capturar exit code, crash dump pointer quando disponível, app logs, accessibility snapshot, screenshot, action timeline e environment.

## Ferramentas legadas/alternativas

LDTP pode inspirar padrões AT-SPI, mas não deve ser dependência central. Squish é opcional. Coordinate-only automation fica fallback de última escolha.
