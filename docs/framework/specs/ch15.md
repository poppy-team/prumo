# Recomendações adicionais aprováveis

Esta página registra incrementos derivados da nova arquitetura que merecem entrar no backlog, sem obrigar o core inicial a implementá-los todos.

## 1. Atlas Doctor 2.0

Além de schema/health:

- connector compatibility;
- stale docs;
- orphan goals/tasks;
- trace gaps;
- dangling knowledge edges;
- dirty generated adapters;
- install ownership inconsistencies;
- SQLite rebuildability;
- risk policy contradictions.

## 2. `atlas diff --knowledge`

Mostrar impacto semântico de uma mudança Git: capabilities, docs, ADRs, tests e Goals afetados.

## 3. Documentation Linter

Validar headings/roles, links, tokens, required sections, freshness metadata e contradictions simples.

## 4. Generated Manifest

Todos os outputs compilados por harness devem estar num manifest com hash/source/version para detectar edição manual e fazer merge seguro.

## 5. Workspace/Monorepo Model

Planejar projects/subprojects com inheritance explícita de policies, skills e docs. Não assumir um único package por repository.

## 6. Policy Packs

Perfis como `strict`, `standard`, `prototype`, `regulated` alteram gates/ceremony sem mudar o protocolo base.

## 7. Offline-first

Todos os comandos determinísticos devem funcionar sem rede. LLM/provider só é exigido em funções explicitamente inteligentes.

## 8. MCP Server oficial

`atlas mcp serve` expõe status, trace, docs, context, goals e validators a qualquer harness MCP, funcionando como connector universal de baixo acoplamento.

## 9. Atlas Language Server futuro

Opcionalmente expor diagnostics para `atlas.json`, schemas, Goal refs e semantic links em editores.

## 10. Project Snapshot / Reproducible Briefing

Gerar um briefing determinístico pequeno de projeto para auditoria, handoff ou issue externa.

## 11. Capability Registry

Capabilities devem ser identificadores estáveis e compostos, evitando inferência por nomes de arquivos. Ex.: `ui.desktop`, `compiler.parser`, `storage.sqlite`.

## 12. Documentation Budget

Além de token budget de contexto, definir `documentation proportionality`: projetos pequenos não recebem packs gigantes; risk/capabilities controlam profundidade.

## 13. Invariant Registry

Centralizar invariantes críticas com id, severity, checker e documentation pointer. Gates e connectors referenciam IDs, não strings duplicadas.

## 14. Compatibility Ledger

Registrar versões de protocol, connector e host testadas em CI.

## 15. Self-hosting dogfood

O próprio Project Atlas deve ser o primeiro projeto completamente gerenciado pelo v0.4. Toda feature nova deve demonstrar como o Atlas documenta, implementa e verifica a si mesmo.

# Princípio de priorização

Implementar primeiro o que aumenta **correção, portabilidade, reversibilidade e qualidade de contexto**. Dashboard visual, servidor compartilhado, embeddings e features sofisticadas entram somente quando uso real demonstrar necessidade.
