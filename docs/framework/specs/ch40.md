# Frame budget

Exemplo conceitual para 60 FPS:

```
frame budget ≈ 16.67 ms
```

O Atlas não deve assumir 60 FPS; target vem da documentação do projeto.

Budgets podem ser repartidos por:

- game thread;
- render thread;
- GPU;
- physics;
- AI;
- animation;
- audio;
- UI;
- streaming;
- networking.

# Metrics

Coletar distributions, não somente médias:

- median;
- p95;
- p99;
- worst frame;
- hitch count;
- frame-time variance;
- CPU/GPU overlap;
- allocations/frame;
- memory high-water mark;
- loading/streaming stalls.

# Regression gates

Budget regressions podem bloquear release mesmo com testes funcionais verdes.

Exemplo:

```
p95 frame time <= project budget
p99 hitch <= allowed threshold
memory <= platform budget
```

# Target hardware profiles

Performance precisa ser medida em profiles reais:

- minimum spec;
- recommended;
- handheld/mobile;
- console tiers;
- low-end integrated GPU quando aplicável.

# Engine adapters

- Unreal Insights / built-in stat/profiling providers;
- Unity Performance Testing + Memory Profiler;
- Godot Profiler + Visual Profiler;
- Nsight Systems/Graphics quando GPU NVIDIA é relevante;
- RenderDoc/provider futuro para frame inspection.

Godot recomenda profiling para localizar bottlenecks e separa CPU profiler de visual rendering profiler. Unity possui Performance Testing API e Memory Profiler. Nsight Systems fornece timeline system-wide de CPU/GPU e atividade do sistema.

# Optimization review rule

Toda otimização relevante deve declarar:

- observed bottleneck;
- measurement method;
- baseline;
- change;
- after measurement;
- complexity cost;
- portability impact.

Clean Code continua valendo, mas performance-critical code pode aceitar complexidade localizada quando respaldada por measurement e documentação.
