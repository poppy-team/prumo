A fundação de testes de gameplay deve ser **simulação controlável e reproduzível**.

# Simulation Contract

Quando tecnicamente possível, gameplay deve poder executar com:

- fixed timestep configurável;
- RNG seed explícito;
- input stream gravável;
- snapshots/checkpoints;
- relógio virtual ou controlável;
- headless mode;
- rendering/audio opcionais;
- observabilidade de eventos e estado;
- deterministic hashes quando a arquitetura permitir.

# Replay Contract

Formato de replay recomendado:

```json
{
  "build": "...",
  "scenario": "combat.arena-03",
  "seed": 42,
  "fixed_dt": 0.0166667,
  "inputs": [],
  "checkpoints": [],
  "expected_invariants": []
}
```

Não exigir determinismo bit-a-bit em engines/plataformas onde isso não é garantia; registrar o nível de determinismo efetivamente suportado.

# Scenario tests

Cada mecânica relevante deve poder possuir pequenos cenários reproduzíveis:

- movimento;
- combate;
- inventário;
- crafting;
- quests;
- economia;
- checkpoints/save-load;
- interação com objetos;
- streaming/level transition;
- multiplayer/reconnect.

# Automated Playtesting

Três famílias distintas:

1. **Scripted bots** — trajetórias e ações conhecidas para regressão.
2. **Search/simulation agents** — exploram espaço de estados e procuram falhas ou estratégias degeneradas.
3. **Learned agents/RL** — úteis para exploração e representação de diferentes playstyles, mas não devem ser tratados como jogadores humanos universais.

Pesquisa da Ubisoft/AIIDE mostrou RL condicionado por estilos para automated playtesting mais representativo; isso justifica um provider de playtest agents, mas não substitui estudos com jogadores.

Fonte: [https://ojs.aaai.org/index.php/AIIDE/article/view/21958](https://ojs.aaai.org/index.php/AIIDE/article/view/21958)

# Coverage de gameplay

Não usar apenas line coverage. Coletar, quando aplicável:

- mechanic coverage;
- state-machine/BT node coverage;
- ability/action coverage;
- map-region coverage;
- item/weapon/enemy coverage;
- quest branch coverage;
- damage/death cause distribution;
- nav link usage;
- interaction coverage;
- network condition coverage.

# Simulation fuzzing

Gerar sequências de ações e seeds sob invariantes:

- nunca NaN/Inf em estado permitido;
- vida/recursos respeitam constraints;
- entidades removidas não permanecem referenciadas;
- save-load preserva estado esperado;
- nenhuma transição impossível;
- progressão não entra em dead-end indevido;
- economia não cria recursos sem causa definida, salvo design explícito.

# Long-run / soak

Executar milhares/milhões de ticks em headless para procurar:

- leaks;
- drift numérico;
- acumuladores sem bound;
- crescimento de entidades;
- deadlocks/livelocks;
- AI stuck;
- memory fragmentation;
- degradação progressiva.

# Human checkpoint

Automated playtesting produz sinais e hipóteses. Balance, gamefeel, legibilidade e emoção exigem validação humana antes de serem classificados como `verified`.
