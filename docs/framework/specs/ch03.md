# 03 — Documentation Contracts, Profiles e Qualidade Documental

> Authority: canonical specification.
> Logical ID: PART1-CH-03
> Source: Notion Living Book (3d59bb7d023f81a6b307fb72e510ff9c)
> Status: Especificação de engenharia do Framework (Capítulo 03).


Transformar documentação de “arquivos que existem” em **artefatos com contratos verificáveis de profundidade, aplicabilidade, freshness e rastreabilidade**.

## Documentation Contract

Cada tipo documental define campos/cobertura obrigatórios, opcionais e condicionais. O gate avalia informação, não nome do arquivo.

### Estados de coverage

- `missing`
- `partial`
- `implementation-ready`
- `verified`
- `stale`
- `not-applicable`

### Propriedades recomendadas

- contract id e version;
- semantic role;
- applicability rules;
- required knowledge sections;
- blocking questions;
- evidence requirements;
- update triggers;
- owners/agentes elegíveis;
- staleness policy;
- canonical source pointers.

## Documentation Profiles

Perfis ativam conjuntos de contratos conforme capabilities detectadas.

### Perfis iniciais

- Core Software
- CLI
- Desktop GUI
- Web Application
- Mobile
- API/Service
- Database/Data Platform
- Compiler
- Programming Language
- Game Engine
- Graphics/Rendering
- Plugin Host/SDK
- Library/Package
- Distributed System

## Core documentation pack

Para projetos não triviais, considerar:

- Product Vision
- Scope / Non-goals
- Feature Catalog
- Glossary
- Architecture Overview
- Component Contracts
- Data/State Model
- Error Model
- Security & Trust Model
- Test Strategy
- Performance Expectations
- Operations/Diagnostics
- Compatibility Policy
- Dependency Policy
- Risk Register
- Assumption Register
- Known Limitations
- Technical Debt Register
- Decision Log / ADRs
- Implementation Journal
- Traceability

## Readiness

`atlas docs readiness` deve diferenciar:

- completeness geral;
- completeness do Goal atual;
- blockers para implementação;
- gaps não bloqueantes.

Nunca exigir 100% documental para mudanças triviais.

## Documentation Delta

Mudanças em código/contratos produzem um impacto estruturado:

```json
{
  "changed_capabilities": ["parser.typed-declaration"],
  "impacted_documents": ["language.syntax", "compiler.parser"],
  "severity": "material",
  "requires_review": true
}
```

O Documentation Maintainer/Knowledge Curator atualiza somente os documentos realmente afetados.

## Document ownership

Cada semantic role tem owner lógico. Exemplo: architecture pelo Architect/Knowledge Curator; user docs pelo Documentation Maintainer; design system pelo UI specialist; critérios locked por Goal governance.

## Contradiction detection

Ao aceitar nova decisão, comparar com conhecimento canônico e gerar explicitamente:

- conflito detectado;
- fonte antiga;
- nova decisão;
- superfícies afetadas;
- migration delta.

## Nova recomendação — Evidence-backed documentation

Se uma afirmação técnica pode ser verificada automaticamente, o documento deve apontar para uma evidência ou teste. Ex.: formatos suportados, versões, benchmarks, APIs e guarantees.

# Amendment 2026-09-21 — Total Assurance

[84 — Total Assurance Constitution: Gauntlet Loop, Evidence e Anti-False-Green](../../quality/gauntlet-84.md) torna-se metacontrato transversal deste sistema. Documentation Contracts devem incluir, quando aplicável, behavioral/negative guarantees, failure/recovery, state/resource ownership, NFR budgets, compatibility/migration, oracle/evidence requirements, freshness dependencies e known unknowns. Readiness deixa de significar apenas “conteúdo suficiente para implementar”: também precisa permitir **provar** a implementação e detectar drift posterior.

# Amendment 2026-09-21 — Canonical Truth e Arquitetura Documental v2

[85 — Canonical Truth, Authority Graph e Constituição Anti-Invenção](../../contracts/llm-agent-execution-contract.md) passa a definir authority, supersession, UNKNOWN, assumptions e anti-invention para todos os Documentation Contracts.

[88 — Arquitetura Documental v2: Canonical Graph, IR, Microcontextos e Promotion](../../architecture/documentation-architecture-v2.md) consolida o fluxo Knowledge IR → Document IR → Implementation Dossier → microcontextos → promotion.

A partir desta emenda, readiness documental não mede apenas presença de informação. Também deve comprovar:

- autoridade da fonte;
- freshness;
- distinção planned/implemented/verified;
- absence de contradiction P0;
- unknowns/assumptions explícitos;
- provenance;
- capacidade de compilar contexto mínimo suficiente para a task;
- capacidade de provar a implementação posteriormente.

**Regra:** documentação insuficiente gera GAP/UNKNOWN, nunca preenchimento plausível por LLM.
