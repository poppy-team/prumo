## Repository Scale Engine

Adoption/retrieval não podem rescanner grandes repos a cada mudança. Usar hashes, Git diff, directory sharding, generated/vendor ignores, binary detection e invalidation incremental.

## Index strategy

Persistir derived indexes por content hash e parser/version. SQLite deve ser rebuildable; stale index nunca supera Git/canonical state.

## Huge repo budgets

Scanning tem budget de files/bytes/time e pode produzir partial confidence explicitamente em vez de fingir cobertura total.

## Branch awareness

Distinguir canonical mainline, branch-local working state e proposals. Experience/documentation de uma feature branch não é automaticamente verdade da main branch antes de merge.

## Monorepo model

```
Repository
└── Workspace
    ├── Project A
    ├── Project B
    └── Project C
```

Inheritance explícita para policies/skills/contracts; projects podem sobrescrever somente o que authority rules permitem.

## Task leases

Em execução concorrente, task pode possuir lease com owner/expiry/heartbeat. Evitar dois agentes executando a mesma task sem intenção.

## Workspace/file claims

Claims temporários reduzem colisão entre agents; não substituem Git merge. Canonical docs preferem patch proposals + merge engine.

## Conflict policy

Conflito não resolvido interrompe merge automático e cria review item/evidence de conflict.
