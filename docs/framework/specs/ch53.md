# 53 — Model Registry, Router, Drift, Fallback e Provider Health

## Model Registry

Metadados não devem ficar espalhados em condicionais. Registrar provider/model, context/modalities, structured-output/tool support, reasoning controls, cache features, privacy/data policy, pricing metadata, rate-limit profile, latency class e Atlas eval history.

## Model Router

Entradas: task class, complexity, risk, context need, tools, modality, latency/cost budget, privacy/data classification e eval scores.

Saída deve ser explicável: route + alternatives + policy constraints.

## Eval-driven routing

Roteamento usa benchmarks internos por task class. Reputação pública pode orientar experimentos, nunca substituir evals do Atlas.

## Model drift

Registrar model ID/revision quando disponível e data da avaliação. Mudanças de alias/provider disparam shadow eval/canary antes de promoção para rotas críticas.

## Fallback

Separar reasoning retry de action retry. Nunca replayar side effects por trocar de modelo. Fallback preserva checkpoint e tool journal.

## Provider health

Circuit breaker por provider/model para falhas repetidas. Health não altera invariants; apenas reduz rotas disponíveis.

## Independent verification

Policies podem exigir modelo/provider/verificador diferente do implementador em segurança, migrations ou risco high/critical.

## Offline/local

Model Registry deve suportar modelos locais no futuro sem tornar cloud obrigatório; data-egress policy pode obrigar rota local.
