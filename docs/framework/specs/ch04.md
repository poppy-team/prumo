# 04 — UI/UX Documentation Pack Completo

> Authority: canonical specification.
> Logical ID: PART1-CH-04
> Source: Notion Living Book (3d59bb7d023f81a49cfdefbee7c1b202)
> Status: Especificação de engenharia do Framework (Capítulo 04).


Uma UI importante deve poder ser reconstruída com alto grau de fidelidade por outra equipe lendo a documentação, sem depender de screenshots soltos ou memória do autor.

## Cobertura obrigatória do profile Desktop/Web UI

### 1. Product UX

- objetivos da interface;
- personas/usuários quando aplicável;
- tarefas primárias;
- princípios de interação;
- densidade informacional desejada;
- restrições de plataforma.

### 2. Information Architecture

- áreas da aplicação;
- navegação global/local;
- hierarchy;
- flows principais;
- entry/exit points.

### 3. Screen Inventory

Cada tela/workspace/modal/panel relevante deve possuir identificação e responsabilidade.

### 4. Wireframes semânticos

Wireframe não deve ser somente imagem. A fonte deve possuir layout estruturado e dimensões/tokens; SVG/PNG pode ser derivado.

### 5. Layout specification

Para cada tela:

- reference viewport;
- regions;
- widths/heights mínimas/ideais/máximas;
- resizing behavior;
- splitters;
- grid;
- padding/margins;
- alignment;
- overflow;
- z-order quando relevante.

### 6. Design tokens

- color primitives e semantic colors;
- typography families/sizes/weights/line-height;
- spacing scale;
- border widths;
- radii;
- shadows/elevation;
- opacity;
- motion durations/easing;
- icon sizes;
- control heights;
- density modes.

Preferir tokens versionados em JSON quando possível.

### 7. Typography

Registrar família, fallback, licença/origem, tamanhos por role, weight, line-height, letter spacing, monospace/editor font e comportamento de ligatures quando aplicável.

### 8. Components

Para cada componente:

- purpose;
- anatomy;
- props/inputs;
- variants;
- normal/hover/pressed/focus/disabled/loading/error;
- keyboard behavior;
- accessibility semantics;
- tokens usados;
- edge cases.

### 9. Interaction specification

- mouse;
- keyboard;
- touch/gesture quando aplicável;
- drag/drop;
- selection;
- multi-selection;
- focus;
- context menus;
- undo/redo;
- feedback timing.

### 10. State catalog

Obrigatório avaliar:

- empty;
- loading;
- error;
- no selection;
- multiple selection;
- partial data;
- read-only;
- offline;
- unsaved;
- conflict;
- permission denied.

### 11. Accessibility

- focus order;
- keyboard-only operation;
- contrast;
- screen reader semantics quando aplicável;
- reduced motion;
- text scaling;
- color-independence;
- shortcut discoverability.

### 12. Localization

- text expansion;
- RTL quando aplicável;
- pluralization;
- locale-sensitive numbers/dates;
- no strings baked into pixels.

### 13. Theming

Dark/light/custom themes, semantic tokens e inheritance.

### 14. Visual regression

Definir reference screens, deterministic state fixtures e tolerâncias.

## Exemplo de especificação de região

```
Properties Panel
ideal-width: 280px
min-width: 220px
max-width: 420px
resizable: true
padding-inline: spacing.3
background: surface.1
border-left: border.subtle
```

## Wireframe renderer futuro

Criar um renderer opcional capaz de gerar SVG a partir de uma representação declarativa de layout. A imagem é derivada; o modelo semântico permanece canônico.

## Gate UI implementation-ready

Bloqueadores típicos:

- navigation flow indefinido;
- estados críticos sem definição;
- tokens essenciais ausentes;
- componente central sem comportamento de interação;
- conflito entre wireframe e design system.

# Amendment 2026-09-21 — Interaction Assurance

[84 — Total Assurance Constitution: Gauntlet Loop, Evidence e Anti-False-Green](../../quality/gauntlet-84.md) e sua página 84.E endurecem o profile UI. Além de screen/component documentation, toda UI material deve possuir Interaction Manifest, reachability coverage, dead-control gate, microinteraction coverage, proof-of-use, first-run/clean-state flow, DPI/responsive/localization matrix e relação explícita entre command/action → state mutation → feedback → Undo/recovery → evidence. Screenshot isolado nunca satisfaz implementation-ready nem verified.
