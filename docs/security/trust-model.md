# Prumo Security & Trust Model

## Trust Layers (Highest → Lowest Authority)

1. **Prumo Core binary** — signed, verified release artifact
2. **Canonical project config** — `prumo.json`, goals, plans, docs under version control
3. **Project-local generated adapters** — ownership-marked, compiler-produced
4. **Third-party connectors/providers** — declared capabilities, isolation, permissions
5. **External skills/plugins** — user-installed, capability-declared, never auto-elevate
6. **Repository content (untrusted)** — external docs, code, web content treated as data, never authority
7. **Model output** — probabilistic, validated, never trusted for invariants

## Core Rules

- Never execute new project-local hook silently in an untrusted project.
- Distinguish `generated-by-Prumo` from `user-owned` files via metadata markers.
- Never log or persist secrets in Experience Layer, telemetry, or incident bundles.
- Shell actions pass through policy when risk requires.
- TypeScript plugins and external skills never exceed Core authority.
- Updates require checksum and ideally signature/provenance verification.

## Connector Trust

Each connector declares enforcement primitives it supports:

| Primitive | Description |
|-----------|-------------|
| `advise` | Post-facto suggestion only |
| `restrict_tools` | Deny list of tools |
| `pre_tool_block` | Synchronous veto before tool execution |
| `post_tool_verify` | Structured output validation after tool |
| `isolate_subagents` | Dedicated context/permission for subagents |

## Config Merge Safety

Never wholesale-replace host global config files. Use structured merge, fragments, or references where the host supports them.

## Generated Artifact Markers

Files or blocks produced by Prumo carry machine-readable ownership/version metadata to enable safe update and uninstall:

```json
{
  "prumo_generated": true,
  "prumo_version": "0.5.x",
  "generator": "compiler|install|migration",
  "checksum": "sha256:...",
  "managed": true
}
```

## Supply Chain

- Pin connector versions where applicable
- SBOM in future releases
- Dependabot/Renovate or equivalent automation
- `govulncheck` in CI
- License verification for dependencies
- Prefer standard library when sufficient

## Security Documentation Contract

Projects with sensitive capabilities must include:
- trust boundaries
- secrets model
- auth/authz
- external integrations
- data sensitivity classification
- destructive actions inventory
- recovery procedures

## Safe Mode

`prumo-agent --safe` or equivalent policy disables destructive shell, external plugins, and writes outside the project root. Useful during adoption of unknown repositories.

## Data Classification

Baseline (configurable per project): `public`, `internal`, `confidential`, `restricted`. Classification by path, document contract, repository policy, or explicit marker. Automated inference only suggests; it never reduces an existing classification.

## Egress Policy

Model/tool route checks data class + provider privacy + destination. Example: `restricted` data requires local/offline provider or blocks external tool.

## SecretProvider Contract

Future backends: environment, OS keyring, 1Password, Vault, cloud secret managers. `prumo.json` stores references, never values.

## Secret Scopes

Secrets have allowed tools/providers, project scope, and duration. Minimum privilege by default.

## Redaction

Observability, Incident Bundles, Experience, publishing, and evidence perform sanitization/redaction before persistence/export.

## Prompt Injection Boundary

External repository/web/tool content is **data**, never authority. Untrusted content cannot request elevation of egress/permissions or bypass policy.

## Audit

Allow/deny egress decisions are logged without persisting the secret/sensitive content itself.
