# Design Critique Skill Package

## 1. Purpose
The purpose of this skill is to facilitate structured, constructive, and actionable design critiques and reviews. It distinguishes between collaborative critique (for craft improvement during design) and formal reviews (milestone checkpoints for stakeholder approval), using criteria-based evaluation and formalized feedback protocols.

## 2. Use When
- Evaluating design deliverables (mockups, prototypes, wireframes).
- Providing asynchronous or synchronous feedback on UI/UX work.
- Conducting milestone design reviews for stakeholder approval.
- Defining the rationale behind design decisions.

## 3. Do Not Use When
- The design is in early unstructured brainstorming (brainstorming needs exploration, not formal critique).
- Providing feedback on code implementation (use code review skills instead).
- Evaluating project timelines or budget constraints.

## 4. Required Context
- Clear understanding of the problem space and user goals.
- Explicit definition of the scope of feedback requested (e.g., visual design, UX flow, accessibility).
- Access to the design artifacts (e.g., Figma links, prototypes) and any existing design system guidelines.

## 5. Procedure
1. **Context Setting:** Review the problem statement, goals, and the requested scope of feedback.
2. **Evaluation:** Assess the design against key criteria:
   - Usability and user flow.
   - Strategic alignment with business goals.
   - Brand consistency and design system adherence.
   - Visual quality (typography, spacing, color).
   - Accessibility compliance (WCAG standards).
   - Technical feasibility.
   - Content clarity and voice.
3. **Drafting Feedback:** Formulate feedback using the 'I notice...', 'I wonder...', 'What if...' framework.
4. **Severity Assignment:** Assign severity to identified issues:
   - 1 = Cosmetic
   - 2 = Minor usability issue
   - 3 = Major usability issue
   - 4 = Catastrophe/Blocker
5. **Documentation:** Compile the feedback into a structured critique report or decision log, capturing trade-offs and rationale.

## 6. Decision Rules
- Focus feedback on the work, not the person.
- Frame feedback as questions or observations rather than definitive statements.
- Prioritize issues based on severity and impact on the primary user goal.
- Feedback must be actionable and specific.

## 7. Evidence Required
- A completed Critique Report or Feedback Log.
- Documented severity ratings for identified issues.
- Clear alignment of feedback with the requested scope.

## 8. Output Contract
- **Critique Report:** A structured document detailing context, evaluation criteria, specific feedback points with severity ratings, and actionable recommendations.
- **Decision Log:** A log capturing trade-offs, rationale, and alternatives considered during the review.

## 9. Stop Conditions
- All elements within the requested feedback scope have been evaluated.
- The Critique Report and Decision Log have been finalized and delivered.

## 10. Escalation Rules
- Escalate to the Lead Designer or Product Manager if technical feasibility is fundamentally compromised.
- Escalate to stakeholders if the design completely misaligns with core business strategy.
